---------------------------------------------------------------------

현재 공통 기준:

- 실제 운영 대상은 지상 로봇 4대 H1, H2, B1, B2다.
- 기본 관측안은 고정 카메라 2대이며 드론은 선택 비교안이다.
- 아래 본문의 2~3대 또는 6대 표현 중 의사결정 역사와 이전 시뮬레이터를
  설명하는 부분은 보존 기록이다. 현재 실물 수량과 다음 작업 판단에는 이
  인계 부분과 docs/SOFTWARE_PLAN_KO.md의 최신 상태를 우선 적용한다.
- 구현 기준 부모는 origin/main a93376b이며 실제 비전 구현 커밋은 ef5e020이다.

완료한 소프트웨어 - 같은 기능을 별도로 다시 구현하지 말 것:

1) M2 실제 영상 입력 및 경기장 보정
   - USB/웹캠과 로컬 영상 파일 입력
   - 읽기 시작/완료 시각, 프레임 번호, 재생 시간축 기록
   - 네 모서리 TL -> TR -> BR -> BL 보정과 픽셀 <-> 경기장 mm 변환
   - 보정 JSON 저장/불러오기, 독립 기준점 오차 검사
   - 오래됨, 역순, 영상원 변경, 해상도 변경, 잘못된 영상의 fail-closed 거부
   - 명령: python -m robo_control.vision calibrate/run/check

2) M3 실제 영상의 로봇 AprilTag 프레임 관측
   - OpenCV DICT_APRILTAG_36h11 ID 0,1,2,3을 H1,H2,B1,B2에 기본 배정
   - 실제 사진, 실제 카메라, 녹화 영상에서 태그 ID, 중심, 로봇 회전중심,
     경기장 mm 위치와 방향 rad 출력
   - 로봇별 태그 장착각과 태그 중심 -> 회전중심 오프셋 설정
   - 미등록 ID, 중복 ID, 누락, 경기장 밖, 잘못된 투영, 태그 크기 불일치를
     관측에서 제외하고 임의 위치를 만들지 않음
   - 흰 quiet zone이 포함된 인쇄용 태그와 전방 확인 이미지 생성기
   - JSONL 프레임 로그, 주석 이미지/미리보기, 검출 후 지연 재검사
   - 명령: python -m robo_control.vision detect

3) 자동 검증과 문서
   - vision 환경 Python 회귀시험 172개 통과
   - OpenCV 없는 기본 환경도 전체 시험 통과(vision 시험 87개 skip)
   - 웹 회귀시험 26개 통과
   - Windows/Linux에서 vision 의존성을 설치하는 CI 작업 추가
   - 사용법: docs/CAMERA_CALIBRATION_KO.md, docs/APRILTAG_TRACKING_KO.md

아직 완료하지 않은 소프트웨어 - 팀원이 새 작업으로 맡을 수 있는 범위:

1) 여러 프레임을 잇는 로봇 추적과 검출 손실 500ms 안전정지 watchdog
2) 빨강/노랑/초록 HSV 물체 검출, 조명별 보정과 물체 ID 추적
3) 고정 카메라 2대의 카메라별 보정 관리, 시간 동기화, 중복 관측 융합
4) 비전 관측을 예선 WorldState/임무/경로 엔진에 연결하는 폐루프
5) 명령/텔레메트리 계약, ESP32 펌웨어, 엔코더 PID와 실제 모터 출력
6) 렌즈 왜곡 및 태그 높이 보정과 9지점 x 4방향 실물 정확도 시험

중요한 안전 경계:

- config/robot_tags.json의 hardware_verified는 false다.
- tag_size_mm은 실물 태그를 정하기 전까지 null이다.
- observation_complete는 한 프레임에서 태그 4개가 유효했다는 뜻일 뿐,
  모터 출력 허가가 아니다.
- 현재 vision CLI는 실행당 카메라 한 대만 처리한다. 시뮬레이터의 고정
  카메라 2대 가정과 실제 두 영상 융합을 혼동하지 않는다.
- 팀원은 robo_control/vision과 robo_control/adapters.CameraFrame을 새로
  만들지 말고 현재 계약 위에 추적/융합/물체 검출을 추가한다. 좌표계나 JSON
  스키마를 바꿀 때는 먼저 팀과 합의한다.


0. 이 문서의 목적과 읽는 방법
---------------------------------------------------------------------

이 문서는 대회 참가자가 AI 조력자와 나눈 지금까지의 대화를 바탕으로,
질문과 답변에서 나온 모든 핵심 정보, 판단 변화, 구현 아이디어, 부품,
규정 해석, 불확실한 부분, 향후 할 일을 하나의 기술 기록으로 통합한 것이다.

단순한 대화 원문 복사가 아니라, 실제 제작자가 이어서 설계하고 시험할 수
있도록 내용을 주제별·시간순으로 재구성했다. 대화 도중 잘못 단정했다가
수정한 내용도 최종 결론만 남기지 않고 수정 이유와 함께 기록했다.

주의 사항:

1) 아직 실제 드론 통신, 조종기 회로, 로봇 주행, 경기 물체 포획을 실물로
   검증하지 않았다. 아래의 일부 수치는 설계 목표 또는 제공된 모델 파일의
   매개변수다.
2) 운영진이 드론, 외부 서버, 무선통신을 명시적으로 허용했다고 확정된
   상태가 아니다. 관련 질문은 이 문서에 별도로 정리했다.
3) 경기 요소의 최종 부속 도면과 실물 치수가 공개되거나 키트가 도착하면
   포획 장치 치수를 다시 확정해야 한다.
4) 이 문서는 공개 저장소에 배포되므로 개인 PC의 절대 경로, 비밀번호,
   로그인 토큰 등의 비공개 정보는 포함하지 않았다.
5) 생성형 AI가 실시간으로 로봇을 조종하는 구조가 아니다. 실제 제어에는
   컴퓨터 비전, 상태기계, 경로계획, 피드백 제어를 사용한다.


1. 프로젝트 한 줄 요약
---------------------------------------------------------------------

출발구역에서 자동으로 시작하는 지상 로봇 4대(H1, H2, B1, B2)와 고정
카메라 2대를 기본으로 사용하고, 로컬 서버가 실시간 영상으로 로봇과 경기 물체를 추적한
뒤 임무와 충돌 없는 경로를 계산하여 각 ESP32 로봇에 명령을 전달한다.
드론 1대는 운영진 허용과 독립 안전시험을 통과했을 때만 쓰는 선택 비교안이다.

두 가지 운용안을 모두 준비한다.

A안 - 드론 사용:
  드론이 출발구역에서 자동 이륙한 뒤 경기장 중앙 상공에서 체공한다.
  서버는 드론 영상을 분석한다. 순정 드론 조종기는 별도 ESP32로 자동화해
  사람이 스틱을 조작하지 않아도 드론이 움직이도록 한다.

B안 - 드론 미사용:
  규정상 필요한 고정 상부 카메라의 영상을 심사용으로 원본 녹화하면서,
  같은 프레임을 서버의 위치 추적에도 사용한다. 고정 카메라 방식은 영상이
  안정적이고 구현 난도가 낮아 기본안과 비상 대체안으로 적합하다.

최종 권고는 A안과 B안을 서로 다른 프로그램으로 만들지 않는 것이다.
카메라 입력 모듈만 교체할 수 있도록 만들고, 그 아래의 좌표 보정, 인식,
임무 배정, 경로계획, 통신, 로봇 펌웨어는 동일하게 공유한다.


2. 대화의 시간순 진행과 의사결정 변화
---------------------------------------------------------------------

2.1 최초 구상

최초 구상은 여러 개의 소형 로봇을 움직이고, 드론 한 대에서 촬영한 영상을
실시간 분석해 각 로봇의 경로를 최적화하는 것이었다. 처음에는 약 12대의
로봇을 생각했으며, 중앙 인공지능이 전체 로봇을 제어할 수 있는지 질문했다.

결론은 기술적으로 가능하지만, 1m급 경기장과 2분 경기에서는 로봇 수가
많을수록 점수가 늘어난다고 볼 수 없다는 것이었다. 로봇 수가 증가하면
다음 문제가 급격히 늘어난다.

- 출발구역 포장 문제
- 로봇끼리의 충돌과 교착상태
- Wi-Fi 또는 무선 패킷 충돌
- 배터리와 기계 고장의 수 증가
- 포획 장치와 로봇별 상태 추적의 복잡도 증가
- 검사, 장식, 비상정지 장치의 수 증가

2.2 중앙 컴퓨터와 서버

노트북 정도의 중앙 컴퓨터로 가능한지 질문했다. 한 대의 720p 또는 1080p
영상을 OpenCV로 분석하고 로봇 2~6대의 경로를 계산하는 일은 현대적인
노트북 CPU와 16GB 정도의 메모리로 충분하다. 대규모 딥러닝을 사용하지
않으면 고성능 GPU는 필수가 아니다.

중요한 사양은 단순 연산 성능보다 다음과 같다.

- 카메라 영상을 안정적으로 받을 수 있는 USB 또는 네트워크 인터페이스
- 드론망과 로봇망을 동시에 연결할 수 있는 네트워크 인터페이스 2개
- 영상과 명령·응답 로그를 저장할 충분한 SSD 공간
- 2분 경기 중 전원관리나 절전 기능이 개입하지 않도록 하는 설정
- 유선 LAN 또는 별도 USB Wi-Fi 어댑터

사용자가 별도 서버를 확보했다고 하여, 이후 설계에서는 서버 성능 문제가
해결된 것으로 보았다.

2.3 로봇 수를 6대로 축소

사용자는 12대 대신 6대를 고려했다. 6대로 줄이면 충돌쌍과 통신량은 크게
감소하지만, 실제 대회 출발구역은 480 x 280mm이므로 여전히 복잡하다.
국제 규정에는 로봇 수의 명시적 상한이 없으나 모든 로봇이 출발구역 안에
완전히 들어가야 한다.

대회와 제공된 기구 모델을 분석한 뒤 최종 권고 수량은 지상 로봇 2~3대로
줄어들었다. 특히 제공된 SCAD 로봇은 본체가 100 x 100mm이지만 바퀴를
포함한 실제 폭이 약 126mm이므로, 단순히 100mm 정사각형으로 계산하면
안 된다. 여기에 드론까지 출발구역에 들어가야 한다.

2.4 녹화가 아닌 실시간 추적

사용자는 녹화 영상이 아니라 실시간 추적이 가능한지 질문했다. 가능하며,
권장 구조는 다음과 같이 정리되었다.

  카메라 -> 실시간 좌표 보정 -> AprilTag 로봇 추적
          -> 물체·색상 검출 -> 세계 상태 갱신
          -> 임무 배정 -> 경로 생성 -> 로봇 명령

단, 카메라로 모든 모터 PWM을 직접 조종하지 않는다. 서버는 목표좌표와
고수준 동작을 보내고, 각 로봇의 ESP32가 엔코더 기반 PID로 실제 모터를
제어하는 분산 구조를 사용한다.

2.5 사용할 드론 지정

사용자는 롯데마트 제타 상품 페이지의 SY15 스카이 랩터 계열 소형 드론을
사용할 예정이라고 밝혔다.

대화 중 확인·언급한 상품 정보는 다음과 같다.

- 약 110g급 소형 완구 드론
- 30만 화소로 표시된 카메라
- 듀얼 카메라 표기
- 스마트폰 Wi-Fi 영상/앱 연동
- 2.4GHz 조종 계통
- 자동고도유지 기능
- 배터리 1개당 약 7~8분 비행 표기

30만 화소 영상은 심사용 720p 조건에는 부족하고, 드론은 고정 카메라도
아니다. 따라서 드론 카메라는 심사용 영상이 아니라 제어용 제3 센서로만
사용하는 방향이 되었다.

2.6 경기 조건 추가

사용자는 경기 시간이 2분이고 경기장 크기가 약 1m이며, 로컬 서버를
확보했다고 설명했다. 이에 따라 클라우드 없이 로컬에서 모든 계산을 하고,
네트워크 지연과 인터넷 단절에 영향을 받지 않는 구조를 선택했다.

2.7 라즈베리파이가 필요한지

결론은 각 지상 로봇에 라즈베리파이가 필요하지 않다는 것이다.

- 영상처리와 경로계획은 확보한 중앙 서버가 담당한다.
- 각 지상 로봇은 ESP32-S3가 모터, 엔코더, 게이트, 안전정지를 담당한다.
- 드론에 라즈베리파이를 올리는 것도 권하지 않는다. 110g급 기체에 추가
  중량을 올리면 비행시간, 체공 안정성, 안전성이 나빠진다.
- 외부 서버 사용이 금지되거나 온보드 영상 처리가 반드시 필요한 상황에만
  SBC를 다시 검토한다.

2.8 공식 대회 사이트 조사

사용자가 https://robotics-2026.web.app/ 사이트를 알려주어 공식 홈페이지,
예선 안내, 본선 안내, FAQ, 자료실, 한국어 예선 규정 초안, 국제 영문 규정,
프로그램 개요를 조사했다.

이 과정에서 출발구역, 경기시간, 영상 제출 조건, 로봇 자율성, 로봇 수,
배점과 일정이 구체화되었다. 자세한 내용은 3장에 정리한다.

2.9 고정 카메라 2대와 드론의 관계에 대한 판단 수정

처음에는 심사용 상부 카메라가 고정이어야 하고 드론 카메라 해상도가 낮다는
이유로 드론 사용 자체가 위험하다고 강하게 표현했다. 사용자는 심사용 고정
카메라 2대를 별도로 설치하면 드론 사용은 상관없지 않느냐고 지적했다.

이 지적이 타당하여 판단을 다음과 같이 수정했다.

- 고정 상부·정면 카메라 2대 조건만으로 제3의 드론 센서를 금지한다고
  해석할 수는 없다.
- 드론은 심사용 카메라가 아니라 제어용 보조 센서로 사용할 수 있다.
- 남는 쟁점은 촬영 규정이 아니라 드론의 로봇 분류, 출발 방식, 외부 서버,
  무선통신, 자율성, 안전, 프로펠러 바람이다.
- 규정에 명시적으로 금지된 것은 아니지만 명시적으로 허용된 것도 아니므로
  운영진의 서면 확인이 필요하다.

2.10 예선만 고려하도록 범위 확정

사용자는 드론을 출발구역에 두었다가 시작 후 자율 이동시키며, 본선은
신경 쓰지 말라고 명시했다. 이후의 모든 최종 설계와 이 문서의 적용 범위는
예선만으로 제한했다. 본선 동시 경기, 본선 행사장 설치, 상대 팀 간섭 등의
조건은 최종 설계 판단에서 제외했다.

2.11 운영진 문의문 작성

드론과 외부 서버 사용에서 애매한 항목을 모아 이메일 초안을 작성했고,
사용자가 너무 길다고 하여 핵심 질문 5개로 줄였다. 최종 핵심 질문은
12장에 다시 기록한다.

2.12 로봇 기구 설계 검토

사용자는 hamster_print_ready_v0.7.scad 파일을 제공했고, 이 모델로 구현할
가능성이 높다고 설명했다. 파일의 약 95KB 분량 OpenSCAD 코드를 읽어
본체 외형, 모터·바퀴·배터리 공간, 포획 구조, 게이트 이동량, 기계 검증용
assert, 출력 부품 선택자를 조사했다.

결론은 검체용 로봇 베이스로는 상당히 구체적인 제조 설계지만, 모든 경기
물체에 그대로 사용할 범용 포획기는 아니라는 것이다. 자세한 분석은 7장에
정리한다.

2.13 색상 인식과 AI의 역할

사용자는 색 구분과 AI가 필요한지 물었다. 환자 요소가 빨강·노랑·초록이고
색에 따라 목적지가 다르므로 색 구분은 필요하다. 하지만 생성형 AI 또는
대형 딥러닝 모델은 필요하지 않다.

- 원거리: 서버가 영상에서 HSV 색상 분할로 위치와 색을 판정한다.
- 근거리: 필요하면 로봇 내부 TCS34725 센서가 포획한 물체의 색을 재확인한다.
- 로봇 식별: AprilTag를 사용한다.
- 계획: 상태기계, 비용 기반 임무배정, A*, 우선순위 예약을 사용한다.

2.14 드론 조종 방식에 대한 추가 수정

사용자가 드론은 전용 컨트롤러로 움직인다고 지적했다. 이에 따라 서버가
드론에 Wi-Fi 명령을 직접 보낸다는 단일 가정을 버리고, 순정 조종기 자체를
자동화하는 방식을 기본 설계에 추가했다.

  드론 영상 -> 서버 -> 조종기 자동화 ESP32
                         -> 조이스틱/버튼 신호 모사
                         -> 순정 조종기 RF -> 드론

사람이 조종기를 잡고 스틱을 움직이면 완전자율로 인정받기 어렵다. 따라서
조종기의 네 축과 이륙·착륙 버튼을 전기적으로 자동화하거나, 초기 시험에만
서보가 실제 스틱을 움직이게 하는 방법을 사용한다.

2.15 두 안을 비교한 PDF 제작

사용자의 요청에 따라 드론 사용안과 비사용안을 비교하는 11페이지 PDF
"robotics_qualifier_drone_vs_fixed_camera_plan.pdf"를 제작했다. PDF에는
준비물, 시스템 구조, 기구 변경점, 조종기 자동화, 상태기계, 경로계획,
개발 순서, 합격 기준, 촬영 전 체크리스트를 포함했다.


3. 공식 대회 조사 결과 - 예선 중심
---------------------------------------------------------------------

3.1 대회 개요

- 대회명: 2026 로보틱스 챌린지
- 대상 트랙: 로보틱스 챌린지 문제해결
  (Robotics for Good Youth Challenge 한국대회)
- 국제 연계: ITU AI for Good Youth Challenge
- Junior: 2013~2017년생
- Senior: 2009~2012년생
- 팀 구성: 참가자 1~8명 + 성인 지도자
- 단일 기관 소속 팀을 기준으로 안내됨
- 부문별 예선 100팀 규모 안내

이 프로젝트의 최종 범위는 예선뿐이다. 국제 결선 및 한국 본선 정보는
대화 초기에 조사했으나, 사용자의 명시적 지시에 따라 구현 기준에서는
제외한다.

3.2 예선 경기장과 출발구역

- 예선 경기장: 1,143 x 1,181mm
- 로봇 출발구역: 480 x 280mm
- 경기시간: 최대 120초
- 모든 로봇은 출발구역 안에 완전히 들어가야 한다.
- 사전 적재가 허용되는 요소가 있다면 해당 요소까지 포함해 출발 상태를
  카메라에서 판독할 수 있도록 배치해야 한다.
- 로봇 수의 명시적인 최대 제한은 국제 규정에서 확인되지 않았다.
- 여러 로봇은 경기 시작 때 동시에 활성화되어야 한다.
- 로봇은 시작 후 완전자율로 동작해야 한다.
- 각 로봇에는 식별 가능한 비상정지 수단이 필요하다.
- 로봇별 안전·무결성 검사를 전제로 한다.

3.3 공식 경기 요소의 크기와 재질

공식 예선 페이지를 조사하면서 확인한 경기 요소의 기본 표기는 다음과 같다.

- 의료 키트 큐브: 약 25 x 25 x 20mm
- 환자 원통: 약 지름 20mm x 높이 20mm
- Senior 검체 디스크: 지름 약 56mm
- 환자 원통 색상: 빨강, 노랑, 초록
- 경기 요소는 원목 재질로 안내됨

검체 디스크 두께와 제조 허용오차는 최종 부속 도면 또는 실제 키트로 다시
확인해야 한다. 제공된 SCAD가 가정하는 검체 두께는 5mm다. 높이 20mm인
의료 키트와 환자 원통은 현재 SCAD 게이트의 12mm 개방부를 통과하지 못할
가능성이 매우 높으므로 높은 물체용 게이트가 필요하다.

3.4 Junior 예선 미션

총점 80점으로 안내되었다.

- 의료 키트 2개를 병원 H에 배치: 각 10점, 총 20점
- 빨간 환자 원통 2개를 병원 H에 배치: 총 20점
- 노란 환자 원통 2개를 같은 1차 진료소 PCC에 배치: 총 20점
- 초록 환자 원통 2개를 회복구역 RZ에 배치: 총 20점

3.5 Senior 예선 미션

총점 160점으로 안내되었다.

- 검체 3개를 실험실에 배치: 총 30점
- 의료 키트 4개 배치: 병원 2개, 각 PCC에 1개씩, 총 40점
- 빨간 환자 원통 3개를 병원 H에 배치: 총 30점
- 노란 환자 원통 3개를 두 PCC에 분산 배치하되 각 PCC에 최소 1개:
  총 30점
- 초록 환자 원통 3개를 회복구역 RZ에 배치: 총 30점

미션 순서는 자유롭게 선택할 수 있다.

3.6 득점 판정에서 중요한 조건

- 물체가 목적지 경계 안에 완전히 들어가야 한다.
- 로봇이 물체를 놓아 접촉이 해제되어야 한다.
- 잘못된 색의 원통이 목적지에 있으면 관련 득점 판정이 무효가 될 수 있다.
- 노란 환자는 지정된 분산 또는 동일 PCC 조건을 정확히 만족해야 한다.
- 경로 확보를 위해 아직 사용하지 않는 원통을 이동시키는 것은 최종 조건을
  위반하지 않는 범위에서 가능하다고 안내되었다.
- 로봇이 출발구역으로 돌아올 필요는 없다.

따라서 서버는 단순히 물체 중심이 목적지에 들어갔는지만 보면 안 된다.
물체의 전체 외곽선이 목적지 다각형 안에 있고, 로봇 외형과 더 이상 겹치지
않는지를 확인해야 한다.

3.7 시간과 종료 방식

- 제한시간은 120초다.
- 예선 페이지에서는 준비 후 팀원의 손이 로봇에서 떨어질 때 시작하는
  방식으로 설명되어 있다.
- 조기 종료 시 카메라 앞에서 손을 들고 "종료"라고 말하는 절차가 안내된다.
- 종료 시점의 경기 상태로 점수를 판정한다.
- 종료 후 최소 5초 동안 경기장을 그대로 유지해야 한다.
- 시작 후 사람의 개입은 영상을 무효로 만들 수 있다.

3.8 영상 제출 조건

동일한 한 번의 경기 수행을 두 대의 고정 카메라로 동시에 촬영한다.

상부 카메라:
  경기장 전체가 보이는 수직 상부 시점. 움직이지 않는 고정 카메라.

정면 카메라:
  경기장 전체, 실제 타이머, 시작·종료 동작이 보이는 시점.

공통 조건:

- 각 영상 720p 이상
- 각 영상 초당 30프레임 이상
- 무편집 원테이크
- 최대 5분
- 두 카메라는 같은 경기 수행을 촬영
- 시작 부분에 검증 코드를 표시
- 종료 후 최종 상태 유지
- 컷 편집, 배속, 화면 전환, 중요 구간 가림 금지

제출 항목으로는 두 영상, 로봇 전체 사진 1장, 주요 메커니즘 사진 1장,
플랫폼·센서·주행전략·코드 등을 설명하는 기술 요약 문서가 안내되었다.
마감 전 재제출이 가능하고 마지막 제출본을 심사하는 방식으로 안내되었다.

4. 전체 시스템 공통 아키텍처
---------------------------------------------------------------------

4.1 역할 분리

카메라 또는 드론:
  경기장을 관찰해 원본 프레임을 공급한다. 스스로 최종 판단하지 않는다.

로컬 서버:
  카메라 보정, 로봇 추적, 물체 검출, 세계 상태 관리, 임무 배정, 경로계획,
  로봇·드론 명령, 로그를 담당한다.

지상 로봇:
  서버의 목표를 받아 엔코더 PID로 주행하고, 포획·배출 장치를 움직이며,
  통신이 끊기면 안전하게 정지한다.

드론 조종기 자동화 장치(A안):
  서버의 비행 보정 명령을 순정 조종기의 스틱·버튼과 같은 신호로 바꾼다.

4.2 카메라 입력 추상화

서버의 첫 모듈은 영상원과 관계없이 다음만 제공해야 한다.

- 최신 프레임
- 프레임 촬영 시각
- 해상도와 프레임률
- 영상 연결 상태
- 원본 저장 위치

A안에서는 드론 영상 입력기가 이 인터페이스를 구현하고, B안에서는 고정
상부 카메라 입력기가 같은 인터페이스를 구현한다. 그 다음 단계는 어떤
카메라에서 온 프레임인지 몰라도 동작해야 한다.

4.3 서버 내부 모듈

1) 영상 입력기
   카메라 연결, 시간표시, 프레임 드롭 검사, 원본 녹화를 담당한다.

2) 카메라 보정부
   렌즈 왜곡을 보정하고 경기장 네 모서리를 찾아 수직 시점으로 변환한다.
   픽셀 좌표를 실제 mm 좌표로 변환한다.

3) 로봇 추적기
   AprilTag ID, 중심, 방향, 신뢰도를 계산한다. 짧은 검출 누락은 칼만 필터
   또는 최근 속도 추정으로 보완한다.

4) 물체 인식기
   빨강·노랑·초록 HSV 마스크, 크기, 원형도, 초기 위치, 로봇과의 관계를
   이용해 경기 물체를 찾는다. 검체와 의료 키트는 색상 외에 형태와 예상
   위치를 함께 사용한다.

5) 세계 상태 관리자
   모든 로봇과 물체를 하나의 시간 일관된 2차원 지도에 저장한다.

6) 임무 관리자
   물체 하나를 한 로봇에 예약하고, 예상 소요시간과 성공확률을 비교해
   다음 임무를 선택한다.

7) 경로 관리자
   장애물 여유를 포함한 A* 경로를 만들고, 로봇별 통행 우선권과 대기점을
   관리한다.

8) 로봇 게이트웨이
   고수준 명령을 보내고 응답, 배터리, 엔코더, 포획 센서, 게이트 상태를
   수집한다.

9) 안전 관리자
   영상·통신 끊김, 로봇 경계 접근, 비정상 속도, 시간 초과를 감시한다.

10) 기록기
    원본 영상, 좌표, 검출 결과, 임무 선택, 명령, 응답, 오류를 동일한
    시간축으로 저장한다. 심사용 원본 영상에는 분석 표시를 합성하지 않는다.

4.4 권장 처리 주기

- 카메라 입력과 영상 처리: 초당 15~30회
- 세계 상태 갱신: 초당 10~20회
- 임무/경로 재평가: 초당 3~10회 또는 사건 발생 시
- 서버의 로봇 명령: 초당 10~20회
- ESP32 내부 모터 PID: 초당 50~100회

드론의 실제 영상 프레임이 낮다면 가짜로 처리 주기를 높이지 않는다.
오래된 프레임은 폐기하고 최신 프레임을 처리하는 것이 중요하다.


5. A안 - 드론을 사용하는 구현
---------------------------------------------------------------------

5.1 물리 구성

- SY15 소형 드론 1대
- 예비 드론 배터리
- 순정 조종기
- 조종기 자동화 전용 ESP32 1개
- 디지털 가변저항 또는 DAC 4축
- 버튼 자동입력용 옵토커플러/트랜지스터
- 수동/자동 전환 스위치
- 독립 비상착륙 또는 모터 정지 버튼
- 서버와 자동화 ESP32 사이 USB 또는 유선 연결
- 프로펠러 가드
- 드론 영상 수신용 노트북 Wi-Fi
- 지상 로봇망용 유선 LAN 또는 두 번째 USB Wi-Fi

5.2 드론과 영상의 역할

드론은 심사용 영상 카메라가 아니다. 심사용 상부·정면 고정 카메라 2대는
별도로 운영한다. 드론은 제어 서버에 위치 정보를 제공하는 제3 센서다.

드론은 출발구역에서 정지한 상태로 시작하고, 시작 신호 후 사람의 스틱
조작 없이 자동으로 이륙해 경기장 중앙 상공으로 이동한다. 이후에는 로봇을
쫓아다니기보다 중앙에서 고정된 관측 시점을 유지하는 편이 좋다.

5.3 왜 순정 조종기 자동화가 필요한가

처음에는 서버가 드론 Wi-Fi에 직접 명령을 보내는 방법을 생각했다. 하지만
사용자는 실제 드론이 전용 컨트롤러로 움직인다는 점을 강조했다.

순정 비행제어기를 교체하거나 드론에 SBC를 추가하면 무게와 안정성 문제가
커진다. 따라서 순정 조종기의 RF 링크는 유지하고, 조종기 입력만 자동으로
만드는 것이 현실적이다.

조종기 네 축:

- 스로틀: 상승·하강
- 요: 좌우 회전
- 피치: 전진·후진
- 롤: 좌우 이동

조종기 개조 절차:

1) 전원을 끈 상태에서 조종기 구조와 조이스틱 가변저항을 확인한다.
2) 멀티미터로 각 축의 중립·최소·최대 전압을 측정한다.
3) 조종기 로직 전압, 공통 접지 여부, 스틱 방향을 기록한다.
4) 한 축씩 디지털 가변저항 또는 DAC와 절연 회로를 연결한다.
5) 드론 프로펠러를 제거한 상태에서 입력 반응을 먼저 시험한다.
6) 이륙·착륙 버튼은 옵토커플러 또는 트랜지스터로 눌림을 모사한다.
7) 자동 회로를 즉시 분리하는 수동/자동 전환 스위치를 둔다.
8) 비상 버튼은 일반 서버 프로그램과 독립적으로 작동하게 한다.

조종기 전압을 모른 채 ESP32의 3.3V를 직접 연결해서는 안 된다. 조종기를
손상시키거나 예기치 않은 최대 입력이 들어갈 수 있다.

초기 시험용으로는 소형 서보 4개가 실제 스틱을 움직이는 기구를 만들 수
있다. 그러나 이 방식은 유격, 속도, 스틱 중립 오차가 크므로 최종 대회용
구성에는 전기적 입력 모사를 권장한다.

5.4 드론 영상 수신 검증

이 프로젝트의 첫 번째 기술적 중단 기준은 드론 영상 직접 수신이다.

확인해야 할 사항:

- 드론 Wi-Fi에 노트북이 직접 연결되는가.
- 공식 앱 없이 원본 영상 스트림 주소 또는 패킷을 받을 수 있는가.
- 영상 코덱과 프레임률은 무엇인가.
- 앱과 드론 사이 로컬 UDP/TCP 패킷을 Wireshark로 확인할 수 있는가.
- 영상 지연이 200ms 안팎으로 유지되는가.
- 2분 이상 프레임 드롭 없이 받을 수 있는가.

공식 앱 화면을 화면 캡처하여 다시 분석하는 방식은 지연과 불안정성이 커서
최종안으로 권장하지 않는다. 직접 스트림을 받을 수 없다면 A안을 중단하고
B안으로 전환해야 한다.

5.5 자동 이륙 및 관측 위치 확보

예상 시간 순서:

- 0~1초: 전체 시스템 시작, 지상 로봇은 활성화 후 대기
- 1~3초: 드론 자동 이륙 및 수직 상승
- 3~5초: 경기장 전체가 보이는 위치로 미세 이동
- 안정 확인 후: 지상 로봇 임무 시작
- 경기 종료: 최종 상태 확인이 끝날 때까지 체공 후 안전 착륙

미리 정한 시간만큼 전진하는 개방루프 방식은 배터리, 바닥 무늬, 초기 자세에
따라 위치가 달라져 위험하다. 서버는 화면에서 경기장 중심과 크기를 검출해
다음과 같이 폐루프로 보정해야 한다.

- 경기장 중심이 화면 왼쪽이면 왼쪽으로 아주 조금 이동
- 오른쪽이면 오른쪽 이동
- 화면 위쪽이면 전진, 아래쪽이면 후진
- 경기장이 화면에 너무 크게 보이면 상승
- 너무 작게 보이면 하강
- 경기장 선이 회전되어 보이면 요 방향 보정

중앙에 들어온 뒤에는 작은 흔들림마다 명령하지 않는다. 허용범위와
히스테리시스를 두어 일정 범위를 벗어날 때만 낮은 속도로 보정한다.

5.6 움직이는 카메라의 좌표 보정

드론은 자동 체공 중에도 위치와 각도가 계속 변한다. 따라서 첫 프레임에서
한 번만 만든 픽셀-mm 변환을 계속 사용하면 안 된다.

매 프레임 또는 충분히 자주 다음을 수행한다.

1) 경기장 외곽선 또는 변하지 않는 검은 선 교차점 검출
2) 네 모서리의 순서 확정
3) 수직 시점으로 원근변환
4) 실제 경기장 1,143 x 1,181mm 좌표로 변환
5) 이전 변환과 큰 차이가 나면 프레임을 일시적으로 사용하지 않음

로봇 상단 AprilTag는 바닥보다 약 100mm 높으므로, 바닥 평면 변환을 태그에
그대로 적용하면 특히 가장자리에서 수 cm 오차가 날 수 있다. 카메라 자세와
알려진 태그 높이로 바퀴 중심의 바닥 좌표를 다시 투영하거나, 위치별 실험
보정표를 만들어야 한다.

5.7 드론안 네트워크

- 노트북 내장 Wi-Fi: 드론 AP와 영상 연결
- 노트북 유선 LAN 또는 USB Wi-Fi: 지상 로봇 전용 AP 연결
- USB/시리얼: 서버와 조종기 자동화 ESP32 연결
- 지상 로봇: 로봇 전용 AP에 고정 ID 또는 고정 IP로 연결

드론과 로봇이 모두 2.4GHz를 쓰면 간섭이 발생할 수 있다. 가능한 경우
채널 1과 11처럼 멀리 떨어진 채널을 사용한다. 운영체제가 드론 AP를 기본
네트워크 경로로 선택하더라도 로봇 명령이 잘못된 인터페이스로 나가지 않게
주소와 인터페이스를 고정한다.

5.8 A안의 주요 실패 요인과 대응

조종기 신호 미확인:
  네 축을 한꺼번에 개조하지 않고 한 축씩 실측·시험한다.

영상 직접 수신 불가:
  초기 단계에서 A안을 중단하고 B안을 사용한다.

낮은 해상도와 압축:
  6~8cm 무광 AprilTag, 균일한 조명, 무채색 로봇, 낮은 접근 속도를 쓴다.

체공 드리프트:
  경기장 중심 기반 보정, 히스테리시스, 속도 제한을 둔다.

프로펠러 바람:
  실제 키트와 원통으로 이동량을 시험한다. 지상 로봇은 이륙 중 대기하고
  드론은 최대한 빠르게 안전한 관측 고도를 확보한다.

배터리 부족:
  경기 직전에 완충 배터리로 교체하고, 반복시험용 예비 배터리를 둔다.

영상 또는 네트워크 손실:
  지상 로봇을 정지시키고, 드론은 안정적인 체공 또는 자동착륙 상태로 간다.


6. B안 - 드론 없이 구현
---------------------------------------------------------------------

6.1 권장 비드론 방식

심사용으로 반드시 설치해야 하는 고정 상부 카메라의 영상을 원본으로
저장하면서, 같은 프레임의 복사본을 서버 분석에 사용한다.

  고정 상부 카메라 -> 원본 무편집 녹화
                   -> 실시간 프레임 복사 -> 서버 인식·경로계획

정면 카메라는 심사용으로 별도 녹화한다. 원본 상부 영상에는 검출 사각형,
좌표, 글자 등을 합성하지 않는다. 분석 화면은 별도 창이나 별도 로그로
관리한다.

운영진이 심사용 상부 카메라 영상의 제어 겸용을 허용하지 않거나, 해당
촬영 장비가 실시간 출력을 제공하지 않는다면 제어용 고정 상부 카메라를
한 대 더 둔다. 이때 카메라 구성은 심사용 상부 1대, 심사용 정면 1대,
제어 전용 상부 1대로 총 3대가 된다.

고정 카메라의 장점:

- 드론 이륙을 기다리지 않고 시작 즉시 인식 가능
- 카메라 자세가 고정되어 좌표 변환이 안정적
- 보통 드론 카메라보다 높은 해상도와 낮은 지연
- 조종기 개조와 드론 비행제어 불필요
- 프로펠러 바람과 드론 배터리 문제 없음
- 출발구역에 지상 로봇을 배치할 공간 증가
- 실전 반복 성공률을 높이기 쉬움

6.2 카메라 설치

- 규정 최소치 720p/30fps를 충족한다.
- 인식 여유를 위해 1080p/30fps를 권장한다.
- 경기장 네 모서리가 모두 보이게 수직에 가깝게 설치한다.
- 흔들리지 않는 강성 거치대를 사용한다.
- 자동초점과 자동노출이 가능하면 고정한다.
- 좌우 또는 천장 확산 조명으로 강한 그림자를 줄인다.
- USB 연장 사용 시 프레임 드롭과 전압 저하를 확인한다.

6.3 시작 절차

- 시작 전: 카메라 보정과 모든 로봇의 초기 검출 확인
- 0초: 한 번의 시작 입력으로 120초 타이머와 로봇 상태기계 시작
- 0~1초: 최신 프레임으로 초기 위치와 물체 상태 확인
- 1초 이후: 각 로봇이 첫 임무 수행
- 105~110초 이후: 새 임무 제한, 현재 운반 중인 물체만 마무리

6.4 영상이 끊겼을 때

카메라가 끊겨도 로봇이 미리 받은 전체 경로를 끝까지 달리면 안 된다.
각 명령에 짧은 유효시간을 두고, 마지막 명령만 제한된 시간 동안 실행한 뒤
정지한다. 영상이 복구되면 현재 위치를 새로 확인하고 경로를 다시 만든다.

6.5 완전 비전 없는 최소 대체안

고정 상부 카메라 영상도 제어에 사용할 수 없다고 운영진이 답하면, 다음의
온보드 방식이 최후 대안이다.

- 바퀴 엔코더로 사전 측정 경로 실행
- 전방 ToF 센서로 벽과 로봇 근접 정지
- TCS34725로 가까운 물체 색상 확인
- 초기 배치가 고정된 Junior에서는 미리 측정한 경로 사용
- 위치 누적 오차가 커질 수 있으므로 속도와 임무 수를 낮춤

이 방식도 ESP32로 구현할 수 있으며 라즈베리파이가 반드시 필요한 것은
아니다. 다만 Senior처럼 배치 변화가 있거나 정밀한 충돌 회피가 필요하면
상부 비전 방식보다 성공률이 낮을 수 있다.


7. 제공된 OpenSCAD 로봇 분석
---------------------------------------------------------------------

파일명: hamster_print_ready_v0.7.scad

7.1 확인한 주요 매개변수

- 설계 본체 폭: 100mm
- 설계 본체 길이: 100mm
- 설계 본체 높이: 100mm
- 목표 검체 원판 지름: 56mm
- 목표 검체 두께: 5mm
- 포획 포켓 내부 반지름: 30mm
- 검체 방사 여유: 2mm
- 곡선 깔때기 전면 중심간 폭: 94mm
- 깔때기 출구 중심간 폭: 62mm
- 깔때기 길이: 32mm
- 깔때기 벽 높이: 9mm
- 전면 게이트 높이: 10mm
- 게이트 DOWN 바닥: 0.3mm
- 게이트 UP 바닥: 12mm
- 게이트 실제 수직 이동량: 11.7mm
- SG90급 서보 가정
- 모터 공간 가정: 30 x 15 x 20mm
- 모터 축 지름 가정: 3mm
- 바퀴 지름: 45mm
- 바퀴 폭: 10mm
- 배터리 공간 가정: 24 x 36 x 20mm
- 제어기 공간 가정: 45 x 35 x 8mm
- 캐스터 지름 가정: 12mm

바퀴 중심과 폭을 포함하면 전체 외형 폭은 약 126mm다. 코드 내부의
100mm 외형 검사는 주로 본체와 포획 구조를 대상으로 하며, 바깥으로 나온
바퀴까지 100mm 안에 들어가는 것은 아니다.

7.2 장점

- 56mm 납작한 원판을 바닥에서 포획하는 목적이 명확하다.
- 94mm 전면 깔때기가 물체 접근 오차를 줄인다.
- 곡선 장벽과 이동 게이트로 포획 후 이탈을 막는다.
- 게이트 슬라이더, 가이드 캡, 서보 클램프, 링크 등이 분리 가능하다.
- 모터 마운트, 배터리 마운트, 전자장치 데크, 뚜껑, 캐스터가 모듈화되어
  정비가 가능하다.
- M3 너트 포켓과 M2.5 파일럿 구멍 등 제조를 고려한 구조가 있다.
- 간섭과 여유를 검사하는 많은 assert가 포함되어 있다.
- fit_coupon과 guide_test_key 같은 시험 출력용 선택자가 있다.

7.3 그대로 사용하면 생길 수 있는 문제

첫째, 현재 구조는 사실상 56 x 5mm의 납작한 검체 원판 전용이다.
게이트를 올려도 바닥에서 12mm만 열리므로 12mm보다 높은 환자 원통이나
의료 키트는 입구를 통과하지 못할 수 있다.

둘째, 깔때기 벽 높이가 9mm여서 높은 원통의 하단만 잡는다. 원통이 기울거나
넘어질 경우 안정적으로 유지하지 못할 수 있다.

셋째, 바닥 여유 0.3mm는 FDM 출력의 첫층 번짐, 차체 기울기, 경기장 요철에
비해 너무 작을 수 있다. 시험 후 약 0.8mm 전후를 시작점으로 조절한다.

넷째, 일반적인 엔코더 포함 N20 모터는 코드가 가정한 30mm보다 길 수 있다.
모터 본체, 기어박스, 엔코더 보드, 커넥터까지 실측해야 한다.

다섯째, 일반 ESP32 개발보드는 길이가 45mm를 넘을 수 있다. 45 x 35mm
공간에 맞는 소형 ESP32-S3 보드를 선택하거나 전자장치 데크를 수정해야 한다.

여섯째, 24 x 36 x 20mm 배터리 공간에 실제 2셀 LiPo가 맞는지 확인해야
한다. 배터리 받침은 스트랩으로 길이를 조정할 수 있게 만드는 것이 좋다.

일곱째, SCAD 주석은 별도의 README를 언급하지만 제공된 폴더에는 SCAD
파일만 있었다. 출력 방향, 서포트, 볼트 수량, 조립 순서를 별도 문서로
정리해야 한다.

7.4 권장 수정

- 바닥 간격을 실물 시험으로 조정하고 교체 가능한 얇은 슬라이더를 사용
- 엔코더 포함 실제 모터 치수에 맞춰 마운트 길이 수정
- 배터리와 ESP32 보드의 실측 치수로 전자장치 데크 수정
- 뚜껑에 6~8cm AprilTag 평면과 물리 비상정지 버튼 공간 추가
- 전방 ToF 센서와 내부 물체 감지 센서 장착구 추가
- 높은 물체용 회전 게이트 또는 옆으로 열리는 게이트 모듈 추가
- 포획 폭을 나사 슬롯으로 조절 가능하게 설계
- 게이트 상·하한 확인용 리미트 또는 위치 확인 방법 추가

7.5 권장 출력 순서

1) fit_coupon
2) guide_test_key
3) gate_slider와 가이드 캡
4) 하부 차체 일부와 모터 마운트
5) 실제 모터·서보·배터리 끼움 시험
6) 지상 로봇 1대 전체
7) 한 물체 포획·배출 시험
8) 성공한 설계를 나머지 로봇으로 복제


8. 지상 로봇 권장 구성
---------------------------------------------------------------------

8.1 수량

대회와 출발구역만 보고 판단하면 지상 로봇 2~3대가 현실적이다.

- Junior: 2대로도 충분할 가능성이 높다.
- Senior: 3대의 역할 분담이 유리하다.
- 6대는 규정상 원칙적으로 가능할 수 있지만 출발구역, 충돌, 기구 수,
  네트워크, 디버깅 부담 때문에 권장하지 않는다.

8.2 공통 차체

- 차동구동 바퀴 2개 + 뒤쪽 볼 캐스터
- 엔코더 N20 모터 2개
- 45mm 고무바퀴
- ESP32-S3 소형 보드
- TB6612FNG 또는 DRV8833 모터 드라이버
- SG90 또는 금속기어 MG90S 서보
- 2셀 LiPo + 5/6V 전압조절기
- 전방 ToF 센서
- 내부 물체 감지 센서
- 선택적인 TCS34725 색 센서
- 물리 전원·비상정지 스위치
- 상단 무광 AprilTag

8.3 역할 예시

Senior 3대 기준:

1호 - 검체 로봇
  현재 SCAD의 56mm 원판 포획 구조를 우선 사용한다.

2호 - 의료 키트 로봇
  넓은 가이드와 회전 게이트 또는 낮은 밀판을 사용한다.

3호 - 환자 원통 로봇
  높은 측벽, 높은 물체가 통과하는 게이트, 내부 색 센서를 사용한다.

차체와 전자장치는 가능한 한 동일하게 만들고 전면 포획 모듈만 교체한다.
한 로봇이 고장 나면 다른 로봇이 일부 임무를 대신할 수 있도록 완전히
서로 다른 전용 차체는 피한다.


9. 색상 인식, 로봇 추적, 물체 추적
---------------------------------------------------------------------

9.1 로봇 식별

각 로봇 상단에 서로 다른 AprilTag ID를 붙인다.

- 최소 6cm, 가능하면 7~8cm
- 무광 출력
- 흰 여백 유지
- 로봇 상단과 평행하게 부착
- 로봇별 고유 ID 사용
- 태그를 가리는 케이블, 손잡이, 서보 링크 금지

드론 30만 화소 영상에서 경기장 폭이 약 640픽셀로 보인다고 가정하면
7cm 태그는 약 수십 픽셀 수준이다. 압축과 흔들림을 고려하면 작은 태그보다
큰 태그가 유리하다.

9.2 색상 인식

빨강·노랑·초록 환자는 HSV 색공간에서 분리한다. RGB는 밝기 변화에 민감해
직접 임계값을 쓰기 어렵다. 빨강은 색상환 양 끝에 걸쳐 있으므로 두 범위를
합쳐야 할 수 있다.

처리 순서:

1) 노출과 화이트밸런스가 안정된 프레임 확보
2) 수직 보정 영상으로 변환
3) 빨강·노랑·초록 마스크 생성
4) 작은 잡음 제거와 구멍 채우기
5) 예상 면적과 형태에 맞는 외곽선 선택
6) 중심, 외곽 다각형, 신뢰도 계산
7) 이전 프레임과 연결해 동일한 물체 ID 유지

오인식을 줄이기 위해 로봇 외장을 검정·흰색·회색 위주로 만든다. 로봇의
빨간 케이블이나 초록 장식이 외부에서 크게 보이면 물체로 오인될 수 있다.

9.3 근거리 색상 확인

드론이나 고정 카메라의 색 판정만으로도 가능하지만, 조명과 카메라 자동
보정 때문에 색이 흔들릴 수 있다. 선택적으로 TCS34725를 포획 포켓 내부에
장착해 물체가 들어온 뒤 색을 다시 확인한다.

서버 판정과 로봇 센서 판정이 다르면 즉시 잘못된 목적지로 이동하지 않고,
정지 후 서버가 여러 프레임을 다시 확인한다.

9.4 목적지 완료 판정

완료는 다음 조건을 모두 만족할 때만 기록한다.

- 물체 외곽선 전체가 목적지 경계 안에 있음
- 안전 여유를 포함해 경계에 걸리지 않음
- 로봇 외형과 물체가 겹치지 않음
- 물체가 연속된 여러 프레임 동안 정지 상태
- 색상과 목적지가 올바르게 대응


10. 임무 배정과 경로 최적화
---------------------------------------------------------------------

10.1 세계 상태

각 로봇에 저장할 정보:

- ID
- X, Y 위치(mm)
- 방향 각도
- 추정 속도
- 현재 임무
- 현재 상태
- 포획한 물체 ID
- 배터리
- 통신 마지막 시각
- 게이트 상태
- 고장 또는 대기 여부

각 물체에 저장할 정보:

- ID
- 종류와 색상
- X, Y 위치 및 외곽
- 목적지
- 미처리/예약/포획/운반/완료/분실 상태
- 담당 로봇
- 마지막 검출 시각

10.2 임무 선택

모든 물체가 같은 10점이라면 단순 최단거리보다 다음 값을 사용한다.

  기대 효율 = 점수 x 성공확률 / 예상 소요시간

예상 소요시간에는 다음을 포함한다.

- 물체까지 이동
- 최종 정렬
- 포획
- 목적지까지 운반
- 배출
- 충돌 대기시간

처음에는 역할을 고정하고 실패 또는 시간 초과 때만 재배정한다. 매 순간
모든 임무를 다시 바꾸면 로봇이 방향만 바꾸다가 시간을 잃을 수 있다.

10.3 경로 생성

경기장을 mm 단위 좌표계와 작은 격자로 표현한다. 다음을 장애물로 만든다.

- 경기장 물리 벽
- 다른 로봇의 현재 위치와 예정 경로
- 운반하지 않을 경기 물체
- 이미 득점한 물체와 보호구역
- 드론 착륙 예정 위치(A안에서 필요한 경우)

장애물은 실제 크기보다 로봇 반폭과 10~20mm 안전여유만큼 크게 만든다.
제공된 로봇은 바퀴 포함 폭 약 126mm이므로 100mm 본체 기준으로만 여유를
계산하면 충돌할 수 있다.

A*로 격자 경로를 찾은 뒤 불필요한 굴곡을 줄여 몇 개의 웨이포인트로 만든다.

10.4 다중 로봇 충돌 방지

- 물체를 운반 중인 로봇 우선
- 목적지에 가까운 로봇 우선
- 빈 로봇 또는 먼 로봇은 대기점에서 정지
- 좁은 구역에는 한 번에 한 대만 진입
- 서로 마주 보는 경로를 만들지 않음
- 한 방향 통행 구간을 미리 지정
- 다른 로봇이 예정 구간에 들어오면 정지 후 재계산
- 위치 오차가 30mm 이상이면 해당 로봇 경로 재계산

3대 규모에서는 복잡한 완전 최적 MAPF보다 우선순위 예약과 대기점이 더
단순하고 안정적이다.

10.5 속도 정책

- 빈 공간 장거리 이동: 약 0.2~0.3m/s에서 실물 검증
- 물체 20cm 앞: 속도 감소
- 최종 포획 접근: 약 0.05~0.1m/s
- 목적지 배출: 더 낮은 속도
- 태그 검출 신뢰도가 낮아지면 감속 또는 정지

10.6 종료 전략

105~110초부터 새 임무를 시작하지 않도록 제한한다. 남은 시간에는 이미
포획한 물체만 목적지에 놓고, 득점한 물체를 건드리지 않는 곳으로 이동한다.
마지막 한 개를 무리하게 시도하다 기존 물체를 밀어 점수를 잃는 상황을
피해야 한다.


11. 로봇 상태기계와 통신
---------------------------------------------------------------------

11.1 물체 하나를 처리하는 상태기계

IDLE:
  임무를 기다린다.

RESERVED:
  특정 물체를 예약하고 서버에서 접근 경로를 받는다.

NAVIGATE:
  물체 20cm 전까지 일반 속도로 이동한다.

ALIGN:
  물체와 로봇 입구의 중심과 방향을 맞춘다.

OPEN_GATE:
  게이트가 실제로 열린 것을 확인한다.

CAPTURE:
  낮은 속도로 직진해 물체를 포획 포켓에 넣는다.

VERIFY_CAPTURE:
  내부 센서와 영상으로 포획 여부를 확인한다.

CLOSE_GATE:
  게이트를 닫고 위치를 확인한다.

TRANSPORT:
  통행 우선권을 가지고 목적지까지 이동한다.

RELEASE:
  목적지 안에서 게이트를 열고 천천히 후진한다.

VERIFY_RELEASE:
  물체가 로봇에서 분리되고 전체가 목적지 안인지 확인한다.

RETRY:
  실패 시 한 번 정도 위치를 보정해 재시도한다.

ABANDON:
  반복 실패나 시간 부족 시 해당 물체를 포기한다.

SAFE_STOP:
  통신, 센서, 시간, 경계 이상 시 모터를 정지한다.

11.2 서버 명령

서버가 보내는 명령에는 최소한 다음 개념이 필요하다.

- 로봇 ID
- 순서가 증가하는 명령 번호
- 서버 생성 시각
- 명령 유효시간
- 동작 종류
- 목표 X, Y
- 목표 방향
- 최대 선속도와 회전속도
- 게이트 열기/닫기/유지
- 즉시 정지

서버는 모터 PWM을 원격으로 직접 보내지 않는다. 로봇은 목표와 제한을 받아
자체 엔코더 PID로 주행한다.

11.3 로봇 응답

- 마지막으로 처리한 명령 번호
- 현재 모터 상태
- 좌우 엔코더 증가량
- 배터리 전압
- 포획 센서
- 색 센서 결과
- 게이트 위치
- 오류코드
- 마지막 서버 패킷 이후 시간

11.4 안전 타임아웃

300~500ms 동안 유효한 새 명령이 없으면 로봇을 정지한다. 서버가 다시
연결되더라도 자동으로 이전 동작을 재개하지 않고, 새로운 명시적 명령을
받은 뒤 움직인다.


12. 운영진에게 확인할 애매한 사항
---------------------------------------------------------------------

최종적으로 예선에 대해서만 다음을 문의하기로 했다.

1) 드론과 지상 로봇이 출발구역 안에 있다가 시작 후 드론이 자동 이륙하는
   방식을 예선에서 허용하는가.

2) 고정 상부·정면 카메라 2대는 심사용으로 별도 촬영하면서, 드론을 제어용
   제3 카메라로 사용해도 되는가.

3) 경기장 밖 로컬 서버가 영상을 분석하고 Wi-Fi로 지상 로봇에 명령을
   보내는 방식도, 경기 중 사람이 개입하지 않으면 완전자율로 인정되는가.

4) 서버와 무선망은 경기 전에 준비하고, 시작 입력 한 번으로 드론과 여러
   지상 로봇을 활성화해도 되는가.

5) 자체 공유기, Wi-Fi, ESP-NOW 사용에 주파수 또는 방식 제한이 있는가.

6) 드론의 비행 고도와 평면상 비행 범위에 제한이 있는가.

7) 드론 프로펠러 바람이 경기 물체를 우연히 움직이면 어떻게 판정하는가.

8) 순정 조종기를 ESP32가 전기적으로 자동 조작하는 것을 사람의 개입 없는
   완전자율 비행으로 인정하는가.

9) 드론의 원격 비상착륙 또는 모터 정지 버튼이 비상정지 장치로 인정되는가.

10) 로봇 상단 AprilTag와 필요시 경기장 바깥의 보정용 마커를 사용할 수
    있는가.

11) 심사용 고정 상부 카메라 영상을 원본 녹화하면서 실시간 제어에도 함께
    사용할 수 있는가.

12) 홈페이지와 한국어 초안이 다른 경우 최신 홈페이지 기준을 우선하면
    되는가.

최종적으로 사용자에게 전달한 짧은 문의문:

제목: 예선 드론 및 로컬 서버 사용 문의

안녕하세요. 2026 로보틱스 챌린지 예선 참가를 준비 중인 [팀명]입니다.

심사용 고정 카메라 2대는 별도로 설치하고, 다음과 같은 자율 시스템을
사용하려고 합니다.

- 드론과 지상 로봇은 모두 출발구역 안에서 시작
- 시작 후 드론이 자동 이륙하여 경기장 상공에서 체공
- 외부 로컬 서버가 드론 영상을 분석해 지상 로봇에 무선 명령 전송
- 경기 중 사람의 조종이나 프로그램 수정 없음

다음 사항을 문의드립니다.

1. 이러한 드론 사용이 예선에서 허용되나요?
2. 외부 로컬 서버를 이용한 제어도 완전자율로 인정되나요?
3. Wi-Fi 등 무선통신을 사용해도 되나요?
4. 드론의 비행 고도와 범위에 제한이 있나요?
5. 프로펠러 바람으로 경기 물체가 움직이면 어떻게 판정되나요?

가능하면 서면 답변 부탁드립니다. 감사합니다.

15. 권장 정량 합격 기준
---------------------------------------------------------------------

경기장 보정:
  100개 프레임 중 99개 이상 성공하고 모서리 순서 오류가 없어야 한다.

로봇 위치:
  바닥 기준 위치 오차 15mm 이하, 방향 오차 5도 이하를 목표로 한다.

물체 색상:
  각 색상 최소 50회 시험에서 95% 이상 정확히 구분한다.

영상-명령 종단 지연:
  프레임 촬영부터 로봇 명령 반영까지 200ms 이하를 목표로 한다.

주행:
  1m 이동 후 오차 30mm 이하. 정지 명령 뒤 과도한 미끄러짐이 없어야 한다.

포획·배출:
  같은 조건 10회 중 9회 이상 성공해야 한다.

통신 안전:
  유효한 명령이 끊긴 뒤 500ms 이내에 정지해야 한다.

전체 경기:
  120초 시험 10회 중 8회 이상 목표점수를 달성하고 기존 득점 요소를
  훼손하지 않아야 한다.

드론 A안:
  2분 동안 경기장 네 모서리를 유지하고, 영상 끊김과 조종기 중립 이탈이
  없어야 한다.

17. 최종 권고안
---------------------------------------------------------------------

1) 예선만을 목표로 한다.

2) 지상 로봇은 6대보다 2~3대를 사용한다.

3) 모든 지상 로봇에 라즈베리파이를 넣지 않는다. 중앙 서버 + ESP32 구조를
   사용한다.

4) 제공된 SCAD는 검체 로봇의 시작점으로 활용하되, 의료 키트와 높은 원통은
   별도 포획 모듈을 만든다.

5) 색상은 생성형 AI가 아니라 HSV 영상처리로 분류하고, 필요하면 TCS34725로
   근거리 재확인한다.

6) B안 고정 상부 카메라 시스템을 먼저 완성한다. 이것이 드론 실패 시에도
   점수를 낼 수 있는 기본 시스템이다.

7) A안 드론은 동일 서버의 교체 가능한 영상원으로 추가한다.

8) 드론은 순정 조종기 RF를 유지하고 조종기 입력을 ESP32가 자동화한다.
   사람이 경기 중 스틱을 보정하지 않는다.

9) 서버는 고수준 목표만 보내고, 각 ESP32가 엔코더 PID와 안전정지를
   담당한다.

10) 완전한 최적화보다 반복 성공률을 우선한다. 105~110초부터 새 임무를
    제한하고 획득한 점수를 보호한다.
