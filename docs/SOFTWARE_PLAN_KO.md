# Robo 소프트웨어 구현 계획

기준일: 2026-09-04  
대상: 한국 예선 120초 경기  
기본 전략: 고정 상부 카메라(B안) 우선, 드론(A안)은 후속 영상원

## 2026-09-05 구현 상태

- 동료가 추가한 `robo_control` 패키지와 시뮬레이터를 공통 저장소 기반으로 사용한다.
  아래 초기 설계의 `robo_server` 명칭 대신 현재 패키지명은 `robo_control`이다.

  수동 네 모서리 보정, 픽셀↔mm 변환, 보정 JSON, 독립 기준점 오차 검사,
  프레임 지연·순서·해상도 검사를 구현했다.
- 현재 M2+M3 전체 회귀시험은 vision 의존성 환경에서 Python 172개와 웹 26개를
  통과했다. 영상 파일 디코딩·보정·AprilTag 검출·로그 저장을 포함하며,
  실물 카메라 정확도는 아직 측정하지 않았다.
- M2 전체 통과 조건인 실물 100프레임 보정 확인, 렌즈 파라미터 보정·저장,
  실제 촬영부터 처리까지의 지연 측정은 남아 있다.
- M3 첫 단위인 AprilTag 로봇 ID·위치·방향 검출을 구현했다. 네 로봇의
  구성 가능한 ID, 장착 방향·회전중심 오프셋, 누락·중복·미등록·경기장 밖
  관측 차단, 실제 이미지·영상 CLI와 JSONL 로그를 포함한다.
- 다음 코딩 단위는 HSV 색상 물체 검출과 여러 프레임의 로봇 추적이다. 기존
  엔진에 관측을 연결하는 작업과 ESP32 주행 제어는 아직 구현하지 않았다.
- 설치와 실제 카메라 사용은 [카메라 보정 사용 설명](CAMERA_CALIBRATION_KO.md)을 따른다.

스키마를 변경할 팀원은 기존 시험과 두 사용 설명을 먼저 확인하고 합의한다.

## 1. 결과 목표

최종 소프트웨어는 고정 상부 카메라에서 경기장을 관찰하고, 물체와
로봇을 추적하며, 4대의 지상 로봇(`H1`, `H2`, `B1`, `B2`)이 충돌하지 않도록 임무와 경로를
계산하고, ESP32 로봇에 고수준 명령을 전송해야 한다.

첫 번째 수직 기능 조각(vertical slice)은 다음 한 사이클이다.

1. 시뮬레이터 또는 녹화 프레임을 받는다.
2. 로봇 한 대와 물체 한 개의 상태를 만든다.
3. 물체를 목적지에 배정하고 경로를 계산한다.
4. `NAVIGATE → CAPTURE → TRANSPORT → RELEASE` 상태를 수행한다.
5. 완료 판정과 모든 명령·상태 전환을 로그로 남긴다.

이 사이클이 자동 테스트에서 반복 가능해진 뒤 실제 카메라와 ESP32를
연결한다.

## 2. 범위와 비범위

초기 필수 범위:

- Python 중앙 서버
- 고정 카메라, 영상 파일, 시뮬레이터 입력
- 경기장 원근 보정과 mm 좌표계
- AprilTag 로봇 식별
- HSV 기반 빨강·노랑·초록 검출
- 세계 상태, 임무 상태기계, A* 경로계획
- UDP 기반 서버·로봇 통신
- ESP32 엔코더 PID와 500ms 안전 타임아웃
- 실행 로그와 오프라인 재생
- 1대에서 시작해 2대, 최종 4대로 확장하는 충돌 회피

초기 비범위:

- 생성형 AI 또는 대형 딥러닝 모델
- 클라우드 서버 의존성
- 처음부터 완전 최적 다중 에이전트 경로계획
- 실제 프로토콜을 모르는 상태에서의 드론 제어
- GUI 중심의 운영 프로그램

## 3. 시스템 경계

```text
FrameSource
  ├─ SyntheticSource
  ├─ VideoFileSource
  ├─ FixedCameraSource
  └─ DroneSource (후속)
          │
          ▼
Calibration → Perception → Tracking → WorldState
                                          │
                                          ▼
                                  MissionManager
                                          │
                                          ▼
                              Planner + TrafficManager
                                          │
                                          ▼
RobotGateway ← telemetry ─────────── command
    ├─ SimulatedRobotGateway
    └─ UdpRobotGateway → ESP32 firmware
```

안전 관리자는 영상 입력, 세계 상태, 명령 송신, 텔레메트리를 모두 감시하고
이상이 있으면 새 임무 발급을 중지하고 `SAFE_STOP`을 전송한다.

## 4. 핵심 계약

### 좌표와 시간

- 경기장 원점, X/Y 방향, 회전각 부호를 설정 문서에 고정한다.
- 서버 내부 길이 단위는 mm, 각도 단위는 rad, 시간은 단조 시계 기반 초다.
- 영상 프레임에는 캡처 시각과 처리 시각을 별도로 기록한다.
- 오래된 프레임과 유효시간이 지난 명령은 폐기한다.

### 영상 입력

모든 영상원은 최신 프레임, 캡처 시각, 프레임 번호, 해상도, 연결 상태를
같은 형식으로 제공한다. 인식 모듈은 영상원이 드론인지 웹캠인지 알지 못한다.

### 로봇 명령

초기 전송 형식은 디버깅하기 쉬운 UDP JSON으로 한다. 모든 패킷에
`protocol_version`, `robot_id`, `sequence`, `command`, `ttl_ms`를 포함한다.
목표 이동 명령에는 X/Y/방향과 선속도·회전속도 제한을 포함한다.

ESP32는 패킷 수신 시각을 자체 단조 시계로 기록하고 500ms 동안 유효한
새 명령이 없으면 모터를 정지한다. 연결 복구만으로 이전 동작을 재개하지
않는다.

### 로그와 재생

- 심사용 원본 영상과 분석 오버레이를 분리한다.
- 프레임, 검출, 세계 상태, 임무, 경로, 명령, 응답, 오류를 한 실행 ID와
  같은 시간축으로 연결한다.
- 실패 실행을 실제 로봇 없이 재생할 수 있어야 한다.

## 5. 마일스톤과 통과 조건

### M0 — 기반 구조

산출물:

- Python 패키지, CLI, 설정 예시, 테스트, 정적 검사, CI
- ESP32 PlatformIO 구조
- 핵심 데이터 모델과 어댑터 인터페이스

통과 조건:

- Python 3.11/3.12에서 설치 및 테스트 성공
- `python -m robo_control` 실행 성공
- 하드웨어 값이 설정 파일 밖에 하드코딩되지 않음

### M1 — 결정론적 2D 시뮬레이터

산출물:

- 1,143 × 1,181mm 경기장
- 차동구동 로봇, 물체, 목적지, 충돌 모델
- 고정 seed와 시간 단계 실행
- 헤드리스 테스트와 선택적 OpenCV 표시

통과 조건:

- 같은 입력은 같은 최종 상태와 로그를 생성
- 로봇이 벽과 다른 로봇을 통과하지 않음
- 포획·운반·배출 이벤트를 재현 가능

### M2 — 카메라와 좌표 보정 (코드 부분 완료, 실물 검증 미완료)

산출물:

- 영상 파일·웹캠 입력기 — 구현 완료 (`ef5e020`)
- 네 모서리 원근변환과 픽셀-mm 변환 — 구현 완료 (`ef5e020`)
- 보정 JSON·독립 기준점 오차·프레임 지연 검사 — 구현 완료 (`ef5e020`)
- 렌즈 보정 파라미터와 태그 높이 보정 — 미구현

통과 조건:

- 100프레임 중 99프레임 이상 경기장 변환 성공
- 모서리 순서 반전 없음
- 오래된 프레임을 제어에 사용하지 않음

### M3 — 인식과 추적 (AprilTag 프레임 관측만 코드 완료)

산출물:

- AprilTag ID·중심·방향 검출 — H1/H2/B1/B2 구현 완료 (`ef5e020`)
- 실제 사진·영상 CLI, 인쇄 태그, 합성 투영·PNG·MJPG 회귀시험 — 구현 완료
- HSV 물체 색상·외곽 검출 — 미구현
- 짧은 가림·재획득·500ms 손실 정지를 처리하는 추적기 — 미구현
- 고정 카메라 2대 동기화·중복 관측 융합 — 미구현

통과 조건:

- 로봇 위치 오차 15mm, 방향 오차 5도 이내 목표
- 색별 50회 시험에서 95% 이상 정확도
- 검출되지 않은 대상을 임의 위치에 생성하지 않음

### M4 — 세계 상태와 오프라인 재생

산출물:

- 로봇·물체 수명주기와 신뢰도
- 미처리/예약/포획/운반/완료/분실 상태
- 녹화된 입력으로 전체 상태를 재생하는 도구

통과 조건:

- 같은 녹화와 설정으로 임무 결정이 재현됨
- 가려진 물체가 중복 ID로 즉시 생성되지 않음

### M5 — 단일 로봇 임무·경로·상태기계

산출물:

- 역할 기반 임무 배정
- 장애물 팽창을 적용한 A*
- 웨이포인트 단순화
- 전체 포획 상태기계와 시간 제한
- 105~110초 신규 임무 차단

통과 조건:

- 시뮬레이션 100회에서 교착 없이 종료
- 실패 이유가 `RETRY`, `ABANDON`, `SAFE_STOP` 중 하나로 기록
- 이미 득점한 물체를 장애물·보호 대상으로 취급

### M6 — 통신과 가상 로봇 게이트웨이

산출물:

- 버전이 있는 명령·텔레메트리 스키마
- UDP 게이트웨이와 가상 게이트웨이
- 명령 번호, 중복 제거, TTL, heartbeat
- 지연·손실·재정렬 장애 주입 테스트

통과 조건:

- 중복되거나 오래된 명령을 실행하지 않음
- 통신 손실 후 500ms 이내 정지 상태 확인
- 영상부터 명령 반영까지 200ms 이하 목표를 측정 가능

### M7 — ESP32 펌웨어

산출물:

- 보드·핀 설정 분리
- 엔코더 계측, 바퀴 속도 PID, 서보 게이트
- 포획·게이트·배터리 텔레메트리
- 물리 정지와 통신 watchdog
- 모터 없는 모의 입출력 빌드

통과 조건:

- 바퀴를 든 상태에서 방향·엔코더 부호 검증
- 잘못된 입력과 통신 손실에서 항상 모터 출력 0
- 재연결 시 명시적 새 명령 전까지 정지 유지

### M8 — 실제 로봇 한 대 폐루프

산출물:

- 카메라 위치 보정과 엔코더 제어 결합
- 목표 좌표 이동, 최종 20cm 저속 정렬
- 실제 포획·배출 전체 사이클

통과 조건:

- 1m 이동 오차 30mm 이하
- 포획·배출 10회 중 9회 성공
- 비상정지와 통신 장애 시험 통과

### M9 — 다중 로봇과 제출 안정화

산출물:

- 2대 후 4대 우선순위 예약, 대기점, 좁은 구간 상호배제
- 전체 120초 실행과 촬영 절차
- 필요할 경우 드론 영상 입력기 독립 실험

통과 조건:

- 120초 시험 10회 중 8회 이상 목표 점수
- 기존 득점 물체 훼손 없음
- 한 로봇 장애가 다른 로봇의 안전정지를 방해하지 않음

| 9/27~9/28 | 제출 리허설 | 영상·사진·기술 요약 검증 |
| 9/29 | 완충일 | 새 기능 금지, 제출 확인 |

임계 경로는 `고정 카메라 → 단일 로봇 → 포획 성공 → 전체 반복`이다.
드론은 이 경로를 막아서는 안 된다.

## 7. 팀 작업 분할

두 명 이상이면 다음 작업을 병렬로 진행할 수 있다.

- 서버 기반/시뮬레이션: 데이터 모델, 상태기계, 테스트
- 영상: 기존 `robo_control.vision` 위에 HSV, 추적, 2카메라 융합, 실측 데이터 추가
- 펌웨어: 모터·엔코더·서보·watchdog
- 통합/기구: 프로토콜, 측정, 포획 반복시험, 로그 분석

공유 인터페이스 변경은 먼저 작은 설계 PR로 합의한다. 한 PR에서는 가능하면
한 모듈의 계약 또는 한 가지 사용자 동작만 변경한다.

## 9. 완료 정의

기능은 다음을 모두 만족해야 완료로 본다.

- 정상 경로와 실패 경로의 자동 테스트가 있다.
- 설정과 입력 자료로 결과를 재현할 수 있다.
- 하드웨어가 없어도 모의 구현으로 테스트할 수 있다.
- 시간 제한과 안전 동작이 코드에 명시되어 있다.
- 로그만 보고 실패 위치와 이유를 확인할 수 있다.
- README 또는 관련 문서가 함께 갱신된다.
- CI의 테스트와 코드 검사가 통과한다.
