# 하드웨어 없는 운영 준비: 대상 연결·관측 접근점·장애물·검증

2026-09-07 후속. 기존 검출기/추적기/WorldState/임무/차동/가짜 통신을 재사용한다.
새 코드는 실제 운용용 소프트웨어지만, 출력은 계속 기록 또는 메모리 가짜 수신기다.
물체의 실제 신원·집기·배출·득점·물리 정지 검증을 대신하지 않는다.

## 2시간 작업의 우선순위

사용자 요청의 작업 시간은 2026-09-07 21:15:37~23:15:37 KST다.
팀원 코드/웹 동선/CAD/사양 및 팀원의 작업에는 관여하지 않는다.

1. 관측 물체의 임시 ID와 임무 물체 ID를 운영자가 명시적으로 연결하는 흐름.
2. 관측 위치를 반영하는 픽업 접근점과 그 변경/유실의 안전 경계.
3. 검토한 외곽과 현재 관측을 경로/제동 검사에 연결하는 동적 장애물 지도.
4. 영상→관측→대상 연결→접근점→장애물→가짜 통신의 반복 검증 및 오류 경계 강화.

다중 로봇 동시 실행은 현재 단독 이동보다 안전 상태가 크게 복잡해지므로,
식별/접근점/장애물 증거 연결이 안정화되기 전에는 우선 확장하지 않는다.

## 1. 임무를 시작하지 않고 관측 기록

카메라/색상/임무 계획은 실제로 준비한 파일로 대체한다. `runtime_mission.example.json`의
null은 여전히 실행 불가이며, 접근 자세/반경을 검토해야 한다. 카메라 없이 이미 녹화한
파일을 쓰려면 `--camera 0`을 `--video recordings/match.avi`로 바꾼다.

```powershell
.\.venv\Scripts\python.exe -m robo_control.runtime --camera 0 --calibration recordings/camera.json --fleet config/qualifier_senior.json --mission recordings/mission-reviewed.json --colors recordings/colors-reviewed.json --mission-observe-only --report recordings/preflight-001.jsonl --duration-s 15
.\.venv\Scripts\python.exe -m robo_control.binding_tools inspect recordings/preflight-001.jsonl
```

`--mission-observe-only`는 임무 카탈로그·로봇·물체 WorldState만 기록한다. 임무 시계와
작업 단계는 시작하지 않고 모든 출력은 0이다. `--wire-fake`/`--bindings`와 같이 쓰면
거부한다. 색상 프로필에 원기둥만 있으면 디스크/큐브가 검출되지 않는다. 사용할 물체
종류와 색의 HSV 프로필을 별도로 검토해야 하며 이 작업은 임의 색상 임계값을 넣지 않는다.

`inspect`는 종료된 정상 JSONL의 마지막 ready WorldState를 보여 준다. 현재 카메라에
다시 연결하지 않는다. 모든 위치/유효성은 **기록 당시**의 값이며 `historical_only=true`다.
관측 물체가 누락된 최신 ready 기록을 피해서 더 오래된 물체 위치를 찾아 주지 않는다.

## 2. 운영자가 ID를 고르고 미검토 초안 생성

아래 `object-000001`은 예시 문자열이다. 실제 inspect 출력의 object_id로 바꾼다.
관측 결과·실제 배치·물체 구분을 함께 확인하여 선택한다. 임무 ID에는 `D1`, `R1` 등
카탈로그의 ID를 쓰며 서로 다른 물체를 같은 ID로 지정하지 않는다.

```powershell
.\.venv\Scripts\python.exe -m robo_control.binding_tools draft recordings/preflight-001.jsonl --select D1=object-000001 --half-size-mm 15 --output recordings/bindings-draft.json
```

- 색깔/거리만으로 임무 ID를 자동 선택하지 않는다. `--select`는 사용자의 명시 선택이다.
- `--half-size-mm`는 사용자가 검토할 초기 배치 영역의 반폭/반높이다. 물체 반경이나
  카메라 정확도 인증값이 아니다. 위 15mm도 사용 예시이지 권장 실측값이 아니다.
- 출력은 `reviewed=false`, `reviewed_by=""`, `evidence=""`인 **실행 불가 초안**이다.
- 물체 종류/색, 영역과 대응 ID를 확인한 뒤에만 reviewed를 true로 바꾸고 검토자와
  근거를 적는다. 운영 코드나 이 도구가 사용자를 대신해 검토 완료 처리하지 않는다.
- 파일을 다시 읽어 변경을 자동 반영하지 않는다. 검토 완료 파일은 새 runtime 시작 시 고정한다.
- 기존 보고서/초안 파일은 덮어쓰지 않는다. 다른 이름을 지정한다.

초안에는 과거 임시 track ID를 넣지 않는다. 대신 명시 선택한 물체의 위치에서 작성한
**초기 식별 영역**을 넣는다. 다음 실행에서는 같은 영역의 새 관측으로 새 세션 ID를 연결한다.
영역에 다른 동종 물체를 바꿔 놓아도 카메라만으로 진짜 물리 신원을 증명할 수는 없다.
장면/배치가 바뀌었다면 과거 영역 계획을 그대로 사용하지 말고 재검토한다.

## 3. 새 세션에서 검토한 연결 적용

```powershell
.\.venv\Scripts\python.exe -m robo_control.runtime --camera 0 --calibration recordings/camera.json --fleet config/qualifier_senior.json --mission recordings/mission-reviewed.json --colors recordings/colors-reviewed.json --bindings recordings/bindings-reviewed.json --wire-fake --report recordings/bound-runtime-001.jsonl --duration-s 120
.\.venv\Scripts\python.exe -m robo_control.runtime_report recordings/bound-runtime-001.jsonl
```

`--bindings`에는 `--mission`과 `--colors`가 모두 필요하다. 생략하면 기존 정적 접근 계획
모드가 유지되므로, 연결 기능이 모든 기존 실행에 암묵적으로 적용되지는 않는다.

| 조건 | 처리 |
|---|---|
| 카메라/재생 모드/경기장 치수/관측 프로필 불일치 | 시작 전에 거부 |
| 프로필에 해당 kind/colour가 없음 | 시작 전에 거부 |
| 중복 임무 ID, 영역 겹침/경계 접촉, 범위 밖 | 시작 전에 거부 |
| 선택 임무의 비큐브 픽업 대상에 연결 영역 누락 | 시작 전에 거부 |
| 빈 영역, 여러 물체, 다른 종류/색, 미확인/소유 중 트랙 | 전체 초기 연결 대기, 임무/통신 허가 미시작 |
| 모든 영역에 새 관측 3회로 확인된 단일 대상 | 하나의 원자적 배치로 전부 연결 |
| 연결된 현재 픽업 대상의 누락/모호성/다른 ID로 교체 | 종료 잠금, 전체 정지 요청; 자동 대체 연결 없음 |
| 집기 조작 이후 대상이 가려짐 | 관측만으로 소유/성공을 만들지 않음; 기존 별도 센서 단계 적용 |

다른 색 물체나 tentative/missing 트랙도 영역 점유 후보에 포함한다. 잘못된 색을
무시해 혼잡한 영역을 단일 대상으로 만드는 동작은 없다. lost 트랙은 초기 후보에서
제외하지만 이미 연결한 ID를 다른 ID로 바꾸지는 않는다.

초기 모든 연결을 확인한 뒤에는 **현재 픽업 단계**의 대상만 즉시 출발 조건으로 검사한다.
나중 임무의 대상이 사라졌으면 그 임무를 시작할 때 거부한다. 집기 이후 가림을
허용한다는 것은 집기가 확인되었다는 뜻이 아니다. 큐브의 기존 confirm_load/센서 계약도
보존하며 바닥 관측을 적재 센서로 대체하지 않는다.

통신 오류 후 명시적 API 재연결은 기존대로 새 관측 3프레임이 필요하다. 확인 중인
WorldState를 신원 유실로 오인하지 않되, 새 관측이 준비된 뒤 대상이 없으면 종료한다.
대상 유실 확인은 가짜 통신 큐 처리보다 먼저 수행해 그 tick의 대기 중 이동을 폐기한다.

`observation_profile_id`는 정규화된 calibration/tags/colors의 SHA-256이다. 보정/태그/HSV
설정 변경을 구분하기 위한 식별자이지 장치 인증/영상 서명은 아니다. 임무 실행 옵션과
관측 전용 옵션은 이 ID에서 제외하므로 같은 관측 설정으로 새 세션을 만들 수 있다.

## 기록과 테스트

매 runtime tick의 `bindings`는 초기 연결 배치의 상태/근거/후보/대응표를 기록한다.
`bound`는 배치가 적용됐다는 **역사적 상태**이며, 각 물체가 지금도 보인다는 뜻은 아니다.
현재 위치/유효성은 해당 tick의 `mission.world.pieces`를 봐야 한다.
`binding_wait_ticks`, `binding_fault_ticks`, `mission_observe_only`는 보고서 요약에도 포함된다.
모드 혼합·대응표 변경·미래 순번·검토자 변경·허위 물리 확인·대기 중 이동 주장은 거부한다.

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -p 'test_mission_bindings.py' -q
.\.venv\Scripts\python.exe -m unittest discover -s tests -p 'test_binding*.py' -q
```

생성한 색상 물체/AprilTag 영상을 실제 OpenCV로 디코딩하고 자식 프로세스/CLI로
관측 전용→초안→새 세션 연결→4대 가짜 수신기→종료 로그를 시험한다.
시험에서만 synthetic-test 검토자를 사용한다. 실제 촬영/물체 배치/모터/집게 검증은 아니다.

대상 연결 단계의 전체 Python 회귀는 603개 통과했다. 21:52 KST 중간 검증에서는
관측 픽업점/로그 검사까지 포함한 전체 **634개 통과**(기존 556개 대비 78개 추가).
OpenCV 실제 영상·자식 프로세스·CLI 연결을 포함한다. 실제 하드웨어 시험 결과가 아니다.

## 관측 위치 기반 픽업점 — 임무 schema 2

`config/runtime_observed_mission.example.json`은 **null을 검토한 값으로 채워야 하는
실행 불가 예제**다. schema 1의 고정 접근점은 그대로 지원한다. schema 2에서는
하나 이상 task의 pickup에 `mode="observed_piece"`를 명시하고 아래 값을 모두 제공한다.
실행에는 검토된 `--bindings`가 필수이며, 관측 전용에서는 연결 없이 기록만 할 수 있다.

| 설정 | 의미 |
|---|---|
| `heading_rad` | 접근 완료 시 로봇이 향할 경기장 기준 방향. 물체 yaw 측정값이 아님 |
| `tool_forward_mm`, `tool_left_mm` | 로봇 회전중심→픽업 접촉점의 몸체 좌표. 전방/좌측 양수 |
| `max_anchor_drift_mm` | 최초 확인한 대상 위치에서 허용하는 누적 변위 상한 |
| `replan_distance_mm` | 마지막 경로 계획 목표에서 이보다 이동하면 A* 재계획 |
| `max_replans` | 대상 이동으로 인한 재계획 허용 횟수. 0이면 재계획 필요 시 종료 |

로봇 목표 = 새로 관측한 물체 중심 − 설정한 접촉점 오프셋을 목표 방향으로 회전한 값.
집게 길이·측면 오프셋·카메라 오차 허용치·변위 한계는 자동 결정하지 않는다.
사용자가 미정인 하드웨어 수치를 추정해 넣은 것도 아니다. 단위 시험의 값은 합성 예시다.

- 최초 물체 위치/임시 트랙은 현재 WorldState에서만 가져온다. 시나리오 배치점을
  측정값이나 장애 시 대체 목표로 사용하지 않는다.
- 모든 새 유효 관측에서 대상 위치·신원·최초점 기준 변위를 검사한다. 변위 초과,
  신원 교체, 바깥/고정 장애물/다른 로봇에 겹치는 목표는 가짜 이동 큐 처리 전에 종료한다.
- 작은 대상 이동도 경로 마지막 점에 즉시 반영한다. 예전 계획점에 도착했다는 이유로
  새 위치의 집기 정렬이 완료됐다고 처리하지 않는다. 기존 새 관측 2회 도착 확인을 유지한다.
- A* 재계획은 현재 관측한 로봇 위치에서 수행한다. 시작/끝 연결 선분과 차체 여유를
  계속 검사하며, 재계획 횟수 초과 시 오래된 목표로 계속 움직이지 않는다.
- 카메라/통신 복구가 최초 물체 위치나 이미 사용한 재계획 횟수를 초기화하지 않는다.
- 집기 조작에 진입하면 마지막 픽업점은 진단 이력일 뿐이다. `observed_pickup_in_use`
  플래그로 현재 접근/정렬에 쓰는지 구분한다. 가림만으로 grip/load/release를 만들지 않는다.
- 큐브는 기존 적재 확인에서 시작하고 물체 회전각도 미측정이므로 관측 픽업 모드를
  거부한다. 배출 위치/자세와 후퇴 위치는 기존 검토한 고정 계획과 별도 센서 계약이다.

추가 검증:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -p 'test_observed_pickup.py' -q
.\.venv\Scripts\python.exe -m unittest discover -s tests -p 'test_binding_video.py' -q
```

아래 동적 장애물 지도 및 통합·성능 검증까지 이어서 구현했다.

## 관측 물체의 동적 장애물 지도

`--object-obstacles recordings/object-obstacles-reviewed.json`을 명시하면 기존 경로/제동
검사에 현재 관측 물체의 외곽을 추가한다. `--mission`과 `--colors`가 필요하다. 관측 전용
모드에서도 지도를 진단할 수 있다. 예제는 `config/object_obstacles.example.json`이며,
미검토/null 상태는 실행 불가다. 아래 값을 운영자가 검토해야 한다.

- HSV 프로필의 모든 kind/colour 조합에 대응하는 `radius_mm`: 물체 전체를 포함하는
  보수적 반경. 큐브는 방향을 측정했다고 가정하지 않고 어떤 방향에서도 포함해야 한다.
- `position_margin_mm`: 위치 불확실성 여유. 카메라 정확도를 자동 인증하는 값이 아니다.
- `max_route_replans`: 막힌 경로를 새 관측 위치에서 다시 계획할 수 있는 횟수, 0~100.
- `reviewed=true`, 검토자, 근거. CAD 초안이나 물체 이름에서 치수를 자동으로 가져오지 않는다.

```powershell
.\.venv\Scripts\python.exe -m robo_control.runtime --camera 0 --calibration recordings/camera.json --fleet config/qualifier_senior.json --mission recordings/mission-reviewed.json --colors recordings/colors-reviewed.json --bindings recordings/bindings-reviewed.json --object-obstacles recordings/object-obstacles-reviewed.json --wire-fake --report recordings/obstacle-runtime-001.jsonl --duration-s 120
```

지도는 검토한 반경과 여유를 포함하는 축 정렬 사각형으로 경로를 보수적으로 검사한다.
새 tentative 물체도 현재 raw 검출과 같은 좌표/종류/색으로 연결되면 즉시 잠재 장애물이다.
이는 픽업 신원이 확인됐다는 뜻이 아니며, 픽업에는 여전히 별도 3프레임 확인과 연결이 필요하다.
종류/색별 크기가 없거나 모호한 raw 후보를 대응할 수 없으면 진행하지 않는다.

| 상황 | 동작 |
|---|---|
| 관측 준비 전 | 지도/임무 대기, 출력 0 |
| 물체가 이동하거나 새로 나타남 | 새 관측 외곽을 경로와 제동 검사에 반영 |
| 앞으로 갈 경로가 막혔지만 당장 제동 위험은 아님 | 현재 로봇 위치에서 제한된 횟수의 재계획 |
| 새 장애물이 현재/기존 명령의 제동 범위에 들어옴 | 대기 중 가짜 이동 전달 전에 전체 정지/종료 |
| 기억한 장애물이 누락·모호·다른 ID가 됨 | 마지막 외곽을 진단용으로 보존하고 종료 잠금 |
| 카메라 전체 관측 만료 | 외곽을 지우지 않고 ready=false, 기존 관측 watchdog 적용 |
| 물체가 64개를 초과하거나 모르는 크기/종류가 들어옴 | 용량/규격 오류로 종료 |

`object_obstacles`의 `ready`는 **관측한 후보의 보수적 충돌 검사에 쓸 수 있음**을 뜻한다.
카메라가 경기장 전체를 빠짐없이 봤다거나 장애물을 모두 검출했다는 뜻은 아니다.
`field_coverage_verified`, `physical_clearance_verified`, `unobserved_is_free`는 항상 false다.
오류 후에는 다른 물체로 자동 치환하거나 감지되지 않는 장애물을 자동 삭제하지 않는다.

### 픽업 접촉과 소유권 한계

현재는 **자동 접촉 예외가 없다**. 임무의 대상이라는 이유, 집게 명령을 보냈다는 이유,
시나리오에서 적재됨으로 설정했다는 이유만으로 장애물을 제거하지 않는다.
검토한 로봇 회전/팔/적재물 외곽과 물체 외곽이 겹치면 목표/경로를 거부한다.
실제 집게가 닿는 좁은 접촉 구간이나 집기 후 가림을 허용하려면 기구 외곽과 검증된
센서/소유권 전이 계약이 추가로 필요하다. 이 옵션을 켠 상태에서 센서 없는 전체
집기/배출 임무가 완주한다고 주장하지 않는다. 관측 픽업 목표와 외곽이 충분히 분리되는
접근 주행은 하드웨어 없이 검증할 수 있다.

확인용 테스트:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -p 'test_observed_obstacles.py' -q
.\.venv\Scripts\python.exe -m unittest discover -s tests -p 'test_obstacle_report.py' -q
```

보고서는 지도 모드/대응 ID/크기/관측 시각/개수/재계획 횟수의 연속성도 검사한다.
중간에 외곽을 삭제하거나, 오래된 외곽을 ready로 바꾸거나, 임의 접촉 예외/물리 검증을
추가한 기록은 거부한다. 종료한 지도의 외곽은 현재 위치가 아니라 마지막 관측 이력이다.
ready인 지도는 같은 프레임 WorldState의 ID/분류/좌표/확인 상태와 전부 대응해야 한다.
revision만 증가시켜 임의 좌표를 넣거나 관측 물체를 통째로 누락한 기록도 거부한다.

### 지연된 이동 명령의 안전 검사

ACK 대기 중 로컬 출력이 0이라는 사실만으로 수신기가 정지했다고 보지 않는다.
새 관측을 처리한 뒤, 큐를 전달하기 **전** 다음을 모두 제동 검사에 넣는다.

- 현재 카메라에서 측정한 이동과 로컬 출력.
- 가짜 수신기의 마지막 목표 속도.
- 아직 ACK가 없는 전송 대기/적용 여부 미확인 차체 명령.

이전 차체 전진 명령의 방향은 현재 측정한 로봇 자세로 계산한다. 목표 속도를 실측
속도라고 기록하지 않으며, 서로 다른 명령을 평균하여 위험을 숨기지 않는다.
수신기 조회/대기 명령 조회는 읽기 전용으로 시계/명령 유효기간을 갱신하거나 큐를
전달하지 않는다. 0 출력 대기 중에도 이전 이동 명령이 위험하면 전달 전에 폐기·정지한다.

### 입력 규모와 기하 연산 검증 — 중간 결과

최종 전체 회귀는 **698개 통과**했다. 사각형과 선분 거리 연산을
특화했고, 고정 시드 6,000개 사례를 기존 일반 다각형 거리 구현과 비교했다. 모서리는
사각 팽창만으로 잘못 판정하지 않고 정확한 유클리드 거리를 사용한다.

로컬 합성 64물체/4로봇/20mm 격자 사례에서 연속 tick 계산은 약 40~59ms에서
약 7.4~8.7ms로 줄었고, 최초 경로 계획 포함 tick은 약 75ms에서 41ms로 줄었다.
이 수치는 해당 PC의 짧은 비교 측정이며, OS 실시간성/실제 통신/현장 제동 보장이 아니다.
감시 100ms/관측 200ms/명령 300ms 제한은 완화하지 않았다.
이후 4대 가짜 수신기와 이전/대기 명령 검사를 모두 켠 같은 64물체 사례에서는 일반 tick
약 10.7~15.1ms, 최초 경로 계획 포함 tick 약 43.3ms였다. 입력 종류가 다른 수치끼리는
단순 성능 비교로 쓰지 않으며, 호스트 부하에 따라 감시 기한을 넘으면 기존 정책대로 종료한다.

## 6. 하드웨어 없이 반복하는 통합 검증

```powershell
.\.venv\Scripts\python.exe tools/verify_mission_operations.py --output-dir recordings/operations-001 --seconds 12
.\.venv\Scripts\python.exe tools/verify_mission_operations.py --output-dir recordings/operations-soak-001 --seconds 12 --observe-only-soak-s 120
```

새 디렉터리에 AprilTag 4개와 색상 물체 2개가 있는 시험 영상을 생성하고, 평소 사용하는
`robo_control.runtime` CLI를 별도 프로세스로 실행한다. `--seconds`는 6~20초다.
영상 재생·OpenCV 검출·기존 추적·보고서 검증·가짜 통신을 생략하거나 모의 함수로 대체하지 않는다.

가짜 통신 세 시험은 모두 실제 CLI의 보고서가 완결되어야 하며, 4대의 수신기 모델 0 목표와
정지 ACK를 확인해야 한다. 임의 오류나 다른 정지 이유는 통과가 아니다. 가짜 이동이 한 번도
계산되지 않아도 성공 처리하지 않는다. 관측 전용 soak는 별도 세션이며 5~600초 또는 생략이다.

시험에는 자세 적분기나 집기/배출 센서 성공 주입이 없다. 따라서 정적 태그 영상으로 임무를
완주했다고 보고하지 않는다. 120초는 스트리밍 지속성 시험이지 120초 경기 전략 검증이 아니다.
모든 반경/오프셋/색상/검토자 값은 생성 픽셀을 위한 **시험 전용**이다. 실제 사용자 입력을
자동 검토하거나 실제 기구 치수로 저장하지 않는다. 거친 격자가 안전상 접근점을 차단할 수
있으며, 검증 도구는 그런 경우도 임의로 무시하지 않고 다른 실패 원인으로 보고한다.

`verification.json`, 시나리오별 `*-verification.json`, 원본 JSONL, 프로세스 출력과 입력
스냅샷을 남긴다. OpenCV/Python/NumPy 버전도 기록한다. 기존 증거는 덮어쓰지 않으며,
실패한 시도의 폴더도 남는다. `recordings/`는 Git 추적 대상이 아니므로 큰 영상/로그는 push하지 않는다.
OpenCV 5.0.0/4.14.0에서 세 가지 짧은 영상 시험을 각각 통과했다.
OpenCV 5의 120초 관측 전용 시험도 완료했다: 실제 호스트 경과 120.016초, 감시 tick 5,900개,
관측 프레임 2,019개, 준비된 장애물 tick 5,872개, 최대 tick 간격 63ms, 최대 호스트 관측 나이 109ms.
출력 0·임무 미시작 상태를 유지했다. `recordings/goal-operations-soak-cv5-20260907/verification.json`과
`observation-soak-verification.json`이 로컬 증거다.
OpenCV 4에서도 같은 120초 시험을 통과했다: 120.015초, 감시 tick 5,891개, 관측 2,043프레임,
준비된 장애물 tick 5,870개, 최대 tick 간격 63ms, 최대 호스트 관측 나이 94ms.
그 증거는 `recordings/goal-operations-soak-cv4-20260907/`에 있다. 두 실행의 프레임 수 차이는
실제 처리·최신 프레임 전달 시점의 차이이며, 누락 프레임을 생성하거나 관측 시각을 재작성하지 않았다.
