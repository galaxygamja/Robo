# 6대 로봇 시뮬레이터 및 중앙 관제 소프트웨어 구현 가이드

> 적용 범위: 2026 로보틱스 챌린지 **예선**, 1m급 경기장, 120초 경기  
> 현재 단계: 카메라·모터·ESP32·센서 등 실제 부품이 하나도 없는 상태  
> 목표: 실제 부품을 사기 전에도 6대 로봇의 임무 배정·경로 계획·가상 이동·충돌 감시·안전정지를 검증하고, 나중에는 입출력 어댑터와 관측·명령 폐루프를 단계적으로 연결하여 실물 시스템으로 확장한다.

이 1차 버전은 **로컬·오프라인 실행**을 기준으로 한다. 인터넷, 클라우드 API, 생성형 AI, 딥러닝 추론 서버가 없어도 기본 데모와 자동시험이 전부 실행되어야 한다. OpenCV와 NumPy는 합성 영상·향후 실영상 처리에 사용하되, 실제 카메라와 AprilTag 라이브러리는 선택 의존성으로 둘 수 있다.

## 0. 현재 배포된 v0.1과 장기 설계를 구분해서 읽기

이 문서는 두 종류의 내용을 함께 담는다.

- **현재 구현**: 저장소에서 지금 실행할 수 있는 6대 이동·배정·시간예약 A*·안전정지·웹 대시보드
- **확장 설계**: 물체 포획, 실제 비전, 정밀 운동학, 로그 리플레이, ESP32, 드론을 추가할 때 지켜야 할 계약

현재 v0.1은 중앙 관제의 안전한 뼈대다. 아직 포획 장치, 실제 색상 검출, AprilTag 추적, 실제 UDP 송신 활성화, 드론 제어, 점수 최적화까지 완성됐다는 뜻이 아니다. 각 장에서 “권장”, “추가”, “향후”라고 표시한 내용은 구현 명세 또는 시험 계획이다.

현재 바로 실행되는 기능:

- Python 표준 라이브러리만으로 동작하는 로컬 시뮬레이터
- 공식 배치가 아닌 결정적 기본 시나리오의 가상 로봇 6대. 사용자 시나리오와 설정은 1~8대 지원
- 거리와 우선순위를 이용한 정확한 1:1 임무 배정
- 20mm 격자의 4방향 공간-시간 A*
- 정점·맞교환 간선 충돌뿐 아니라 tick 사이 선형 이동의 최소거리까지 예약 검사
- 고정 격자의 연결 성분 사전검사, 정지 로봇 예약, 미해결 로봇을 반영한 경로 재작성
- 경기장 경계 및 설정된 138mm 최소 중심거리 위반 감시
- 120초 제한, 일시정지, 초기화, 재계획, 전체 긴급정지
- `http://127.0.0.1:8080` 로컬 웹 대시보드
- 브라우저 없이 빠르게 끝까지 돌리는 headless 모드
- 향후 카메라·UDP·드론을 위한 독립 어댑터 계약. 현재 엔진 폐루프에는 미연결
- 향후 명령 루프에서 사용할 메모리 기록형 `DryRunTransport` 클래스
- 호출하면 오류로 닫히는 `DisabledDroneController`

현재 미구현이며 이 문서가 다음 단계로 정의하는 기능:

- 실제 차동구동 모터 물리와 엔코더 PID
- 실제 포획·운반·배출 상태기계
- 합성 이미지 렌더링과 AprilTag/HSV 검출
- 카메라 캘리브레이션과 프레임 추적
- seed 기반 무작위 배치 CLI
- 구조화 실행 로그와 `replay` 명령
- 로봇별 실시간 UDP telemetry/ACK 폐루프
- 실제 드론 스트림과 조종기 자동화

## 1. 먼저 알아둘 결론

부품이 없어도 중앙 관제 코드의 대부분은 지금 만들고 시험할 수 있다. 다만 지금 성공했다는 것은 **가상 환경에서 논리와 소프트웨어 구조가 작동한다**는 뜻이지, 실제 로봇이 같은 정확도로 움직인다는 뜻은 아니다.

소프트웨어가 단계적으로 검증해야 하는 전체 범위:

- 6대의 로봇을 동시에 생성하고 움직이는 시뮬레이션
- 로봇별 ID·위치·방향·속도·배터리·임무 상태 관리
- 경기 물체와 목적지 표현
- 점수, 성공확률, 이동시간을 고려한 임무 배정
- 격자 기반 A* 경로 생성
- 로봇 크기와 안전여유를 반영한 장애물 팽창
- 시간 예약과 우선순위를 이용한 로봇 간 충돌 방지
- 포획·운반·배출 상태기계
- 120초 경기 타이머와 105~110초 이후 신규 임무 제한
- 지연, 패킷 손실, 위치 오차, 로봇 고장 등 실패 상황
- 명령 유효시간과 통신 두절 시 자동정지
- 동일한 로그로 오류를 재현하는 리플레이
- 향후 카메라, 드론, ESP32가 연결될 인터페이스

부품을 받은 뒤에만 확정할 수 있는 것:

- 실제 모터의 최대속도, 가속도, 좌우 편차
- 엔코더 1회전당 펄스 수와 바퀴 유효 지름
- 바닥 재질별 미끄러짐과 정지거리
- 포획 장치의 실제 성공률과 필요한 정렬 오차
- 실제 카메라의 렌즈 왜곡, 노출, 영상 지연, 가림 현상
- Wi-Fi 환경에서의 지연과 패킷 손실률
- 로봇 상단 태그 크기별 검출률
- 드론 영상 프로토콜과 체공 흔들림
- ESP32 핀, 모터 드라이버, 서보의 구체적인 배선

따라서 실제 관측·명령까지 포함한 **완성형 후속 버전**의 성공 기준은 “가상 로봇이 예쁘게 움직인다”가 아니라 다음 세 가지다. 현재 v0.1은 이 기준 중 경로 계획과 fail-closed 뼈대만 일부 충족하며, 영구 로그와 실물 폐루프는 아직 없다.

1. 모든 판단의 입력과 출력이 기록된다.
2. 시뮬레이터 대신 실제 장치를 연결해도 계획 코드를 고치지 않아도 된다.
3. 실패를 일부러 넣었을 때 로봇이 위험한 동작을 계속하지 않는다.

## 2. 설계 원칙

### 2.1 생성형 AI가 모터를 직접 조종하지 않는다

이 프로젝트에서 “AI”라고 부르는 중앙 지능은 대화형 생성 모델이 아니다. 실시간 제어에는 결과가 반복 가능하고 처리시간을 예측할 수 있는 다음 기술을 사용한다.

- OpenCV 또는 동등한 영상처리
- AprilTag/ArUco 기반 로봇 식별
- 칼만 필터 또는 단순 알파-베타 필터 기반 상태 추정
- 비용함수 기반 임무 배정
- A* 기반 경로 계획
- 시간 예약 기반 충돌 회피
- 상태기계 기반 임무 실행
- 각 로봇의 엔코더 PID 또는 경로 추종 제어

생성형 AI는 나중에 로그 해석, 파라미터 추천, 문서 생성에 도움을 줄 수 있지만 경기 중 폐루프 제어에 포함하지 않는다.

### 2.2 중앙 서버는 고수준 목표만 보낸다

중앙 서버가 매 순간 왼쪽·오른쪽 모터 PWM을 직접 보내면 영상 또는 네트워크가 잠깐 끊겼을 때 제어가 바로 불안정해진다. 서버는 다음과 같은 고수준 명령을 보낸다.

- `(x, y, heading)` 목표 자세
- 허용 최대 선속도와 회전속도
- 짧은 명령 유효시간
- 게이트 열기·닫기
- 즉시 정지

실물 로봇의 ESP32는 다음을 담당한다.

- 엔코더 읽기
- 모터 PID
- 목표까지의 짧은 구간 추종
- 서보 제어
- 센서 읽기
- 명령 만료 감시
- 물리 비상정지

현재 v0.1에서는 `SimulationEngine`이 계획 경로를 보간해 가상 로봇을 움직인다. `adapters.py`에는 실제 송신 없이 명령을 메모리에만 기록하는 `DryRunTransport`가 준비되어 있지만, 아직 `SimulationEngine`이 `RobotCommand`를 발행하는 폐루프까지 연결되지는 않았다. 따라서 기본 실행은 실제 장치로 어떤 패킷도 보내지 않는다.

1차 배포에는 실제 모터·서보·드론으로 신호를 보내는 출력을 기본 비활성화한다. `UdpRobotTransport`는 향후 계약을 보여주지만 현재 기본 실행 경로에서는 선택되지 않는다. `DisabledDroneController`는 호출 즉시 오류를 내는 fail-closed 구현이다. 실제 출력은 나중에 별도 설정과 명시적인 실행 옵션이 모두 있을 때만 활성화되도록 확장한다. 지금 단계에서 프로그램을 실행했는데 우연히 같은 네트워크의 장치가 움직여서는 안 된다.

### 2.3 입력과 출력은 반드시 교체 가능해야 한다

중앙 알고리즘은 카메라 종류와 통신 종류를 몰라야 한다.

```text
[Synthetic / Replay / FixedCamera / DroneCamera]
                       │
                       ▼
             공통 Observation 형식
                       │
                       ▼
      상태추정 → 임무배정 → 경로계획 → 안전감시
                       │
                       ▼
               공통 Command 형식
                       │
                       ▼
        [VirtualRobot / UDP-ESP32 / Serial]
```

이 원칙을 지키면 드론을 쓰지 못하게 되어도 중앙 계획 코드를 유지할 수 있다. 다만 현재 v0.1은 카메라 어댑터를 `SimulationEngine`의 상태 갱신에 연결하지 않았으므로, 영상 입력 어댑터를 바꾸는 것만으로 동작하지 않는다. 공통 관측 형식으로의 변환, 추적·timeout, 상태 갱신 폐루프를 먼저 구현해야 한다.

### 2.4 기본 수량은 6대지만 설정으로 바꾼다

현재 소프트웨어 검증은 6대로 한다. 그러나 실제 예선에서는 출발구역과 충돌 위험 때문에 2~3대가 더 현실적일 수 있다. 코드에 `6`을 직접 박아 넣지 말고 설정의 `robot_count`와 로봇 목록 길이로 결정한다.

### 2.5 안전은 계획보다 한 단계 아래에서도 보장한다

경로 계획기가 충돌 없는 경로를 만들더라도 다음 독립 안전장치가 있어야 한다.

- 서버 안전감시기: 예측 충돌, 경기장 이탈, 추적 손실 확인
- 통신 계층: 명령 번호, 생성 시각, 유효시간 확인
- 로봇 제어기: 마지막 유효 명령 이후 300~500ms가 지나면 정지
- 실제 장치: 물리 전원 차단 또는 비상정지

## 3. 시스템 전체 구조

### 3.1 목표 데이터 흐름 — 후속 완성형 구조

실제 카메라와 로봇 명령까지 연결했을 때 한 프레임 또는 한 시뮬레이션 틱의 목표 흐름은 다음과 같다. 현재 v0.1은 시나리오 좌표를 직접 사용해 6~8단계의 계획과 가상 경로 보간을 수행하며, 1~5단계의 영상 인식·추적과 9~12단계의 상태기계·명령 송신·영구 로그는 아직 통합하지 않았다.

1. 세계 또는 카메라에서 관측값을 받는다.
2. 픽셀 좌표를 경기장 mm 좌표로 변환한다.
3. 로봇과 물체의 위치·방향·신뢰도를 갱신한다.
4. 추적되지 않는 객체의 불확실성을 증가시킨다.
5. 완료·분실·포획 상태를 판정한다.
6. 임무가 없는 로봇에 물체를 배정한다.
7. 장애물 지도를 만들고 예약을 반영한다.
8. 필요한 로봇의 경로를 생성하거나 재계산한다.
9. 상태기계가 다음 행동을 고른다.
10. 안전감시기가 명령을 승인·감속·정지시킨다.
11. 로봇 어댑터로 명령을 보낸다.
12. 관측, 판단, 명령, 지연시간을 로그로 남긴다.

### 3.2 현재와 확장 단계의 처리 주기

현재 v0.1은 `mission.control_hz` 기본값인 20Hz로 `SimulationEngine`을 갱신한다. 초기화와 수동 `/api/mission/replan` 요청에서 계획하며, 한 라운드의 로봇들이 모두 도착·정지했는데 미완료 임무가 남으면 자동으로 다시 배정하고 재계획한다. 남은 배정 로봇이 모두 도달 불가이면 `PAUSED`와 `planner_stalled` 이벤트로 멈춰 매 tick 재계획 폭주를 막는다. 웹 화면은 약 200ms마다 `/api/state`를 읽는다. `planner_hz`는 후속 주기적 재계획을 위한 설정 자리이며 현재 엔진이 자동으로 4Hz 재계획을 실행한다는 뜻은 아니다.

실제 카메라와 정밀 물리를 추가할 때의 목표 주기는 다음과 같다.

| 루프 | 권장 주기 | 역할 |
|---|---:|---|
| 시뮬레이션 물리 | 100Hz | 가상 로봇 운동·충돌·센서 갱신 |
| 카메라/가상 관측 | 30Hz | 합성·재생·실시간 프레임 입력 |
| 세계 상태·명령 | 20Hz | 상태 추정, 경로 추종, 명령 만료 |
| 안전감시 | 20Hz 이상 | 거리·경계·통신·추적 상태 확인 |
| 충돌 예약·경로 계획 | 5Hz | 가까운 미래 경로 점유와 재계획 |
| 임무 재배정 | 1~2Hz 또는 사건 발생 시 | 새 물체, 실패, 로봇 고장 처리 |
| 운영 화면 | 10~20Hz | 시각화. 제어 루프와 분리 |
| 로그 저장 | 비동기 | 제어 루프를 막지 않게 큐 사용 |

경로 계획을 영상 프레임마다 전부 다시 돌리지 않는다. 다음 사건에서만 재계산하는 편이 안정적이다.

- 새 임무 배정
- 목표 또는 장애물의 의미 있는 이동
- 계획 경로와 현재 위치 차이가 기준 초과
- 다른 로봇의 예약과 충돌 예상
- 로봇 또는 물체 추적 재획득
- 통신 복구 후 명시적 재시작

### 3.3 권장 모듈 경계

현재 저장소 구조는 다음과 같다.

```text
│  ├─ default.json              # 현재 기본 실행 설정

├─ tools/benchmark.py           # 결정적 기본 시나리오 반복 측정
```

기능이 커지면 `camera/calibration/tracking/world/mission/planning/control/safety/simulation/logging/config` 책임으로 나누되, 처음부터 빈 폴더만 많이 만들 필요는 없다. 현재의 작은 파일에서 책임이 실제로 커질 때 패키지로 분리한다. 도메인, 계획, 상태기계는 OpenCV나 소켓을 직접 import하지 않는 원칙을 유지한다. 그래야 작은 입력으로 빠르고 결정적인 단위시험을 만들 수 있다.

## 4. 개발 환경 준비

### 4.1 중앙 서버 권장 사양

6대 가상 로봇, 1080p 한 개 영상, 일반 OpenCV 처리를 기준으로 다음 정도면 충분하다.

- 64비트 Windows 10/11 또는 Ubuntu 계열
- 최근 Core i5/Ryzen 5급 이상
- CPU 4코어 이상
- RAM 16GB 권장
- SSD 여유공간 10GB 이상
- Python 3.11 권장
- 전용 GPU는 필수 아님

영상 녹화와 여러 카메라를 동시에 사용하면 SSD 쓰기 성능과 USB 대역폭이 CPU보다 먼저 문제가 될 수 있다.

### 4.2 권장 소프트웨어

- Git
- Python 3.11 이상
- 가상환경 `venv`
- 기본 시뮬레이터와 대시보드: 외부 런타임 패키지 없음
- 개발·자동시험: `pytest>=8.0` (`.[dev]` 선택 의존성)
- 향후 영상: NumPy와 `opencv-contrib-python` (`.[vision]` 선택 의존성)
- 향후 선택: 별도 AprilTag 검출 라이브러리

현재 대시보드는 FastAPI가 아니라 Python 표준 라이브러리의 `ThreadingHTTPServer`를 사용한다. 인터넷 연결 없이도 설치된 Python만 있으면 소스 트리에서 `python -m robo_control`로 실행할 수 있다. 의존성을 추가할 때는 `pyproject.toml` 한 곳에서 관리한다.

기본 설정과 시나리오는 개발 중 편집하기 쉬운 `config/`에 있으며, wheel/sdist 설치본에서는 `MANIFEST.in`과 패키지 설정으로 포함된 `robo_control/data/` 사본으로 fallback한다. 두 사본이 달라지지 않도록 패키징 회귀시험과 CI smoke test를 유지한다.

### 4.3 Windows PowerShell 실행 예시

기본 시뮬레이터와 `unittest`에는 외부 패키지가 필요 없다. 저장소에서 바로 실행하는 가장 짧은 절차는 다음과 같다.

```powershell
git clone https://github.com/galaxygamja/Robo.git
Set-Location Robo
py -3.11 -m robo_control
py -3.11 -m unittest discover -s tests -v
```

가상환경이나 `pytest`가 필요할 때만 선택적으로 설치한다. `.[dev]` 설치는 로컬 wheel/cache가 없으면 인터넷 또는 사내 패키지 미러가 필요할 수 있다.

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
.\.venv\Scripts\python.exe -m robo_control
```

브라우저 자동 열기를 원하지 않으면 다음처럼 실행한다.

```powershell
python -m robo_control --no-browser
```

### 4.4 Linux 실행 예시

```bash
git clone https://github.com/galaxygamja/Robo.git
cd Robo
python3.11 -m robo_control --no-browser
python3.11 -m unittest discover -s tests -v
```

Linux에서도 가상환경과 `python -m pip install -e '.[dev]'`는 `pytest` 등 개발 선택 의존성이 필요할 때만 사용한다. 기본 로컬·오프라인 실행을 위해 pip 업그레이드는 요구하지 않는다.

### 4.5 가장 먼저 실행할 검사

```powershell
python -m unittest discover -s tests -v
python -m robo_control --headless
```

첫 명령은 Python 표준 `unittest`로 계획기·시뮬레이션·HTTP API를 검사하고, 두 번째 명령은 화면 없이 기본 시나리오를 빠르게 수행해 최종 JSON 상태를 출력한다. 120초 제한은 설정되어 있지만 기본 임무는 시뮬레이션 시각 약 8.05초에 완료되므로 이 smoke test는 120초 timeout 경계까지 검증하지 않는다. `pytest`를 선호하면 `.[dev]` 설치 뒤 `python -m pytest`도 사용할 수 있다. headless 종료 코드는 임무가 완료되고 충돌이 0회이면 0, 그렇지 않으면 2다. `--headless-step 0.02`처럼 가상 시간 간격을 바꿀 수 있지만 0 이하 값은 거부된다. 종료 코드가 0이어도 `status`, `completed_tasks`, `collision_count`, `unresolved_robots`를 확인한다.

다른 설정 파일을 사용할 때:

```powershell
python -m robo_control --config config/default.json
python -m robo_control --scenario config/scenario_demo.json --headless
python -m robo_control --host 127.0.0.1 --port 8080 --no-browser
```

현재 `--scenario`로 로봇·임무·장애물 JSON을 선택할 수 있다. 아직 `run/test/replay` 하위 명령이나 `--robots`, `--seed` 옵션은 없다. 로봇 수는 JSON 설정 파일의 `robot_count`를 바꾼다. 구조화 로그와 replay CLI는 후속 구현 항목이다.

### 4.6 현재 CLI 옵션

```text
--config PATH          JSON 설정 파일. 생략하면 config/default.json
--scenario PATH        시나리오 JSON. 생략하면 패키지의 기본 scenario_demo.json
--host HOST            대시보드 바인드 주소 덮어쓰기
--port PORT            대시보드 포트 덮어쓰기
--no-browser           브라우저 자동 실행 안 함
--headless             웹 서버 없이 빠른 결정적 실행 후 JSON 출력
--headless-step SEC    headless 한 틱의 가상시간, 기본 0.05초
```

설치 후에는 `robo-control` 콘솔 명령도 같은 `main()`을 호출한다.

### 4.7 현재 로컬 HTTP API

| 메서드 | 경로 | 기능 |
|---|---|---|
| `GET` | `/` | 관제 HTML 화면 |
| `GET` | `/api/state` | 전체 snapshot JSON |
| `GET` | `/healthz` | 프로세스 생존과 경기 상태 |
| `POST` | `/api/mission/start` | 시작 또는 완료 뒤 초기화 후 시작 |
| `POST` | `/api/mission/pause` | 일시정지 |
| `POST` | `/api/mission/reset` | 초기 좌표 복원과 재계획 |
| `POST` | `/api/mission/replan` | 현재 위치에서 전체 재배정·재계획 |
| `POST` | `/api/mission/stop` | fail-closed 전체 긴급정지 |

기본 주소가 `127.0.0.1`이므로 같은 컴퓨터에서만 접속된다. 다른 기기에 화면을 공개하려고 `0.0.0.0`으로 바꾸기 전에는 대회망 규정, 운영체제 방화벽, 접근 통제를 검토한다. 현재 API에는 인증이 없으므로 신뢰할 수 없는 네트워크에 그대로 공개하지 않는다.

`/api/state` 주요 최상위 필드:

```text
version, scenario, status, elapsed_s, remaining_s, duration_s,
field, robots, tasks, obstacles, metrics, events, warnings
```

대시보드가 보여주는 경로와 완료 임무는 이 snapshot의 복사본이며 실물 telemetry가 아니다.

## 5. 설정 파일 설계

코드 안에 경기장 크기, 로봇 반경, 속도, 타임아웃을 직접 쓰지 않는다. 현재 `config/default.json`은 다음 의미의 값으로 구성된다.

```json
{
  "field": {
    "width_m": 1.143,
    "height_m": 1.181,
    "grid_cell_m": 0.02,
    "boundary_margin_m": 0.025
  },
  "mission": {
    "duration_s": 120.0,
    "robot_count": 6,
    "control_hz": 20.0,
    "planner_hz": 4.0,
    "simulation_speed": 1.0
  },
  "robot": {
    "radius_m": 0.063,
    "linear_speed_mps": 0.20,
    "goal_tolerance_m": 0.025,
    "tracking_timeout_s": 0.5,
    "command_timeout_s": 0.5
  },
  "network": {
    "dashboard_host": "127.0.0.1",
    "dashboard_port": 8080,
    "robot_udp_port": 9100
  },
  "safety": {
    "minimum_separation_m": 0.138,
    "stop_on_tracking_loss": true,
    "stop_on_predicted_collision": true
  }
}
```

현재 값 해석:

- 1.143×1.181m 경기장
- 20mm 계획 격자
- 반경 63mm의 단순 원형 차체 근사. 126×100mm 직사각형의 임의 자세를 보수적으로 감싸지 않음
- 벽 방향 추가 여유 25mm
- 로봇 중심 간 최소거리 138mm
- 6대 데모
- 20Hz 중앙 갱신
- 0.20m/s 일정 경로 보간 속도
- 목표 허용오차 25mm
- 추적·명령 타임아웃 0.5초
- 로컬 대시보드 `127.0.0.1:8080`

126×100mm 직사각형의 외접반경은 약 80.4mm다. 따라서 현재 반경 63mm와 중심거리 138mm는 소프트웨어용 미검증 근사이며, 회전하는 실물 차체의 비접촉을 보장하지 않는다. 실측 외형 또는 방향 있는 직사각형 충돌 모델로 다시 검증해야 한다.

`planner_hz`, `tracking_timeout_s`, `command_timeout_s`, `robot_udp_port`와 일부 안전 플래그는 확장 계약을 위해 존재하지만 현재 데모의 모든 경로에서 능동적으로 소비되는 것은 아니다. 반면 `goal_tolerance_m`는 경로 끝에서 목표 도착을 판정할 때 사용된다. 설정에 필드가 있다는 사실과 기능이 완성됐다는 사실을 구분한다.

정밀 시뮬레이션 단계에서는 별도 설정 파일에 다음 목표값을 추가한다.

- random seed: 42
- 물리: 100Hz
- 합성/실제 카메라: 30Hz
- 계획: 5Hz 또는 사건 기반
- 계획 격자: 현재 20mm를 기준으로 계산시간과 경로 품질 측정
- 장애물 추가 여유: 15mm부터 실측 조정
- 순항: 250mm/s
- 포획 접근: 75mm/s
- 배출: 50mm/s
- 명령 TTL: 400ms, 500ms 이내 정지
- 위치 오차 30mm에서 재계획
- 신규 임무 제한: 108초
- 포획 재시도: 1회

현재 로더가 시작 시 검사하는 것:

- `field`, `mission`, `robot`, `network`, `safety` 섹션 존재
- 거리·시간·속도·포트 등 필수 수치가 양수인지
- `robot_count`가 현재 v0.1 지원 범위인 1~8인지
- 격자가 경기장보다 작게 설정됐는지

현재 시나리오 로더가 함께 검사하는 것:

- 로봇 ID가 중복되지 않는지
- 요청한 `robot_count`만큼 시작 로봇이 있는지
- 시작 위치가 출발구역과 차체 반경을 고려한 경기장 안에 있는지
- 시작 로봇 중심거리가 설정된 최소거리 138mm 이상인지
- 임무 ID가 중복되지 않고 로봇·임무 좌표가 경기장 안인지

실물용 설정과 포획 임무를 추가할 때 더 검사해야 하는 것:

- `stop_new_tasks_at_s < duration_s`인지
- 명령 만료시간이 제어 주기보다 충분히 긴지
- 최대속도와 가속도가 0보다 큰지
- 물체와 목적지 ID가 유일한지
- 확률 값이 0~1 범위인지

잘못된 설정은 실행 도중 조용히 보정하지 말고 시작 전에 명확한 오류로 중단한다.

이 문서와 기본 데모에 들어가는 물체·목적지·시작 자세 좌표는 소프트웨어 시험을 위한 예시값이다. 공식 최종 배치가 확정되었거나 실물을 측정한 값으로 오해하면 안 된다. 설정과 실행 요약에 `hardware_verified: false` 또는 동등한 표시를 남기고, 공식 배치와 실측치가 확보되면 별도 시나리오 파일을 만든다. 경기장 1143×1181mm, 출발구역 480×280mm 역시 현재 조사 자료 기준이므로 제출 직전 최신 예선 공지를 다시 확인한다.

## 6. 좌표계와 단위

좌표계 혼동은 실제 연동에서 가장 흔한 오류다. 현재 v0.1의 `Point`, `Rectangle`, 설정, 대시보드 API는 모두 **m 단위**다. 실물 측정값은 mm로 기록하더라도 코드 경계에서 m로 변환한다. 향후 네트워크 계약이 mm를 선택한다면 필드명에 단위를 넣고 한 곳에서만 변환한다.

권장 공통 규칙:

- 현재 내부 거리 단위: m
- 내부 시간 단위: 초, 네트워크 시각은 단조증가 시계 기반
- 각도 내부 표현: rad
- 경기장 원점: 보정된 상부 영상의 왼쪽 아래
- +X: 오른쪽
- +Y: 위쪽
- heading 0: +X 방향
- 양의 회전: 반시계 방향
- 픽셀 원점: 영상 왼쪽 위이며, 반드시 변환 계층 밖으로 나오지 않게 함

속도는 통신 계약에 명시적으로 단위를 붙인다. `speed: 0.2` 같은 필드는 금지하고 현재 `linear_speed_mps`, `max_linear_speed_mps`, `max_angular_speed_rps`처럼 이름에 단위를 포함한다.

### 6.1 로봇 자세

실물 통신용 확장 자세를 mm 필드로 선택한다면 최소 다음처럼 명시한다. 현재 대시보드 snapshot의 `position`은 대신 `x`, `y`를 m 단위로 반환한다.

```json
{
  "x_mm": 320.0,
  "y_mm": 470.0,
  "heading_rad": 1.5708,
  "linear_mps": 0.12,
  "angular_rps": 0.0,
  "timestamp_monotonic_s": 18.425,
  "confidence": 0.97
}
```

각도 차이는 단순 뺄셈 후 `[-π, π)`로 정규화한다. 그렇지 않으면 179도에서 -179도로 바뀔 때 358도 회전하라는 명령이 생길 수 있다.

### 6.2 로봇 외형

초기 시뮬레이션에서는 원 또는 회전 사각형으로 표현할 수 있다.

- 빠른 전역 계획: 바퀴 포함 외형을 감싸는 원
- 정밀 충돌 검사: 방향을 가진 직사각형 또는 다각형
- 기본 SCAD 차체 참고치: 바퀴 포함 약 126×100mm
- 안전여유: 각 방향 10~20mm에서 시작

6대가 좁은 경기장에서 움직이므로 중심점끼리만 비교하면 안 된다.

## 7. 공통 데이터 모델

### 7.1 로봇 상태

현재 `RobotState`는 다음의 작은 모델이다.


```text

  battery_voltage
  gate_state
  capture_sensor
  last_observed_at
  last_command_ack
  health_flags
```

### 7.2 물체 상태

현재 v0.1은 포획되는 실제 물체 대신 `Task(id, position, kind, priority, assigned_robot, completed)`를 목적지 임무로 사용한다. 다음 `ObjectState`는 포획 기능 추가 때 도입할 목표 모델이다.

```text
  id

  last_observed_at
```

### 7.3 명령

`adapters.py`에 정의된 현재 `RobotCommand`가 JSON으로 직렬화되면 다음 형태다. `target.x`, `target.y`의 단위는 m다.

```json
{
  "robot_id": "R03",
  "sequence": 1842,
  "server_time_s": 27.415,
  "ttl_s": 0.4,
  "action": "goto",
  "target": {
    "x": 0.72,
    "y": 0.405
  },
  "target_heading_rad": -0.35,
  "max_linear_speed_mps": 0.15,
  "max_angular_speed_rps": 1.2,
  "gate": "hold",
  "emergency_stop": false
}
```

현재 `UdpRobotTransport`는 이 형식을 JSON/UDP로 보낼 수 있는 기반 코드지만 기본 실행에서 사용되지 않는다. 실물 활성화 전 `schema_version`, 세션 ID, ACK, 인증 또는 네트워크 격리 정책을 추가하는 것이 좋다.

중요 규칙:

- 로봇은 자신보다 작은 `sequence`를 무시한다.
- TTL이 지난 명령을 실행하지 않는다.
- 연결이 복구되어도 마지막 명령을 자동 재실행하지 않는다.
- `STOP`은 다른 명령보다 우선한다.
- 상태를 바꾸는 명령은 처리 결과를 ACK로 보낸다.

### 7.4 이벤트

현재 `SafetyEvent`는 종류, 메시지, 관련 로봇 ID, 시뮬레이션 시각을 가지며 최근 20개가 snapshot에 포함된다. 다음과 같은 모든 판단 이벤트의 영구 JSONL 저장은 후속 구현이다.

```json
{
  "time_s": 52.840,
  "type": "MISSION_REASSIGNED",
  "robot_id": "R04",
  "object_id": "OBJ_YELLOW_2",
  "reason": "R02_COMMUNICATION_TIMEOUT"
}
```

원시 상태를 덮어쓰는 것만으로는 “왜 R04가 갑자기 방향을 바꿨는가”를 알기 어렵다. 판단 이유를 이벤트로 남긴다.

### 8.2 현재 데모 좌표

모든 좌표는 m이며 **공식 경기 배치가 아닌 소프트웨어 검증용 placeholder**다.

출발구역:

```text
x=0.000, y=0.901, width=0.480, height=0.280
```

로봇 시작 자세:

| 로봇 | X | Y |
|---|---:|---:|
| R1 | 0.09 | 1.07 |
| R2 | 0.25 | 1.07 |
| R3 | 0.41 | 1.07 |
| R4 | 0.09 | 0.93 |
| R5 | 0.25 | 0.93 |
| R6 | 0.41 | 0.93 |

임무 목표:

| 임무 | 종류 표시 | 우선순위 | X | Y | 기본 배정 결과 |
|---|---|---:|---:|---:|---|
| T1 | medical-kit | 1 | 0.10 | 0.14 | R4 |
| T2 | patient | 2 | 0.30 | 0.18 | R1 |
| T3 | specimen | 1 | 0.49 | 0.14 | R5 |
| T4 | medical-kit | 1 | 0.68 | 0.18 | R6 |
| T5 | patient | 2 | 0.88 | 0.14 | R2 |
| T6 | specimen | 1 | 1.04 | 0.31 | R3 |

고정 장애물:

| X | Y | 폭 | 높이 |
|---:|---:|---:|---:|
| 0.50 | 0.40 | 0.14 | 0.30 |
| 0.22 | 0.50 | 0.10 | 0.12 |
| 0.84 | 0.48 | 0.10 | 0.12 |

`robot_count`가 6보다 작으면 `scenario_demo.json`의 로봇 목록 앞에서부터 해당 수만 사용하지만, 임무 6개는 모두 유지된다. 따라서 1~5대는 한 라운드가 끝날 때 남은 임무를 자동 재배정해 여러 라운드로 처리한다. 설정과 사용자 시나리오의 지원 범위는 1~8대다. 기본 시나리오에는 시작 로봇이 6대뿐이므로 7~8대를 요청하면 명확한 오류가 나며, 그 수량은 `--scenario`로 별도 시작점 파일을 제공해야 한다.

### 8.3 현재 데모의 시간 계산

현재 한 계획 틱은 다음처럼 계산된다.

```text
plan_step_s = grid_cell_m / linear_speed_mps
            = 0.02m / 0.20m/s
            = 0.10s
```

로봇은 각 계획 칸을 0.10초에 이동하도록 선형 보간된다. headless 기본 `--headless-step 0.05`는 이보다 촘촘하게 상태를 갱신한다. 계획 시간창은 경기시간과 계획 틱으로 계산하되 최대 800틱으로 제한된다. 기본값에서는 최대 80초 상당의 예약 창이다.

### 8.4 차동구동 운동학

이 절은 **후속 정밀 시뮬레이터 설계**다. 현재 v0.1은 공간-시간 A*가 만든 격자 중심점 사이를 `linear_speed_mps`로 보간하고, 이동 방향으로 `heading_rad`를 표시한다. 좌우 바퀴 속도나 가속도는 아직 계산하지 않는다.

왼쪽과 오른쪽 바퀴 선속도를 각각 `v_l`, `v_r`, 바퀴 간 거리를 `L`이라 하면 다음을 사용한다.

```text
v = (v_r + v_l) / 2
ω = (v_r - v_l) / L
x_next = x + v × cos(heading) × dt
y_next = y + v × sin(heading) × dt
heading_next = normalize(heading + ω × dt)
```

실제와 더 비슷하게 하려면 목표 속도를 즉시 적용하지 말고 최대 가속도만큼 접근시킨다. 물리 틱 `dt`가 클수록 터널링 충돌이 생길 수 있으므로 기본 물리 주기는 100Hz로 둔다.

### 8.5 결정적 실행

현재 데모에는 난수가 없고 임무·로봇을 ID 기준으로 정렬하며 비용이 같은 경우 ID로 결정하므로 반복 결과가 결정적이다. `--seed` 옵션과 무작위 고장 주입은 아직 없다. 이를 확장할 때 다음을 지킨다.

동일한 설정과 `random_seed`를 사용하면 같은 결과가 나와야 한다. 이를 위해 다음을 지킨다.

- 난수 생성기를 한 곳에서 주입
- 시스템 현재시각 대신 시뮬레이션 시계 사용
- 비동기 작업 완료 순서가 결과에 영향을 주지 않게 이벤트 순서 정의
- 객체 목록 순회 전 ID 기준 정렬
- 부동소수점 비교에 작은 허용오차 사용

버그가 발생한 seed를 로그에 저장하면 정확히 같은 상황을 재현할 수 있다.

### 8.6 충돌 처리

현재 v0.1은 매 갱신 뒤 중심 간 거리가 `safety.minimum_separation_m`, 즉 기본 0.138m보다 작아지면 충돌 수를 올리고 전체 `SAFETY_STOP`으로 전환한다. 경기장 경계를 반경 0.063m 기준으로 넘겨도 전체 안전정지하며 충돌을 물리적으로 튕겨내지는 않는다. 이 63mm 원형은 126×100mm 직사각형을 임의 자세에서 보수적으로 감싸지 않는 미검증 단순 모델이므로, 실물 안전 판정으로 해석하면 안 된다.

후속 정밀 물리에서는 다음 순서로 충돌을 처리한다.

1. 다음 자세의 외형이 벽 또는 다른 로봇과 겹치는지 예측한다.
2. 겹치면 해당 이동을 적용하지 않는다.
3. 충돌 이벤트와 두 로봇 ID를 기록한다.
4. 안전 위반 카운터를 증가시킨다.
5. 관제 로직이 정지·후퇴·재계획을 선택하게 한다.

시뮬레이터가 겹침을 조용히 보정해 주면 실제 시스템에서는 존재하지 않는 능력이 생긴다.

### 8.7 포획 모델

이 절은 후속 구현 명세다. 현재 임무는 로봇이 목적지 점에 도착하면 완료되며 물체 포획은 시뮬레이션하지 않는다.

포획은 로봇이 물체 근처에 왔다는 이유만으로 즉시 성공시키지 않는다. 최소 조건을 둔다.

- 상태가 `CAPTURE`인지
- 게이트가 열려 있는지
- 물체가 로봇 전면 포획 다각형 안인지
- 로봇과 물체의 접근 각도 오차가 허용 범위 이내인지
- 상대속도가 최대 포획속도 이내인지
- 위 조건이 일정 시간 이상 유지됐는지

포획되면 물체 자세는 로봇 포획 슬롯에 결합한다. `RELEASE`에서 게이트를 열고 후진한 뒤 로봇 외형과 물체가 분리될 때 결합을 해제한다.

### 8.8 득점 판정

이 절은 후속 구현 명세다. 현재 대시보드의 “완료 임무”는 공식 득점이 아니라 단순 목적지 도착 개수다.

완료는 중심점만 목적지 안에 있을 때가 아니라 물체 외곽 전체가 목적지 경계 안에 들어간 상태로 판정한다.

- 물체 다각형 전체가 목적지 내부
- 경계에서 설정된 여유 이상 떨어짐
- 로봇과 더 이상 접촉하지 않음
- 여러 프레임 또는 일정 시간 동안 정지
- 물체 색과 목적지가 일치

득점 로직과 계획 로직을 분리한다. 계획기는 “완료될 것으로 예상”할 수 있지만 심판 역할의 점수 모듈만 최종 완료를 결정한다.

## 9. 가상 카메라와 관측 모드

실제 부품이 없을 때도 두 단계로 비전을 시험할 수 있다.

현재 `adapters.py`에는 snapshot 공급자가 준 Python 객체를 `CameraFrame`에 담는 `SyntheticCameraSource`와, `.[vision]` 설치 시 카메라 프레임을 읽는 `OpenCVCameraSource`가 있다. 이들은 교체 가능한 입력 계약을 보여주는 기반 코드이며, 현재 관제 엔진이 이 프레임에서 로봇 위치를 검출하는 폐루프까지 연결된 것은 아니다.

### 9.1 상태 직접 관측 모드

가상 세계의 실제 좌표에 잡음과 지연을 넣어 `Observation`을 생성한다.

장점:

- 영상처리와 무관하게 계획·제어를 빠르게 검증
- 수천 번의 경기 배치 테스트가 가능
- 위치 잡음·누락·지연을 정확히 주입 가능

주의:

- 이 모드의 성공은 AprilTag와 HSV 검출 성공을 의미하지 않는다.

### 9.2 합성 영상 모드

후속 구현 항목이다. 현재 synthetic source는 실제 픽셀 이미지를 그리는 렌더러가 아니라 snapshot ground truth를 전달한다.

가상 경기장을 위에서 본 이미지로 렌더링한다.

- 로봇 위에 실제 인쇄할 예정인 고유 태그 이미지를 합성
- 빨강·노랑·초록 물체 렌더링
- 목적지, 그림자, 밝기 변화, 렌즈 왜곡, 압축 잡음 추가
- 프레임을 실제 OpenCV 인식 파이프라인에 입력

이 모드는 픽셀에서 세계 좌표까지 전체 파이프라인을 시험한다. 상태 직접 관측 모드보다 느리지만 실제 카메라 전환 전에 반드시 거쳐야 한다.

### 9.3 녹화 재생 모드

후속 구현 항목이며 현재 CLI에는 `replay` 명령이 없다.

카메라를 확보하면 실시간 장비를 계속 연결하지 않고 녹화 영상을 반복 재생한다.

- 원본 프레임 번호와 영상 시각 유지
- 실시간 속도 재생
- 0.5배, 2배, 최대속도 재생
- 특정 시각부터 시작
- 프레임 단위 진행
- 인식 결과를 별도 파일로 기록

같은 영상을 서로 다른 알고리즘 버전에 넣어 검출률과 처리시간을 비교한다.

### 9.4 카메라 입력 계약

모든 카메라 어댑터는 최소 다음을 반환한다.

```text
Frame
  image
  frame_id
  captured_at_monotonic
  received_at_monotonic
  source_id
  width
  height
  dropped_since_previous
```

`captured_at`과 `received_at`을 분리해야 실제 영상 지연을 추정할 수 있다. 드론 영상에서 촬영 시각을 알 수 없다면 해당 불확실성을 명시적으로 기록한다.

## 10. 실제 영상 인식 파이프라인

이 장 전체는 카메라를 확보한 뒤 구현할 명세다. 현재 `OpenCVCameraSource`는 프레임 취득까지만 제공하며 보정·태그 검출·HSV 분할·추적은 아직 구현하지 않았다.

### 10.1 고정 상부 카메라

권장 순서:

1. 카메라 고유 파라미터로 렌즈 왜곡 제거
2. 경기장 모서리 또는 고정 보정 마커 검출
3. 호모그래피 계산
4. 수직 시점 이미지 또는 점 좌표를 경기장 mm로 변환
5. AprilTag로 로봇 ID와 방향 검출
6. HSV로 물체 색상 분할
7. 예상 크기·형태로 후보 필터링
8. 이전 프레임의 추적 객체와 연결
9. 신뢰도와 측정 시각을 포함한 관측 생성

심사용 원본 영상에 검출 사각형이나 글자를 합성하지 않는다. 원본 녹화와 분석 화면을 분리한다.

### 10.2 움직이는 드론 카메라

드론 영상은 프레임마다 카메라 자세가 달라지므로 고정 호모그래피를 재사용하면 안 된다.

1. 경기장 네 모서리 또는 외곽 마커를 매 프레임 검출
2. 모서리 순서를 일관되게 정렬
3. 프레임별 호모그래피 계산
4. 직전 변환과 차이가 비정상적으로 크면 프레임 거부
5. 충분한 경기장 영역이 보이지 않으면 추적 불가로 표시
6. 로봇 상단 태그 높이에 의한 위치 오차 보정

드론 카메라는 보조 센서로 취급한다. 운영진 허용 여부와 실제 영상 수신 가능성이 확인되기 전까지 고정 카메라 모드를 기본안으로 유지한다.

### 10.3 태그 높이 보정

태그가 바닥보다 약 100mm 높다면 바닥 평면 호모그래피를 태그 중심에 그대로 적용했을 때 가장자리 오차가 커진다.

보정 방법 우선순위:

1. 카메라 내·외부 파라미터와 태그 높이로 바닥 접점 재투영
2. 경기장 격자 위치별 오차표를 실측해 보간
3. 카메라를 높고 수직에 가깝게 설치하여 투영 오차 자체를 감소

합성 영상에도 태그 높이 효과를 넣으면 보정 코드를 부품 전부터 검증할 수 있다.

### 10.4 색상 검출

빨강은 HSV 색상환 양 끝에 걸칠 수 있으므로 두 범위를 합친다. 고정 숫자를 영구값으로 보지 말고 실제 조명 아래 보정 도구로 저장한다.

처리 절차:

- BGR → HSV 변환
- 색별 마스크 생성
- 열기/닫기 형태학 연산
- 너무 작거나 큰 외곽선 제거
- 원통/키트 예상 종횡비와 면적 검사
- 로봇 태그·외형 마스크 영역 제외
- 연속 프레임 연결
- 신뢰도가 낮으면 임무 시작 보류

로봇 외장은 가능한 한 무채색으로 유지한다.

### 10.5 추적 손실

한 프레임 누락만으로 로봇을 분실 처리하지 않는다. 마지막 속도로 짧게 예측하되 불확실성을 증가시킨다.

예시 정책:

- 0~100ms: 예측 자세로 계속 추적
- 100~300ms: 감속, 경로 예약 여유 확대
- 300ms 초과: 해당 로봇 정지, 주변 로봇은 넓은 장애물로 취급
- 재검출: 이전 자세와 합리적인 거리인지 확인 후 수동 승인 없이도 재획득 가능
- 통신까지 끊겼다면 명시적인 새 명령 전에는 재개 금지

## 11. 세계 상태 추정

현재 엔진은 시뮬레이터 ground truth를 곧바로 `RobotState`에 반영한다. 아래 시간 정렬·필터·가림 처리는 영상 입력을 폐루프로 연결할 때 추가할 명세다.

관측값과 실제 상태를 같은 객체로 사용하지 않는다. 관측에는 잡음과 지연이 있고, 계획기는 현재 시각의 추정 상태를 필요로 한다.

### 11.1 시간 정렬

수신 시각이 아니라 촬영 시각에 측정을 적용한다. 영상이 150ms 늦게 도착했는데 현재 위치로 간주하면 빠르게 움직이는 로봇의 위치가 계속 뒤처진다.

간단한 방법:

1. 측정 자세와 측정 시각 저장
2. 최근 속도 추정
3. 현재 시각까지 짧게 전진 예측
4. 지연이 너무 크면 해당 관측을 거부하거나 감속

### 11.2 필터

첫 구현은 복잡한 확장 칼만 필터보다 알파-베타 필터로 시작해도 충분하다.

- 위치 측정과 예측을 가중 결합
- 속도를 측정 잔차로 보정
- 각도는 원형 값으로 별도 처리
- 태그 신뢰도에 따라 가중치 조절

필터는 급격한 오류를 숨기는 도구가 아니다. 물리적으로 불가능한 점프는 먼저 이상치로 제거한다.

### 11.3 물체 가림

물체가 로봇 내부로 들어가면 카메라에서 보이지 않을 수 있다.

- `VERIFY_CAPTURE`가 성공하면 물체를 로봇에 결합한 상태로 추정
- 결합된 물체는 카메라 미검출을 `LOST`로 바꾸지 않음
- 로봇 포획 센서와 영상 판정을 함께 기록
- 배출 뒤 예상 위치 근처에서 재검출
- 일정 시간 재검출되지 않으면 완료가 아니라 `UNKNOWN`으로 둠

## 12. 임무 배정

현재 `assign_tasks()`는 최대 8개의 로봇/미완료 임무에 대해 순열을 검사하여 정확한 1:1 최소비용 배정을 만든다. 기본 비용은 `로봇-목표 거리 / max(1, priority)`이고, 비용이 같으면 ID로 결정한다. 아래의 포획·운반시간·성공확률 비용은 후속 확장이다.

### 12.1 임무 단위

임무 하나는 단순히 “물체로 이동”이 아니라 다음 전체 사이클이다.

```text
물체 접근 → 정렬 → 포획 → 확인 → 목적지 운반 → 배출 → 완료 확인 → 대기점 이동
```

### 12.2 비용함수

모든 물체의 점수가 같더라도 가까운 물체만 고르면 좁은 길에서 병목이 생길 수 있다. 로봇 `r`이 물체 `o`를 처리하는 비용 예시는 다음과 같다.

```text
cost(r, o) =
  물체까지 예상 이동시간
  + 목적지까지 예상 운반시간
  + 포획/배출 평균시간
  + 예약 충돌 대기시간
  + 역할 부적합 벌점
  + 낮은 성공확률 벌점
  + 낮은 배터리 벌점
```

선택 기준을 기대 효율로 표현할 수도 있다.

```text
expected_efficiency = score × success_probability / expected_time
```

### 12.3 초기 배정과 재배정

6대에서 매 틱 전체 배정을 바꾸면 로봇이 목표를 자주 바꾸게 된다.

- 경기 시작 시 전체 배정
- 새 물체가 확실하게 나타날 때
- 로봇 고장 또는 타임아웃
- 포획 반복 실패
- 현재 임무 예상 완료시간이 남은 시간을 초과
- 목표가 이미 다른 로봇에 의해 완료

이때만 재배정한다. 이미 포획한 물체는 원칙적으로 다른 로봇에 넘기지 않는다.

### 12.4 배정 알고리즘

첫 구현에서는 다음 순서가 충분하다.

1. 처리 가능한 로봇-물체 쌍의 비용행렬 계산
2. 역할·게이트 크기 등 불가능한 쌍은 무한대
3. 헝가리안 알고리즘 또는 작은 규모 완전탐색으로 총비용 최소화. 현재 로봇과 임무가 모두 8개 이하이면 완전탐색을 사용하고, 어느 한쪽이라도 8개를 넘으면 결정적 greedy fallback을 사용한다. 따라서 6대·9개 이상 임무도 실행되지만 전역 최적임을 보장하지는 않는다.
4. 비용 개선이 작은 경우 기존 배정 유지하는 히스테리시스 적용
5. 배정 결과를 예약 상태로 원자적으로 갱신

로봇과 물체가 각각 6개 정도면 알고리즘 계산량보다 비용 추정의 정확성이 더 중요하다.

## 13. 경로 계획

현재 구현은 20mm 격자, 4방향 이동과 제자리 대기, Manhattan 휴리스틱을 사용하는 공간-시간 A*다. 벽·팽창된 고정 사각형 장애물과 우선 계획된 로봇의 시공간 예약을 회피한다. 고정 격자의 연결 성분을 계획기 생성 시 미리 계산하므로, 벽으로 완전히 분리된 목표는 긴 시공간 탐색 전에 즉시 거부한다. 이미 예약된 두 선형 이동은 tick 중간의 연속시간 최소거리까지 검사한다. 아직 계획되지 않은 로봇의 시작점을 영구 정적 장애물로 막지는 않으므로, 실제 동적 재계획 단계에서는 최신 로봇 외형을 별도 점유 입력으로 추가해야 한다. 별도 경로 평활화와 연속 곡률 제어도 아직 없다.

### 13.1 점유 격자

현재 경기장 m 좌표를 20mm 격자로 나눈다. 실물 외형과 서버 성능을 확인한 뒤 10mm·20mm·25mm 등의 계산시간과 경로 품질을 비교할 수 있다.

장애물:

- 경기장 벽
- 고정 구조물
- 운반하지 않는 물체
- 완료된 득점 물체와 보호 여유
- 다른 로봇의 현재 외형
- 다른 로봇의 시간 예약

### 13.2 장애물 팽창

로봇 중심의 경로를 찾으려면 장애물을 로봇 외접반경과 안전여유만큼 팽창시킨다.

```text
inflation = robot_circumscribed_radius + safety_margin + localization_uncertainty
```

운반 중인 물체가 로봇 밖으로 돌출된다면 운반 상태의 외형을 별도로 사용한다.

### 13.3 A*

현재 4방향 격자의 기본 휴리스틱은 Manhattan 거리다. 유클리드 거리나 octile distance는 대각선 이동을 추가하는 후속 설계에서 이동 규칙과 함께 다시 선택한다.

비용에 포함할 수 있는 항목:

- 이동거리
- 회전 예상량
- 벽과 가까운 칸의 벌점
- 좁은 통로 벌점
- 다른 로봇 예약 근처 벌점
- 미끄러운 것으로 측정된 영역 벌점

휴리스틱이 실제 이동비용을 과대평가하면 최단경로 보장이 깨질 수 있다. 최단성보다 안정적인 여유 경로가 중요하다면 가중 A*임을 명시하고 사용한다.

### 13.4 경로 평활화

후속 구현 항목이다. 현재 화면의 경로는 20mm 격자 중심점을 그대로 잇는다.

A* 격자 경로를 그대로 따라가면 불필요한 작은 회전이 많다.

1. 현재 점에서 더 먼 경로점까지 직선 충돌 검사를 한다.
2. 충돌이 없으면 중간 점들을 제거한다.
3. 회전이 큰 구간 앞에 감속 지점을 둔다.
4. 최종 접근 구간은 물체 중심과 입구 방향에 맞게 별도 생성한다.

평활화 후 반드시 연속 선분 전체를 다시 충돌 검사한다.

### 13.5 재계획 조건

현재는 초기화와 사용자의 `/api/mission/replan` 요청뿐 아니라 한 라운드의 배정 로봇이 모두 도착·정지하고 미완료 임무가 남았을 때도 전체 재배정·재계획한다. 로봇 수보다 임무가 많으면 이 사건 기반 동작으로 여러 라운드를 수행한다. 남은 배정 로봇이 전부 도달 불가이면 `PAUSED`로 전환하고 `planner_stalled` 이벤트를 남겨 같은 실패를 매 tick 반복하지 않는다. 아래의 위치·지연·동적 장애물 기반 자동 재계획은 후속 항목이다.

- 경로에서 횡방향 오차 30mm 이상
- 예약된 시간보다 일정 수준 지연
- 앞 구간에 새 장애물 등장
- 목표 물체가 이동
- 추적 불확실성 증가
- 로봇이 0.5~1초 이상 전진하지 못함

재계획 폭주를 막기 위해 최소 재계획 간격과 쿨다운을 둔다.

## 14. 6대 충돌 회피

현재 `MultiRobotPlanner`는 목표까지 가까운 로봇, 그다음 ID 순서로 우선 계획하고 각 경로를 `ReservationTable`에 기록한다. 같은 틱의 근접 정점과 반대 방향 간선 교환을 막고, 먼저 계획된 로봇의 도착점은 계획 시간창 끝까지 점유한다. 대기 행동 `(0, 0)`도 탐색한다. 아래의 임무 기반 동적 우선순위, 명시적 대기점, 교착 복구는 후속 확장이다.

### 14.1 단순 거리 정지만으로 부족한 이유

두 로봇이 가까워진 후 둘 다 정지하면 좁은 통로에서 서로 양보하지 못한다. 충돌 회피는 경로를 만들 때 미래 시간을 함께 고려해야 한다.

### 14.2 우선순위

기본 우선순위 예시:

1. 비상정지 또는 고장 로봇 주변 보호
2. 득점 물체를 운반 중인 로봇
3. 목적지 또는 배출 지점에 가까운 로봇
4. 좁은 구역을 이미 통과 중인 로봇
5. 나머지는 임무 생성 시각과 ID로 결정

우선순위가 같을 때 ID 등 결정적 규칙을 사용해야 매 틱 양보 대상이 뒤바뀌지 않는다.

### 14.3 시간 예약 테이블

각 경로를 100ms 정도의 시간 구간으로 나눠 로봇 외형이 점유할 공간을 예약한다.

```text
(time_slot, grid_cell) -> robot_id
```

새 경로가 기존 예약과 겹치면 다음 중 하나를 선택한다.

- 출발 시각 지연
- 대기점 삽입
- 다른 공간 경로 탐색
- 낮은 우선순위 로봇 경로 재계산

경로점 하나만 예약하지 말고 로봇 외형과 불확실성만큼 주변 칸도 예약한다.

### 14.4 교차 충돌

같은 시간에 같은 칸을 점유하는 충돌뿐 아니라 두 로봇이 칸 A와 B를 서로 맞바꾸는 edge conflict도 막는다.

```text
R1: A -> B
R2: B -> A
```

이 경우 한 로봇이 기다리도록 한다.

### 14.5 대기점과 일방통행

경기장에 미리 안전한 대기점을 지정하면 6대 교착 해결이 쉬워진다.

- 목적지 바로 앞을 대기점으로 사용하지 않음
- 다른 로봇의 주요 통로를 막지 않음
- 로봇 전체 외형이 들어갈 여유 확보
- 좁은 구간은 한 방향 또는 토큰 기반 진입

### 14.6 교착상태 탐지와 해소

교착 판단 예시:

- 이동 명령 중인데 2초 이상 위치 변화가 거의 없음
- 서로의 예약 때문에 2초 이상 모두 대기
- 재계획 결과가 계속 동일한 충돌을 생성

해소 순서:

1. 우선순위가 낮은 로봇의 임무 일시정지
2. 가장 가까운 안전 대기점으로 후퇴 경로 생성
3. 고우선 로봇의 통과 확인
4. 예약을 새로 생성하고 명시적 재개
5. 실패하면 관련 로봇 모두 정지하고 해당 구역을 임시 장애물 처리

무작위 방향으로 후진하게 하지 않는다.

## 15. 경로 추종과 가상 로봇 제어

현재 엔진은 `grid_cell_m / linear_speed_mps`를 한 격자 이동시간으로 보고 계획 경로의 인접 점 사이를 선형 보간한다. 실제 제어기, 가속 제한, Pure Pursuit는 아직 없다. 이 장의 나머지는 실물에 가까운 후속 제어기 명세다.

### 15.1 경로 추종기

첫 구현은 Pure Pursuit 또는 단순 자세 제어기를 사용할 수 있다.

- 현재 경로에서 가장 가까운 점 찾기
- 속도에 따른 look-ahead 거리 선택
- 앞의 목표점으로 곡률 계산
- 선속도·각속도로 변환
- 로봇 한계와 안전감시 결과로 제한

최종 포획 20cm, 배출, 좁은 통로에서는 look-ahead와 속도를 줄인다.

### 15.2 속도 프로파일

- 직선 여유 구간: 0.2~0.3m/s에서 시작
- 큰 회전 전: 미리 감속
- 물체 200mm 전: 접근 모드
- 최종 포획: 0.05~0.1m/s
- 배출: 더 낮은 속도
- 위치 신뢰도 저하: 감속
- 충돌 예상: 정지

시뮬레이터에서도 순간적으로 최대속도를 적용하지 말고 가속 제한을 적용한다.

### 15.3 도착 판정

위치와 각도 조건을 모두 연속된 여러 틱 동안 만족해야 한다.

예시:

- 일반 웨이포인트: 30mm 이내
- 물체 접근 자세: 15mm, 5도 이내
- 목적지 배출 자세: 기구 시험값에 맞춤
- 속도도 충분히 낮아야 도착으로 인정

한 틱의 잡음만으로 상태가 진행되지 않게 한다.

## 16. 임무 상태기계

현재 상태는 경기 전체 `READY/RUNNING/PAUSED/COMPLETED/TIMEOUT/SAFETY_STOP`과 로봇 `IDLE/WAITING/MOVING/ARRIVED/STOPPED/LOST`까지 구현돼 있다. 아래 포획 상태기계는 후속 구현 명세다.

권장 상태와 전이 조건은 다음과 같다.

### `BOOT`

- 설정과 로봇 ID 검증
- 통신 또는 가상 어댑터 준비
- 위치 관측 확보
- 명시적 경기 시작 전에는 모터 명령 금지

### `IDLE`

- 안전한 대기 자세 유지
- 임무 배정 대기

### `RESERVED`

- 물체를 원자적으로 예약
- 접근 자세와 경로 생성
- 실패하면 예약 해제

### `NAVIGATE`

- 물체 전방 접근점까지 이동
- 목표가 움직이거나 추적을 잃으면 정지·재계획

### `ALIGN`

- 물체와 포획 입구 중심을 저속으로 정렬
- 위치·각도·신뢰도 조건을 모두 확인

### `OPEN_GATE`

- 게이트 열기 명령
- 실제 또는 가상 피드백 확인
- 타임아웃 시 재시도 후 오류

### `CAPTURE`

- 제한된 거리와 속도로 직진
- 충돌 또는 센서 이상 시 즉시 정지

### `VERIFY_CAPTURE`

- 내부 센서, 색 센서, 영상 상태를 조합
- 확인 실패 시 정해진 횟수만 재시도

### `CLOSE_GATE`

- 물체 이탈 방지를 위해 게이트 닫기
- 닫힘 피드백 확인

### `TRANSPORT`

- 운반 로봇 우선권 부여
- 운반 외형으로 경로와 예약 재생성

### `RELEASE`

- 목적지 내부에서 게이트 열기
- 천천히 후진

### `VERIFY_RELEASE`

- 물체와 로봇 분리
- 물체 전체가 목적지 안에 있고 정지했는지 확인

### `RETRY`

- 실패 원인별로 한정된 복구 수행
- 같은 동작을 무한 반복하지 않음

### `ABANDON`

- 임무를 포기하고 안전 지점으로 이동
- 남은 시간과 다른 로봇 상태에 따라 재배정

### `SAFE_STOP`

- 모든 운동과 서보의 안전 상태 적용
- 오류 원인이 사라져도 자동 재개하지 않음
- 중앙 관제의 명시적 `RESUME` 또는 새 임무 필요

모든 상태에는 최대 체류시간을 둔다. 예를 들어 `OPEN_GATE`에서 피드백이 오지 않으면 영원히 기다리지 않는다.

## 17. 경기 관리자

현재 웹/API는 시작, 일시정지, 초기화, 재계획, 긴급정지를 제공한다. 모든 임무 도착 시 `COMPLETED`, 120초 경과 시 `TIMEOUT`과 전체 정지를 적용한다. 108초 신규 임무 제한은 포획형 다단계 임무를 추가할 때 구현해야 한다.

### 17.1 시작 전

- 설정 유효성 검사
- 6대 로봇의 초기 위치가 서로 겹치지 않는지 확인
- 모든 로봇 상태와 통신 준비 확인
- 카메라 또는 가상 관측 안정성 확인
- 로그 디렉터리와 저장공간 확인
- 시뮬레이션 seed 기록

### 17.2 시작

하나의 시작 이벤트가 다음을 같은 기준시각으로 시작시킨다.

- 120초 경기 시계
- 임무 배정
- 로봇 상태기계
- 점수 기록
- 원본 영상 녹화 또는 시뮬레이션 이벤트 기록

여러 프로세스를 사람이 따로 클릭해 시작하지 않도록 한다.

### 17.3 종료 전략

- 약 108초부터 신규 임무 금지
- 이미 포획한 물체는 남은 시간과 예상 성공률로 마무리 여부 판단
- 120초에 모든 로봇 정지
- 득점 물체를 건드리지 않는 안전 자세 유지
- 최종 상태와 통계 저장
- 로그 flush 완료 후 프로세스 종료

정확한 신규 임무 제한 시각은 반복시험 결과로 105~110초 범위에서 조정한다.

## 18. 안전감시기

현재 안전검사는 경기장 경계 이탈과 두 로봇의 중심거리가 설정된 최소거리(기본 0.138m)보다 작은지를 매 simulation step마다 검사하여 전체 안전정지한다. 이때 반경 63mm 원형은 실제 126×100mm 직사각형의 임의 자세에 보수적이지 않은 미검증 단순 모델이다. 추적 timeout, 명령 TTL, 예측 정지거리 등은 데이터 계약 또는 설정만 있으며 아직 폐루프로 연결되지 않았다. 아래는 계획 결과를 그대로 신뢰하지 않는 후속 안전감시 명세다.

### 18.1 정지 조건

- 위치 관측이 제한시간 이상 없음
- 명령 또는 상태 데이터가 너무 오래됨
- 예측 시간창 내 다른 로봇과 충돌
- 로봇 외형이 경기장 경계에 닿을 가능성
- 현재 속도에서 정지거리가 남은 여유보다 큼
- 잘못된 명령 번호 또는 만료된 명령
- 비정상 자세 점프
- 제어 루프 주기가 심하게 지연
- 운영자의 비상정지 입력

### 18.2 감속 조건

- 태그 신뢰도 감소
- 좁은 통로 또는 목적지 근처
- 다른 로봇 예약 경계 근처
- 영상 지연 증가
- 계획 경로와 실제 위치 오차 증가

### 18.3 워치독

각 구성요소의 heartbeat를 감시한다.

| 구성요소 | 예시 제한 | 실패 시 동작 |
|---|---:|---|
| 카메라 프레임 | 300ms | 전체 또는 관련 로봇 정지 |
| 로봇 telemetry | 500ms | 해당 로봇 고정 장애물 처리 |
| 계획기 | 500ms | 기존 짧은 명령 만료 후 정지 |
| 관제 프로세스 | 로봇 로컬 500ms | 모든 실물 로봇 로컬 정지 |
| 드론 제어 링크 | 실측 후 결정 | 중립·체공 또는 안전착륙 |

## 19. 통신 계층

현재 기본 실행은 네트워크로 로봇 명령을 전송하지 않는다. `DryRunTransport`가 안전 기본값이고, `UdpRobotTransport`는 명령 JSON을 지정 endpoint에 보내는 기반 클래스일 뿐 현재 CLI로 활성화되지 않는다. telemetry 수신·ACK·세션 관리·인증도 후속 구현이다.

### 19.1 시뮬레이션 전송

프로세스 내부 큐라도 실제 통신의 특성을 흉내 낼 수 있어야 한다.

- 지연
- 패킷 손실
- 중복
- 순서 뒤바뀜
- 연결 끊김
- 대역폭 제한

이 기능은 실제 UDP 연결 전에 TTL과 sequence 처리 버그를 잡는 데 중요하다.

### 19.2 실물 권장 구조

- 서버→로봇: UDP 고주기 명령 또는 신뢰성 계층을 둔 경량 프로토콜
- 로봇→서버: telemetry와 ACK
- 설정·진단: TCP/WebSocket 또는 직렬
- 긴급정지: 반복 송신 + 로봇 로컬 타임아웃

UDP를 사용한다면 손실될 수 있음을 전제로 최신 상태를 반복 전송하고 명령을 짧게 유효하게 한다. TCP만 사용하면 재전송 대기 때문에 오래된 이동 명령이 뒤늦게 적용될 수 있으므로 지연 정책을 분명히 해야 한다.

### 19.3 세션 시작

로봇 부팅 때 임의 또는 증가하는 `session_id`를 사용한다. 재부팅 후 이전 세션의 지연 패킷이 적용되지 않게 한다.

### 19.4 동기화

로봇과 서버의 절대시계가 완벽히 같을 필요는 없지만 다음은 필요하다.

- 왕복시간 측정
- 서버 명령 TTL 해석 방식 정의
- 로봇 로컬 수신시각 기준 타임아웃
- 로그에서 서버와 로봇 이벤트를 비교할 오프셋 추정

## 20. 로그와 리플레이

현재 `JsonlLogger` 기반 클래스는 있으나 `SimulationEngine`의 전체 실행을 영구 기록하거나 다시 재생하는 CLI에는 아직 연결되지 않았다. 대시보드 snapshot에는 최근 안전 이벤트 최대 20개만 포함된다. 아래는 다음 단계에서 구현할 로그 계약이다.

### 20.1 반드시 남길 데이터

- 실행 설정 전체 사본
- Git 커밋 ID
- random seed
- 경기 시작 기준시각
- 매 관측의 위치·신뢰도·지연
- 필터가 만든 추정 상태
- 임무 배정과 비용
- 경로와 예약 버전
- 로봇별 상태 전이와 이유
- 전송 명령과 ACK
- 안전감시 개입
- 충돌, 경계 위반, 추적 손실
- 최종 점수와 물체별 결과
- 루프별 처리시간 통계

### 20.2 파일 형식

- 사건: JSON Lines
- 고주기 수치: CSV, Parquet 또는 압축 바이너리
- 설정: 현재 JSON 원본 복사
- 원본 영상: 별도 파일
- 시각화 영상: 심사용 원본과 구분된 별도 파일

### 20.3 리플레이 단계

1. 로그의 설정과 Git 버전을 확인한다.
2. 기록된 관측을 원래 시각 순서로 주입한다.
3. 계획기 출력이 기록과 같은지 비교한다.
4. 고친 알고리즘으로 다시 돌려 점수와 안전 위반을 비교한다.
5. 차이가 처음 발생한 틱을 출력한다.

최종 화면 녹화만 남기면 문제 원인을 찾을 수 없다.

## 21. 관제 화면

현재 관제 화면은 별도 브라우저에서 동작하며 약 200ms마다 로컬 API를 폴링한다. Python 엔진은 별도 simulation 스레드로 실행되므로 브라우저 렌더링이 제어 루프를 직접 막지 않는다.

현재 화면에 구현된 항목:

- 경기장, 480×280mm 출발구역, 고정 장애물
- 가상 임무 목표와 완료 색상
- 로봇 6대의 ID, 외형, 방향, 예약 경로
- 경기 상태와 남은 시간
- 완료 임무, 계획시간, 재계획, 충돌 수
- 로봇 상태·임무·가상 배터리
- 안전 이벤트와 hardware-unverified 경고
- 시작, 일시정지, 초기화, 재계획, 긴급정지

## 24. 현재 단계 합격 기준

현재 v0.1에서 자동 검증하는 합격 기준:

| 항목 | 현재 자동 검증 |
|---|---|
| 6대 데모 | 모든 가상 임무 도착, 충돌 0회 |
| 다중 라운드 | 사용자 시나리오의 1대가 임무 2개를 자동 재배정으로 모두 처리 |
| 경로 충돌 | 시험된 경로에서 정점·맞교환·tick 중간 최소거리 충돌 없음, 목표 장기 점유 |
| 정지 로봇 | 무임무·미해결 로봇을 고정 예약하고 필요한 앞선 경로를 재작성 |
| 경로 없음 | 완전히 막힌 목표를 정적 연결성 사전검사로 조기 거부하고 재계획 폭주 없이 일시정지 |

| 로컬 API | 상태 조회, 시작, 일시정지 응답 검증 |
| 패키지 데이터 | 설치본용 기본 설정·시나리오가 소스 기본값과 일치하고 fallback 가능 |

아직 구현하지 않은 비전·실물·포획까지 포함한 부품 없는 확장 단계의 목표 기준:

| 항목 | 기준 |
|---|---|
| 결정성 | 같은 seed와 설정으로 결과 및 주요 이벤트 순서 일치 |
| 6대 동시운용 | 120초 완주, 예외·교착으로 프로세스 중단 없음 |
| 충돌 | 정상 시나리오에서 로봇 간 물리 충돌 0회 |
| 경계 | 경기장 이탈 0회 |
| 명령 안전 | TTL 400ms, 명령 단절 500ms 이내 로봇 정지 |
| 관측 안전 | 위치 추적 상실 시 해당 로봇 정지 |
| 종료 | 120초에 모든 로봇 정지 |
| 임무 무결성 | 물체 중복 예약 0회 |
| 로그 | 모든 상태 전이와 안전 개입 이유 기록 |
| 성능 | 중앙 루프 p99가 정해진 주기 이내 |

다음 단계의 목표값:

- 위치오차 15mm 이하
- 방향오차 5도 이하
- 영상→명령 종단 지연 200ms 이하
- 포획·배출 10회 중 9회 이상
- 전체 경기 10회 중 8회 이상 목표점수

뒤의 값들은 실제 장비로 다시 검증해야 한다.

## 25. 구현 순서

현재 v0.1은 단계 0의 실행 뼈대를 **부분 구현**했고, 단계 2·3의 전역 계획 핵심과 단계 5의 단순 120초 관리자까지 먼저 구현한 상태다. 단계 0의 random seed 주입과 구조화 영구 로그는 아직 남아 있다. 정밀 운동학, 포획, 관측, 고장주입은 아래 순서대로 보강한다.

### 단계 0: 실행 뼈대 — 부분 구현

- **구현됨:** 설정·시나리오 로더와 검증, 공통 데이터 모델, 단조증가 시계, 120초 제한 루프
- **미구현:** 외부에서 지정 가능한 random seed, 엔진 전체의 구조화 영구 로그와 replay

완료 조건: 같은 설정을 두 번 실행했을 때 동일한 시작·종료 로그가 생성된다.

### 단계 1: 로봇 1대 물리 — 현재 단순 경로 보간, 정밀 물리는 후속

- 차동구동 운동학
- 가속·속도 제한
- 경기장 경계 충돌
- 목표 자세 제어

완료 조건: 여러 시작자세에서 목표 30mm 이내에 정지한다.

### 단계 2: A*와 경로 추종 — 공간-시간 A* 구현, 평활화·실제 추종은 후속

- 점유 격자
- 로봇 크기 기반 팽창
- A*
- 평활화
- 웨이포인트 추종

완료 조건: 정적 장애물을 건드리지 않고 목표에 도착한다.

### 단계 3: 6대와 예약 — 기본 예약 구현, 동적 교착 복구는 후속

- 로봇 ID 6개
- 시간 예약
- 우선순위와 대기점
- 교착 탐지

완료 조건: 교차·맞교환 시나리오에서 충돌 없이 모두 도착한다.

### 단계 4: 물체와 상태기계 — 후속

- 포획 영역
- 게이트 가상 상태
- 포획·운반·배출
- 목적지 완료 판정

### 단계 5: 임무 배정과 경기 관리자 — 단순 목적지 배정·120초 종료 구현, 다단계 임무는 후속

### 단계 7: 합성 영상 — 어댑터 계약만 존재, 렌더링은 후속

### 단계 8: 고정 카메라 — 프레임 취득 어댑터만 존재, 인식은 후속

- 실시간 프레임 어댑터
- 렌즈/경기장 보정
- 로봇·물체 검출
- 지연 측정

완료 조건: 녹화 영상과 실시간 영상에서 합격 기준을 달성한다.

- 통신 계약 구현
- 엔코더 PID
- 로컬 TTL 정지
- 게이트·센서

완료 조건: 서버 목표로 주행하고 링크 단절 500ms 이내 정지한다.

### 단계 10: 실물 다중 로봇 — 후속

- 2대부터 시작
- 3대로 확대
- 6대는 공간과 성공률 데이터가 허용할 때만 확대

소프트웨어 기본값이 6대라는 이유로 실전에도 반드시 6대를 쓰지는 않는다.

### 단계 11: 드론 옵션 — 기본적으로 강제 비활성

- 운영진 서면 허용

- 조종기 자동화 독립시험
- 움직이는 카메라 보정
- 실패 시 고정 카메라 복귀

드론은 마지막 옵션이다. 고정 카메라 기반 전체 사이클보다 먼저 구현하지 않는다.

## 26. ESP32 연동 설계

### 26.1 서버 코드가 기대할 어댑터

현재 `RobotTransport` 프로토콜은 다음의 최소 출력 계약이다.

```text
RobotTransport
  send(command)
  close()
```

`DryRunTransport`와 `UdpRobotTransport`가 이 계약을 구현한다. telemetry 폐루프를 연결할 때 다음을 별도 프로토콜 또는 확장 인터페이스로 추가한다.

```text
connect()
read_telemetry()
emergency_stop()
health()
```

계획기와 상태기계는 이 객체가 가상인지 UDP인지 알지 못한다.

### 26.2 ESP32 펌웨어 책임

- 고유 로봇 ID와 펌웨어 버전 보고
- 모터 방향과 엔코더 부호 검증
- 목표 선속도·각속도를 좌우 바퀴 속도로 변환
- 각 바퀴 PID
- 가속도 제한
- 서보 상태기계
- 포획 센서·색 센서 읽기
- 배터리 전압 보고
- 명령 sequence와 TTL 검사
- 링크 단절 자동정지
- 부팅 직후 기본 정지

### 26.3 실제 파라미터 보정

로봇별로 다음 값을 따로 저장한다.

- 좌우 바퀴 유효 지름
- 바퀴 간 거리
- 엔코더 펄스/회전
- 좌우 모터 feed-forward
- PID 계수
- 최대 안전속도
- 정지거리
- 서보 열린/닫힌 펄스

같은 부품이라도 오차가 있으므로 한 값을 6대에 무조건 복사하지 않는다.

## 27. 고정 카메라 연동 절차

1. 1080p/30fps USB 또는 네트워크 카메라를 수직에 가깝게 고정한다.
2. 자동초점, 자동노출, 자동화이트밸런스를 안정값으로 고정한다.
3. 체커보드로 렌즈 보정값을 저장한다.
4. 경기장 네 모서리 또는 허용된 외곽 마커의 mm 좌표를 측정한다.
5. 화면 전체가 아닌 실제 경기장 평면의 호모그래피를 계산한다.
6. 여러 위치에 기준점을 놓고 mm 변환 오차를 측정한다.
7. 태그 높이 보정을 적용한다.
8. 조명 조건별 태그 검출률과 HSV 색 검출률을 측정한다.
9. 프레임 촬영부터 명령 생성까지 지연을 기록한다.
10. 카메라 케이블 분리 시험으로 자동정지를 확인한다.

심사용 상부 영상의 제어 겸용이 허용되는지 운영진에게 확인한다. 허용되지 않거나 실시간 출력이 없다면 제어 전용 상부 카메라를 별도로 둔다.

## 28. 드론 연동 절차

드론 관련 규정과 안전 답변을 서면으로 받은 뒤 진행한다.

### 28.1 영상 수신을 먼저 검증한다

- 스마트폰 앱 없이 PC에서 스트림 수신 가능한지
- 스트림 주소·프로토콜
- 실제 해상도와 fps
- 종단 지연
- 끊김 후 재연결
- PC가 드론 AP와 로봇망에 동시에 연결 가능한지

여기서 실패하면 조종기 개조에 시간을 쓰기 전에 고정 카메라안으로 복귀한다.

### 28.2 순정 조종기 자동화

110g급 완구 드론에 라즈베리파이를 싣기보다 순정 RF 조종기를 ESP32가 전기적으로 자동 조작하는 방향이다.

- 각 스틱 축의 중립·최소·최대 전압 실측
- 한 축씩 디지털 가변저항 또는 DAC 방식 검증
- 이륙·착륙 버튼은 적절한 절연 스위칭
- 수동/자동 전환
- 독립 비상착륙·정지
- 프로펠러 제거 상태에서 출력 범위 시험
- 넓고 안전한 공간에서 이륙 시험

회로를 실제로 보기 전에는 조종기 전압이나 부품 값을 추정해 확정하지 않는다.

### 28.3 드론 상태기계

```text
DISARMED
→ PRECHECK
→ TAKEOFF
→ MOVE_TO_OBSERVE
→ STABILIZE
→ OBSERVE
→ LAND
→ DISARMED
```

실패 전이는 `SAFE_LAND` 또는 기체가 지원하는 가장 안전한 동작으로 간다.

### 28.4 드론 실패 시 시스템 동작

- 영상만 실패: 고정 상부 카메라 관측으로 전환
- 드론 자세 불안정: 지상 로봇 정지 후 안전착륙
- 조종 링크 실패: 사전에 시험한 failsafe 적용
- 네트워크 경로 충돌: 드론망과 로봇망 인터페이스를 명시적으로 바인딩

드론을 쓰더라도 심사용 고정 카메라 2대는 별도 유지한다.

## 30. 부품이 생긴 뒤의 교체 순서

한꺼번에 시뮬레이터를 실물 6대로 바꾸지 않는다. 현재의 `SyntheticCameraSource`, `OpenCVCameraSource`, `DryRunTransport`, `UdpRobotTransport`는 독립 경계 클래스이며 `SimulationEngine`이 프레임을 소비하거나 `RobotCommand`를 발행하는 폐루프에는 연결되어 있지 않다. 따라서 어댑터 이름만 바꾸는 작업이 아니라 다음 통합 구현이 필요하다.

1. `SyntheticCameraSource`의 `CameraFrame`을 공통 관측·상태 갱신기로 연결
2. 경로 추종 결과를 sequence·TTL이 있는 `RobotCommand`로 만드는 제어 계층 구현
3. 명령을 `DryRunTransport`에 보내 관측→계획→명령 폐루프와 timeout을 자동시험
4. 녹화 영상 입력을 거쳐 `OpenCVCameraSource`의 고정 실시간 카메라로 전환
5. 검증된 `UdpRobotTransport`와 ESP32 한 대를 HIL로 연결하되 실제 출력은 명시적 opt-in
6. 나머지 로봇은 가상으로 유지하는 혼합 모드를 구현하고 실제 1대의 통신·안전·주행 보정
7. 실제 2대, 그다음 3대로 충돌 회피와 전체 임무를 반복 검증
8. 공간과 반복성 데이터가 좋을 때만 최대 6대로 확대
9. 운영진 허용과 failsafe 검증 뒤에만 선택적으로 드론 카메라·조종기 계층 추가

혼합 모드를 지원하면 로봇 한 대만 도착해도 중앙 시스템 전체를 시험할 수 있다.

## 31. 현실과 시뮬레이션의 차이를 줄이는 방법

### 31.1 시스템 식별

실물 로봇에서 짧은 명령을 실행하고 다음을 기록한다.

- 명령 속도 대 실제 속도
- 가속과 감속 시간
- 직진 시 좌우 편차
- 제자리 회전 반경과 오차
- 정지거리
- 배터리 전압에 따른 변화

측정값으로 시뮬레이터 파라미터를 갱신한다.

### 31.2 도메인 랜덤화

한 개의 완벽한 가상 로봇에만 맞추지 않는다.

- 바퀴 지름 ±오차
- 좌우 모터 출력 편차
- 마찰과 미끄러짐
- 카메라 위치 잡음
- 지연과 손실
- 포획 성공조건

범위를 무작위로 바꿔도 전략이 안전하면 실물 전환 가능성이 높아진다. 단, 무작위 범위는 실측 뒤 현실적인 값으로 수정한다.

### 31.3 시뮬레이션이 대신할 수 없는 시험

- 실제 프로펠러 바람이 경기 물체에 미치는 영향
- 포획기 형상과 재질 마찰
- 배터리·모터 발열
- Wi-Fi 간섭
- 카메라의 실제 압축과 자동노출
- 바닥 이음새와 3D 출력 오차
- 비상정지의 물리적 신뢰성

이 항목은 반드시 실물 반복시험이 필요하다.

## 32. 문제 해결 가이드

### 로봇이 목표 근처에서 빙빙 돈다

- 각도 오차 정규화 확인
- 도착 위치와 방향 허용오차 분리
- 최종 회전 시 선속도 제한
- look-ahead가 너무 작은지 확인
- 제어 주기와 `dt` 단위 확인

### A* 경로는 있는데 로봇이 통과하지 못한다

- 장애물 팽창에 실제 바퀴 포함 폭을 사용했는지
- 평활화 선분을 다시 충돌 검사했는지
- 운반 상태 외형이 더 커지는지
- 격자 대각선 코너 통과를 잘못 허용했는지

### 6대가 계속 양보만 한다

- 우선순위가 틱마다 바뀌지 않는지
- 대기점이 실제 통로를 막는지
- edge conflict 검사가 있는지
- 예약 시간창이 너무 짧거나 긴지
- 교착 타이머와 후퇴 규칙이 있는지

### 물체가 중복 배정된다

- 예약 갱신을 한 번의 원자적 연산으로 하는지
- 상태 복사본에서 따로 배정 후 합치는지
- 로봇 고장 시 기존 예약 해제를 한 번만 하는지
- 물체 ID 추적이 프레임마다 새로 생성되는지

### 영상이 끊겨도 로봇이 계속 간다

- 서버 안전감시만 믿지 말고 로봇 로컬 TTL 적용
- 전체 경로를 한 번에 실행하도록 보내지 않음
- 마지막 telemetry가 아니라 마지막 유효 명령 시각 검사
- 통신 복구 시 이전 큐를 비움

### 시뮬레이션을 돌릴 때마다 결과가 다르다

- 모든 난수에 같은 generator를 주입했는지
- 시스템 시계가 계획 비용에 들어가는지
- dictionary/set 순서에 의존하는지
- 스레드 완료 순서가 상태 갱신 순서를 바꾸는지
- seed와 설정을 로그에 저장했는지

### CPU 사용률이 높다

- 영상 표시와 원본 처리를 분리
- 임무 배정을 프레임마다 하지 않음
- 경로를 사건 기반으로 재계산
- 전체 1080p 대신 보정 후 필요한 해상도 사용
- 로그 저장을 비동기화
- 프로파일링 없이 감으로 최적화하지 않음

## 34. 권장 개발 의사결정

현재 준비물이 전혀 없는 상황에서는 다음 선택이 가장 안전하고 빠르다.

1. 중앙 Python 프로그램과 결정적 시뮬레이터부터 만든다.
2. 기본값은 6대로 두되 로봇 수를 설정 가능하게 한다.
3. 처음에는 세계 상태 직접 관측으로 계획과 상태기계를 검증한다.
4. 그다음 합성 영상으로 비전 경계를 검증한다.
5. 실제 하드웨어는 관측·명령 폐루프를 먼저 구현·검증한 뒤 어댑터 하나씩 연결한다.
6. 고정 상부 카메라 방식을 기준 시스템으로 완성한다.
7. 드론은 동일한 관측 인터페이스를 쓰는 선택 기능으로 추가한다.
8. 실전 로봇 수는 출발구역과 반복 성공률을 측정한 뒤 2~6대 중 결정한다.

핵심은 코드 양이 아니라 **경계를 잘 나눈 구조, 재현 가능한 로그, 고장 시 정지하는 동작**이다. 이 세 가지가 갖춰지면 실제 모터나 카메라가 나중에 바뀌어도 프로젝트 전체를 다시 만들 필요가 없다.

## 35. 다음 작업 제안

이 문서를 기준으로 저장소의 첫 구현은 다음 순서로 커밋하는 것이 좋다.

1. `config/domain/logging` 뼈대
2. 1대 차동구동 시뮬레이터
3. 점유격자와 A*
4. 6대 예약 충돌 회피
5. 물체·상태기계·점수
6. 120초 경기 통합
7. 실패 주입과 자동시험
8. 합성 영상과 비전 어댑터
9. 운영 화면
10. ESP32와 카메라 실물 어댑터

각 커밋은 실행 가능하고 테스트를 통과해야 한다. “전체 기능을 한 번에 완성한 큰 커밋”보다 작은 단계가 실제 장비 연동에서 문제를 찾기 쉽다.

이 가이드의 설계는 기존 상세 기록인 `ROBOTICS_PROJECT_FULL_RECORD_KO.txt`의 결론을 구현 가능한 형태로 구체화한 것이다. 대회 규정, 실제 경기 요소 치수, 드론 허용 여부가 바뀌면 설정과 관련 어댑터를 먼저 수정하고, 중앙 도메인과 안전 원칙은 유지한다.
