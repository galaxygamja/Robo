# Robo Control Lab 상세 테스트 계획

> 대상: 현재 저장소의 `robo_control` 패키지와 6대 로봇 시뮬레이터  
> 기준 설정: `config/default.json`  
> 테스트 프레임워크: Python 표준 라이브러리 `unittest`  
> 작성 기준일: 2026-09-04  
> 범위: 부품 없이 실행되는 v0.1의 검증과 향후 카메라·ESP32·드론 연결 전후의 검증 계획

이 문서는 이미 자동화된 시험과 앞으로 만들어야 할 시험을 분명히 구분한다.
계획에 적혀 있다는 이유만으로 기능이 구현됐거나 검증됐다고 간주하면 안 된다.

## 1. 상태 표기

문서 전체에서 다음 표기를 사용한다.

| 표기 | 의미 |
|---|---|
| **자동화 완료** | 현재 `tests/`에 실행 가능한 `unittest`가 있으며 2026-09-04 기준 통과했다. |
| **자동화 필요** | 소프트웨어만으로 만들 수 있으나 현재 대응 테스트가 없거나 충분하지 않다. |
| **기능 구현 필요** | 테스트보다 먼저 제품 코드 또는 고장 주입 지점이 추가되어야 한다. |
| **실물 검증 필요** | 카메라, ESP32, 모터, 로봇 또는 드론 없이는 최종 합격을 판정할 수 없다. |
| **수동 확인 필요** | 브라우저 표시, 물리 비상정지처럼 사람이 직접 확인할 항목이다. |

`자동화 완료`는 현재 구현 범위에 대한 회귀시험이 있다는 뜻이다. 실제 대회
환경에서 안전하다는 인증은 아니다.

### 2.2 기본 설정값

아래 값은 `config/default.json`과 일치해야 한다.

| 항목 | 현재 값 | 테스트에서의 의미 |
|---|---:|---|
| 경기장 폭 × 높이 | 1.143 × 1.181m | 모든 좌표와 경계 판정의 기준 |
| 격자 한 칸 | 0.020m | 한 경로 tick당 이동 거리 |
| 경계 추가 여유 | 0.025m | 계획 격자의 경계 팽창에 사용 |
| 경기시간 | 120.0초 | timeout 판정 기준 |
| 로봇 수 | 6 | 기본 통합 시나리오 수량 |
| 제어 주기 | 20Hz | background loop 목표 주기 |
| 계획 주기 | 4Hz | 현재는 설정만 있고 자동 주기 재계획에는 사용되지 않음 |
| 시뮬레이션 배속 | 1.0 | `step()`의 시간 배율 |
| 로봇 원형 반경 | 0.063m | 미검증 단순 원형 모델. 126×100mm 차체의 임의 자세에는 보수적이지 않음 |
| 선속도 | 0.20m/s | 경로 한 칸을 약 0.1초에 이동 |
| 목표 허용오차 | 0.025m | 마지막 경로 tick에서 목표까지의 도착 판정 기준 |
| 추적 timeout | 0.5초 | 현재 안전정지 로직에는 연결되지 않음 |
| 명령 timeout | 0.5초 | 현재 수신기/watchdog이 없어 실행되지 않음 |
| 계획 최소 중심거리 | 0.138m | 예약표가 요구하는 로봇 중심 간 거리 |

계획 예약과 `SimulationEngine._validate_safety()`는 모두 중심거리 0.138m
미만을 현재 소프트웨어 안전 위반으로 판정한다. 그러나 126×100mm 직사각형의
외접반경은 약 80.4mm이고, 반경 63mm 원은 회전한 차체를 감싸지 못한다.
따라서 0.138m를 유지해도 실물 직사각형 차체의 비접촉을 보장하지 않으며,
방향 있는 외형과 실측 여유를 사용한 별도 시험이 필요하다.

### 2.3 2026-09-04 실행 기준선

다음 명령과 같은 방식으로 현재 시험을 실행했다.

```powershell
python -m unittest discover -s tests -v
python -m robo_control --headless
```

검증 환경에서는 Python 3.12.14를 사용했다. 프로젝트의 지원 하한인 Python
3.11에서도 별도로 실행해야 한다.

- `unittest` 24개: 모두 통과
- 전체 테스트 시간: 약 1.68초
- 기본 headless 실행: `completed`
- 기본 headless 완료 시뮬레이션 시각: 약 8.05초
- 완료 임무: 6/6
- 충돌 기록: 0
- 100회 벤치마크: 100/100 완료, 100/100 충돌 기록 0
- 100회 벤치마크 계획시간: 평균 61.328ms, p95 71.633ms, 최대 75.243ms

이 벤치마크는 같은 결정적 기본 시나리오를 반복한 것으로 무작위 배치 내구성
시험이 아니다. 실행시간과 계획시간은 컴퓨터·Python·부하에 따라 바뀌므로
고정된 정답이 아니다.
회귀 비교에는 평균만 쓰지 말고 p95, p99와 최댓값을 함께 기록한다.

## 3. 현재 자동화가 보장하는 범위

### 3.1 임무 배정

**자동화 완료**

- 입력 로봇과 임무 순서가 뒤섞여도 단순 예제에서 최소비용 배정 결과가
  `R1→T1`, `R2→T2`로 결정된다.
- `completed=True`인 임무는 배정 대상에서 제외된다.
- 임무가 8개를 넘는 경우에도 greedy fallback이 임무를 중복 배정하지 않고
  같은 입력에 같은 결과를 낸다.

현재 시험은 2대·2임무의 정확 배정과 6대·9임무 fallback의 결정성만 다룬다.
6대 전체 최적성, 우선순위 효과, 동률, 로봇보다 임무가 적은 경우는 아직
보장하지 않는다. 어느 한쪽이라도 8개를 넘는 fallback은 전역 최적해를
보장하지 않는다.

### 3.2 공간-시간 경로 계획

**자동화 완료**

- 경기장을 가로지르는 벽이 있을 때 도달 불가능한 목표가 `None`을 반환한다.
- 고정 격자의 연결 성분 사전검사가 정적 벽으로 분리된 목표를 시공간 A* 확장
  전에 거부한다.
- 두 로봇이 서로 반대편 위치로 교환하는 예제에서 같은 tick의 같은 cell을
  점유하지 않는다.
- 같은 두 로봇이 한 tick 동안 서로의 이전 cell을 맞바꾸는 edge swap을
  만들지 않는다.

추가 회귀시험은 두 선형 이동의 연속시간 최소거리와 목표 도착 뒤 horizon
장기 점유도 검사한다. 다만 임의 6대 교착과 모든 경계·장애물 팽창 조합까지
보장하는 것은 아니다.

### 3.3 시뮬레이션

**자동화 완료**

- 기본 설정에서 가상 로봇 6대가 모두 임무에 도착한다.
- 기본 데모 중 설정된 최소 중심거리 0.138m보다 가까워지지 않는다.
- 기본 데모의 `collision_count`가 0이고 완료 임무가 6개다.
- 사용자 시나리오의 로봇 1대가 남은 임무를 자동 재배정하여 임무 2개를
  여러 라운드로 처리한다.
- 남은 목표가 도달 불가이면 `planner_stalled`와 함께 일시정지하며, 매 tick
  같은 재계획을 반복하지 않는다.
- 긴급정지 후 상태가 `safety_stop`, 각 로봇이 `stopped`가 되고 추가
  `step()` 호출에도 위치가 변하지 않는다.
- 긴급정지 뒤 수동 `replan()`을 호출해도 안전정지가 해제되지 않는다.
- 초기화 전후 생성된 경로가 동일하며 상태가 `ready`로 돌아온다.

현재 기본 6대, 1대 다중 라운드, 도달 불가 일시정지 시나리오를 검증한다.
정확한 120초 timeout, 일시정지 중 위치 고정, 일반 이동 중 수동 재계획,
장애물과의 런타임 충돌, 다른 `dt`와 배속은 아직 시험하지 않는다.

### 3.4 HTTP 서버

**자동화 완료**

- 임의의 빈 포트에서 서버를 시작할 수 있다.
- `GET /api/state`가 `ready` 상태와 로봇 6대를 반환한다.
- `POST /api/mission/start` 후 요청이 성공한다.
- `POST /api/mission/pause` 후 응답 상태가 `paused`다.
- 시험 종료 때 서버와 background simulation thread를 닫는다.

`/healthz`, reset, replan, stop, 잘못된 주소, 응답 헤더와 동시 요청은 아직
자동화되지 않았다.

## 4. 현재 자동화되지 않았거나 구현되지 않은 범위

### 4.1 설정만 있고 동작에는 연결되지 않은 값

다음 값은 설정 모델에 존재하지만 현재 제품 동작 또는 시험이 충분히 연결되지
않았다.

- `mission.planner_hz`: 자동 4Hz 재계획 없음
- `robot.tracking_timeout_s`: 실제 관측 갱신과 추적 손실 정지 없음
- `robot.command_timeout_s`: 명령 수신기와 로컬 watchdog 없음
- `network.robot_udp_port`: 기본 실행에서 사용하지 않음
- `safety.stop_on_tracking_loss`: 현재 참조되지 않음
- `safety.stop_on_predicted_collision`: 현재 참조되지 않음

`robot.goal_tolerance_m`는 현재 경로 마지막 tick에서 목표까지의 도착 판정에
사용된다. 다만 허용오차 경계의 바로 안·밖을 비교하는 전용 회귀시험은 아직
없다.

이 항목은 단순히 테스트만 추가해서 완료할 수 없다. 먼저 기대 동작을 구현한
뒤 고장 주입 시험을 작성해야 한다.

### 4.2 시뮬레이터가 아직 모델링하지 않는 현실 요소

**기능 구현 필요**

- 차동구동 운동학, 회전시간, 가속·감속, 정지거리
- 좌우 모터 편차, 바퀴 미끄러짐, 배터리 전압에 따른 속도 변화
- 프레임 사이 swept collision
- 로봇과 정적 장애물의 런타임 외형 충돌
- 센서 관측 잡음, 지연, 누락과 재획득
- 포획, 운반, 배출, 게이트 상태기계
- 점수와 105~110초 이후 신규 임무 제한
- 통신 ACK, sequence/TTL 검증, ESP32 측 watchdog
- seed 기반 무작위 시나리오 생성 및 로그 replay

현재 시뮬레이션은 계획 경로를 일정 속도로 선형 보간한다. 따라서 현재 성공은
실제 차체가 같은 경로를 추종할 수 있다는 증거가 아니다.

### 4.3 하드웨어 경계

**실물 검증 필요**

- `OpenCVCameraSource`의 실제 USB/RTSP 프레임률, 끊김, 재연결
- AprilTag/ArUco 검출과 경기장 호모그래피 정확도
- `UdpRobotTransport` 이후 ESP32의 명령 검증과 모터 정지
- 실제 엔코더 PID와 목표 위치·방향 오차
- 물리 비상정지와 전원 차단
- 드론 스트림 지연, 체공 흔들림, 조종기 자동화와 failsafe

`DisabledDroneController`가 호출을 거부하는지는 소프트웨어 단위시험으로
확인할 수 있지만, 실제 드론 안전성을 의미하지 않는다.

## 5. 결함 심각도와 공통 불변조건

### 5.1 결함 심각도

| 등급 | 정의 | 예 |
|---|---|---|
| P0 | 사람·기체·득점물을 위험하게 하거나 안전정지를 무력화 | 로봇 겹침, 벽 이탈, 만료 명령 실행, 긴급정지 후 이동 |
| P1 | 경기를 사실상 실패시키는 핵심 기능 오류 | 6대 교착, 임무 이중 배정, 도달 가능한 경로를 반복 실패, 서버 crash |
| P2 | 성능·운영 신뢰도를 크게 낮춤 | p99 지연 초과, 상태와 화면 불일치, 재계획 진동 |
| P3 | 결과에는 영향이 작지만 수정해야 하는 표시·문서 문제 | 정렬, 사소한 메시지, 비핵심 표시 오차 |

P0 또는 P1이 하나라도 재현되면 해당 빌드는 배포 불가다.

### 5.2 매 tick 확인할 불변조건

시나리오 시험은 종료 결과만 보지 말고 매 tick 다음을 확인해야 한다.

1. 모든 좌표, 각도, 시간, 속도는 유한수이며 `NaN`이나 무한대가 아니다.
2. 로봇 중심에서 경기장 경계까지 거리가 최소 반경 이상이다.
3. 서로 다른 두 로봇의 실제 외형이 겹치지 않는다.
4. 명목 운용에서는 중심 간 거리가 `minimum_separation_m` 이상이다.
5. 임무 하나는 동시에 한 로봇에만 배정된다.
6. 로봇 하나는 동시에 하나의 활성 임무만 가진다.
7. 완료된 임무가 다시 미완료로 돌아가지 않는다.
8. `safety_stop` 또는 `timeout` 후 위치가 바뀌지 않는다.
9. 경로 점은 경기장과 허용 공간 안에 있고 정적 장애물을 통과하지 않는다.
10. `elapsed_s`는 감소하지 않고 120초를 넘지 않는다.

현재 코드에서는 3번을 원형 중심거리로만 근사한다. 직사각형 차체와 방향이
추가되면 SAT 또는 동등한 다각형 충돌 판정으로 교체해 검증한다.

## 6. 모듈별 자동화 계획

### 6.1 `config.py`

## 8. 알고리즘 oracle과 판정법

### 8.1 단일 로봇 최단경로 oracle

작은 격자에서는 별도의 단순 BFS 또는 Dijkstra를 시험 코드 안에 구현해 A*
경로 비용과 비교한다. 제품 코드를 oracle로 재사용하면 같은 버그가 양쪽에
존재할 수 있으므로 금지한다.

합격 조건:

- 모든 이동은 상하좌우 한 cell 또는 wait다.
- 정적 장애물과 경계를 통과하지 않는다.
- 예약이 없으면 반환 비용이 oracle 최솟값과 같다.
- 예약이 있으면 시간축을 포함한 작은 상태공간 exhaustive search와 같다.

### 8.2 충돌 oracle

현재 계획기의 단순 원형 모델에서는 각 연속 시각 구간의 두 선형 궤적 사이
최소거리를 계산한다. 단순히 tick 끝점만 비교하지 않는다.

- 현재 계획·런타임 안전 실패: 중심거리 `< 0.138m`
- 벽 실패: 중심이 반경 0.063m보다 벽에 가까움
- 정적 장애물 실패: 로봇 원과 장애물의 거리가 0보다 작음

이 기준은 소프트웨어 모델 안의 판정일 뿐이다. 126×100mm 차체의 외접반경은
약 80.4mm이므로 반경 63mm 원과 138mm 중심거리는 임의 heading에서 실물
차체 비접촉을 보장하지 않는다. 차체를 방향 있는 직사각형으로 바꾸면 swept
polygon 또는 실측으로 검증한 충분히 보수적인 연속 충돌검사를 사용한다.

### 8.3 임무 배정 oracle

최대 6대·6임무는 모든 permutation을 독립적으로 열거할 수 있다. 제품의
`assign_tasks()`가 반환한 합계 비용이 독립 oracle의 최솟값과 같은지 비교하고,
동률일 때 ID 순서가 안정적인지 확인한다.

### 8.4 결정성 비교

같은 scenario, 설정과 입력 순서로 20회 실행한다.

비교 대상:

- 로봇별 배정 임무
- 모든 path 좌표와 wait 위치
- 완료 순서와 시뮬레이션 tick
- 상태 전이와 안전 event 순서
- 최종 위치, 상태, 임무 완료 수

제외 또는 허용오차 대상:

- `planning_ms`
- `time.monotonic()` 기반 camera timestamp
- OS가 선택한 임시 HTTP port

## 9. 성능·부하·장기 실행

### 9.1 계획 성능

**부분 자동화·수동 측정 도구 있음**

고정된 기준 컴퓨터와 Python 버전을 CI 기록에 남긴다. 6대 기본 설정에 대한
초기 목표와 현재 100회 측정은 다음과 같다.

| 지표 | 장기 목표 | 현재 100회 기준선 |
|---|---:|---:|
| `plan_all()` 평균 | 기록 | 61.328ms |
| `plan_all()` p95 | 50ms 이하 | 71.633ms — 목표 미달 |
| `plan_all()` p99 | 100ms 이하 | 도구가 아직 미출력 |
| 단일 계획 최댓값 | 200ms 미만 | 75.243ms |
| 계획 중 예외/timeout | 0 | 0 |

현재 값은 `tools/benchmark.py --runs 100`이 같은 결정적 기본 시나리오를
반복한 결과이며, 실행 환경에 따라 달라진다. p95 50ms 목표는 아직 통과하지
못했다. 다음 단계에서는 warm-up 후 1,000회 분포와 p99도 측정하고, 무작위
시나리오 기능 회귀와 성능 회귀를 분리해 보고한다.

### 9.2 제어와 HTTP 부하

**자동화 필요**

- background simulation 20Hz를 10분 유지한다.
- 동시에 `/api/state`를 초당 20회 읽는다.
- start/pause/replan 요청을 안전한 고정 시퀀스로 반복한다.
- 프로세스 메모리, thread 수, loop 지연을 시작과 종료에 비교한다.
- dashboard가 느려져도 simulation time과 안전감시는 막히지 않아야 한다.

합격 목표:

- uncaught exception 0
- thread 수의 지속 증가 0
- 10분 후 메모리의 단조 무제한 증가 0
- 상태 JSON 손상 0
- 실제 관측부터 명령까지의 장기 목표 p99 200ms 이하

마지막 지표는 실제 관측·명령 파이프라인이 구현된 뒤 측정한다.

### 9.3 Monte Carlo

**기능 구현 필요**

현재 seed 기반 시나리오 생성기가 없으므로 아직 자동화할 수 없다. 생성기를
추가한 뒤 다음 두 묶음을 실행한다.

1. 명목 배치 1,000 seeds
2. 지연·잡음·손실을 포함한 결함 배치 100 seeds

합격 목표:

- 명목: 물리 충돌 0, 경계 침범 0, reachable 임무 완료율 95% 이상
- 결함: 충돌 0, 경계 침범 0, 요구된 watchdog 안전정지 100%
- 모든 실패 seed, 설정, 첫 위반 tick과 snapshot을 저장

임무 성공률보다 안전률을 우선한다. 경로가 없어 정지한 run은 임무 실패일 수
있지만 안전 실패는 아니다.

## 10. 120초 경기 회귀 시험

기본 데모는 약 8초에 모든 가상 임무를 끝내므로 120초 timeout 자체를
검증하지 않는다. 전체 경기 회귀는 긴 경로, 후속 임무 또는 의도적 대기를
포함한 별도 시나리오가 필요하다.

### 10.1 소프트웨어 합격 게이트

| Gate | 진입 조건 | 합격 조건 |
|---|---|---|
| G0 현재 회귀 | 저장소 checkout | 기존 24개 unittest 전부 통과 |
| G1 핵심 단위 | config/models/planner 시험 추가 | P0·P1 실패 0, 핵심 분기 coverage 90% 목표 |
| G2 6대 결정 시나리오 | SCN-N/U/T 구현 | 각 시나리오 20회 동일 결과, 충돌·경계 위반 0 |
| G3 고장 주입 | tracking/network/dynamics 구현 | 모든 timeout에서 안전정지, stale 명령 0 |
| G4 무작위 회귀 | seed generator와 replay 구현 | 명목 1,000 seeds 안전 위반 0 |
| G5 120초 모의 경기 | 점수와 상태기계 구현 | 100회 중 목표점수 80회 이상, 안전 위반 0 |
| G6 HIL | ESP32·카메라 1대 연결 | 500ms watchdog 100%, 위치·지연 기준 통과 |
| G7 실물 다중 | 2대→3대→최대 6대 | 단계별 10회 중 8회 목표, 물리 안전 위반 0 |

자동 배포 또는 release tag는 최소 G2까지 통과해야 한다. 실제 장치 출력을
활성화하는 release는 G6 이전에 만들지 않는다.

### 10.2 빌드 중단 조건

다음 중 하나라도 있으면 즉시 실패로 판정한다.

- 로봇 실제 외형 겹침 1회
- 경기장 벽 또는 정적 장애물 침범 1회
- 긴급정지·timeout 뒤 이동 1회
- 만료되거나 역순인 명령 실행 1회
- 임무 이중 소유 1회
- `NaN`, 무한대, uncaught exception 1회
- 같은 입력의 비결정적 경로 또는 상태 전이
- 도달 불가 검색이 제한시간 안에 끝나지 않음

| 경기장 보정 성공률 | 100 frame 중 99 이상 |
| 바닥 기준 위치오차 | 15mm 이하 |
| 방향오차 | 5° 이하 |
| 영상→명령 종단 지연 | p99 200ms 이하 |
| 0.5초 이상 추적 손실 | 해당 로봇 정지 |

색상 인식은 사용자의 최신 요구에서 필수로 보지 않는다. 코어 합격 게이트에
넣지 않는다. 대회 임무상 다시 필요해질 때 별도 선택 모듈과 데이터셋으로
검증한다.

## 12. ESP32와 통신 시험

### 12.1 소프트웨어 loopback

**자동화 필요**

- 로봇 ID별 UDP endpoint로 올바른 JSON 전송
- sequence, server time, TTL, action, target, 속도 제한, gate 포함
- endpoint가 없는 ID는 송신하지 않고 명확한 오류
- payload 크기와 UTF-8 인코딩 기록

### 12.2 Hardware-in-the-loop

**실물 검증 필요**

1. 모터 전원을 분리한 ESP32로 sequence/TTL 시험
2. 바퀴를 공중에 띄우고 만료 명령 정지 시험
3. 지면에서 저속 한 대 주행
4. Wi-Fi 10% 손실과 200ms 지연 환경
5. 서버 프로세스 강제 종료와 AP 전원 차단
6. 실제 2대, 3대, 필요할 때만 6대로 확대

필수 합격 기준:

- 마지막 유효 명령 후 500ms 이내 모터 정지 100%
- 역순·중복·만료 command 실행 0
- 잘못된 robot ID에 반응 0
- 재연결 직후 과거 큐 재생 0
- 물리 비상정지 작동 100%

## 13. 드론 시험

현재 `DisabledDroneController`만 있으므로 실제 드론 출력은 미구현이다.

### 13.1 지금 자동화할 수 있는 것

**자동화 필요**

- `takeoff`, `hold`, `land`, `emergency_stop` 네 호출이 모두
  `RuntimeError`로 닫힘
- 기본 실행 경로가 어떤 드론 메서드도 호출하지 않음
- 드론 adapter가 없어도 지상 로봇 시뮬레이션 완료

### 13.2 나중에 실물로 확인할 것

**실물 검증 필요**

- 운영진의 드론·조종기 자동화 허용 서면 확인
- 프로펠러 제거 상태에서 축 중립·최소·최대 검증
- 독립 비상착륙과 링크 손실 failsafe
- 120초 체공 중 영상 끊김, 흔들림, 프레임률
- 드론 영상 실패 시 고정 카메라 전환
- 프로펠러 바람이 경기 물체와 지상 로봇에 미치는 영향

드론 시험 결과는 지상 로봇 코어 시험을 대체하지 않는다.

## 14. 로그와 재현성

현재 `JsonlLogger`는 존재하지만 SimulationEngine에 연결되어 있지 않다.
따라서 **기능 구현 필요** 상태다.

모든 시나리오 run이 남겨야 할 최소 정보:

- Git commit ID와 Python 버전
- 설정 전체 사본
- scenario 이름과 random seed
- 시작·종료 상태와 시뮬레이션 시간
- tick 번호와 dt
- 로봇별 위치·상태·임무·경로 tick
- 임무 배정과 재계획 이유
- 안전 이벤트와 최초 위반 시각
- 계획시간과 루프시간의 p50/p95/p99/max
- 최종 완료 임무, collision, unresolved 수

실패 시에는 최초 위반 전후 최소 2초의 상태를 보존한다. 동일 로그를 replay해
첫 차이 tick을 찾아야 하며, 화면 녹화만으로 결함을 닫지 않는다.

결정성 합격 기준:

- 같은 commit/config/seed/input log를 20회 replay
- wall-clock metric을 제외한 상태 hash와 event 순서 일치
- 차이가 있으면 첫 tick, 필드 경로와 두 값을 출력

## 15. 수동 관제 화면 점검

**수동 확인 필요**

자동 API 시험이 통과한 뒤 브라우저에서 다음을 확인한다.

- 경기장 비율이 1.143:1.181로 표시됨
- 녹색 출발구역이 0.48×0.28m 위치와 일치
- 로봇 6대 ID, 진행방향, 경로와 배정 임무가 snapshot과 일치
- 장애물과 목표가 올바른 좌표에 표시
- start, pause, reset, replan, emergency stop 버튼 결과가 API와 일치
- pause와 stop 상태에서 화면 속 로봇도 움직이지 않음
- timer가 감소하고 completed 시 조기 종료 상태를 표시
- 안전 이벤트가 최신순으로 보이고 원인과 robot ID가 읽힘
- 브라우저 새로고침 후 엔진 상태를 잃지 않음
- 모바일 폭에서도 제어 버튼과 긴급정지가 가려지지 않음

관제 화면은 제어 권한의 근거가 아니라 관찰 도구다. 화면 렌더링 오류가
SimulationEngine의 안전감시를 중단해서는 안 된다.

현재 외부 의존성 없이 실행되는 장점을 유지한다. 성능 측정과 실제 카메라처럼

## 19. 최종 판정 원칙

현재 v0.1에 대해 사실대로 말할 수 있는 범위는 다음과 같다.

- 기본 6대는 6/6 완료되고, 사용자 시나리오의 1대도 자동 다중 라운드로 임무 2개를 완료한다.
- 시험된 경로에서 vertex/edge swap, tick 중간 swept 최소거리, 목표 장기 점유,
  정지·미해결 로봇 예약을 처리한다.
- 정적 연결 성분 사전검사로 완전히 분리된 목표를 시공간 확장 전에 거부한다.
- 시험된 시뮬레이션에서 0.138m 중심거리 위반을 검출하지 않았다. 다만 이
  원형 근사는 실제 126×100mm 회전 차체에 보수적이지 않다.
- 소프트웨어 긴급정지가 추가 이동을 막는다.
- 최소 HTTP 관제 API가 동작한다.

아직 말할 수 없는 범위는 다음과 같다.

- 모든 6대 배치에서 교착과 충돌이 없다.
- 모든 배치와 실제 경로에서 최소거리 0.138m가 연속시간 전체에 유지된다.
- 추적 또는 통신이 500ms 끊기면 실제 로봇이 정지한다.
- 120초 실제 경기에서 목표점수를 안정적으로 얻는다.
- 실제 카메라, ESP32, 모터 또는 드론이 안전하게 동작한다.

새 기능을 배포할 때는 이 문서의 상태를 함께 갱신한다. 시험을 추가해 실제로
통과한 항목만 `자동화 완료`로 변경하고, 실물 시험 없이 하드웨어 항목을
완료로 표시하지 않는다.
