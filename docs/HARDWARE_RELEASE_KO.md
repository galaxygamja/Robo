# 소프트웨어 v0.2.0 · 실물 연결 준비 배포

2026-09-18. 대상은 ESP32-C3 SuperMini, DRV8833, N20 6 V 100 RPM 모터 2개, MG90S 서보를 사용하는 H1/H2/B1/B2다. H2는 세 번째 비버 B3의 기존 내부 ID다. CAD 버전과 소프트웨어 버전은 별개다.

## 이번에 연결한 것

- `firmware/`: ID별 네 빌드 환경, 모터 두 개·서보 한/두 개 출력, H1 광센서, 부팅 정지, 보드 자체 250 ms 이내 명령 만료, 비상정지 잠금.
- `robo_control.hardware`: 부품 설정 검사, 실측 속도표를 이용한 좌우 PWM 변환, 네 로봇 비동기 UDP 통신, 바퀴·서보 개별 시험.
- `robo_control.hardware_runtime`: 실제 카메라/AprilTag 측정 → 기존 좌표·신선도·경로·충돌 검사 → 차동 명령 → 실제 송신. 영상 처리는 별도 프로세스에서 실행한다.
- `robo_control.hardware_calibration`: 실제 태그 로그의 일정 속도 구간에서 좌우 PWM 속도표 후보를 계산한다. 재생·유실·역순 프레임을 거부하며 실측 완료 처리는 자동으로 하지 않는다.
- `config/hardware.example.json`, `SETUP_HARDWARE.bat`: 설치와 개인 설정 시작점.
- 새 GitHub Actions: 4대 펌웨어 빌드, 보드 watchdog C++ 시험, Windows/Linux 실제 연결부 회귀시험, 출력 비활성화 펌웨어 아티팩트.

자세한 시작 순서는 [HARDWARE_START_KO.md](HARDWARE_START_KO.md), 통신 형식은 [firmware/PROTOCOL.md](../firmware/PROTOCOL.md)를 따른다. 이 버전의 `robo-hw` 프로토콜은 기존 가짜 수신기 시험용 `robo-wire`와 다르다.

## 검증 범위

자동 시험은 프로필 오류, 누락·중복 로봇, 모터 방향 계산, 출력 한도, 잘못된 ACK, 늦은 응답, 명령 재생 방지, 부팅 ID 변경, 센서 응답 신선도, 영상 유실과 통신 실패 시 전체 중단을 검사한다. Python 통신기는 실제 localhost UDP로도 확인한다. 펌웨어와 호스트는 공통 예제 패킷으로 형식을 대조한다.

보드에 업로드하거나 실제 모터를 구동하는 동작은 배포 과정에서 하지 않는다. 실물 주행, 태그 부착 오프셋, 모터 속도표, GPIO 배선, 무선 지연, 전원 부하, 서보 끝점, 제동 거리는 이 결과로 인증되지 않는다. 정상 통신 응답은 동작/집기 성공의 증거가 아니다.

## 아직 실물 확인이 필요한 경계

- 처음 받은 펌웨어는 `HARDWARE_OUTPUT_ENABLED=0`이고 개인 설정도 미보정이다. 실제 Wi-Fi/IP, 전원·핀맵, 태그의 바퀴 축 중점 오프셋, 바퀴 간격, 속도표를 채운 뒤 출력 활성화 옵션으로 실행한다.
- MG90S에는 코드가 읽을 서보 위치 피드백이 없고 비버에는 물체 유무 센서가 없다. 현재 임무 상태기는 필요한 확인이 없으면 기다리다가 정지한다. 완전 자율 집기·배출·대회 완주가 검증된 배포가 아니다.
- 기존 임무의 `arm_retract`는 현 CAD의 독립 구동기가 아니다. 의료키트 두 개 적재 게이트도 정확한 한 개 배출이 검증되지 않았다. 이를 다른 서보 프리셋이나 시간 지연으로 성공 처리하지 않는다.
- 실제 드론의 비행 제어 규격과 움직이는 카메라 보정은 미확정이므로 자율비행 출력을 추가하지 않았다. 기존 드론 시뮬레이션은 실물 비행 제어가 아니다.
- 구매한 XL4015의 제조사 입력 범위는 8–36 V여서 2S 7.4 V 배터리의 정상 방전 구간 전체에 대한 전원 호환을 보장하지 않는다. 전원부 확인을 먼저 진행한다.

기존 웹 시뮬레이터는 소프트웨어 연습용으로 유지하며, 그 시작 버튼을 누른다고 실물 로봇에 명령을 보내지 않는다. 이번 배포 위치는 GitHub 저장소와 설치 가능한 Python 패키지다.
