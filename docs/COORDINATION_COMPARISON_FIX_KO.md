# 드론 없음 정상 실행과 공정한 드론 활용 비교 — 2026-09-06 후속 수정

## 무엇이 문제였나

사용자가 지적한 **두 모드 모두 41.3초가 남는다**는 결과를 재현했습니다. 이전 정상 장면은 78.66초에 끝났고, 드론 있음/없음의 지상 궤적과 대기 시간이 같았습니다. 이미 완전한 연습 지도와 정상 위치 입력을 제공하면서 작업 순서도 고정했기 때문에, 드론이 더 관측해도 일정이 바뀌지 않았습니다. 관측 화면만 추가한 것으로 정상 임무가 더 빨라지지는 않았습니다.

‘드론 없음’ 비교 버튼에는 H2 위치 입력을 계속 끊는 가림 시험이 연결되어 있었습니다. 이 경우 정지는 안전 동작이지만, 정상 실행과 구분하기 어려운 화면이었습니다. 정상 모드 자체는 첫 로봇이 4초에 출발해 완주합니다. 이번에는 이 두 문제를 분리해 수정했습니다.

## 바로 사용하는 방법

[공개 시뮬레이터](https://robo-six-arena-simulator.magic-shark-7297.chatgpt.site/)에서 다음을 사용합니다.

1. **드론 없이 정상 실행 / 박쥐와 정상 실행**: 고장 설정을 모두 지우고 자동 시작합니다. 처음 4초의 출발 준비와 현재 정지 이유를 표시합니다.
2. **공통 경로·작업 순서 최적화**: 두 모드에 같은 알고리즘을 적용합니다. 끄면 기존 계획을 비교할 수 있습니다. 변경하면 경기를 다시 시작합니다.
3. **같은 조건 · 세 모드 비교**: 정상 입력, 간헐 누락, 지속 가림 중 비교 조건을 고릅니다. ‘세 모드 결과 한 번에 계산’은 별도 Web Worker에서 현재 엔진을 실제 실행해 결과를 계산합니다. 현재 지도 경기를 바꾸지 않으며 결과를 하드코딩하지 않습니다. 계산을 중단할 수도 있습니다.
4. 개별 드론 없음/중앙 관측/이동 관측 버튼은 **선택한 시험 조건**을 지도에서 재생합니다. 고장 조건이면 타이머 위에 조건을 표시하고, ‘고장 없는 정상 조건으로 복귀’ 버튼을 제공합니다.

정상 실행과 고장 시험은 별개입니다. 특히 ‘가림 복구 시험’의 드론 없음이 멈추는 것은 모든 위치 입력을 일부러 없앤 시험이지 정상 모드의 고장이 아닙니다.

## 공통 최적화의 내용

### 1. 남은 작업 순서를 실제로 비교

같은 비버에 이미 배정된 미시작 원기둥 작업의 순서를 비교합니다. 현재 측정 위치→집기→회전 대기점→색별 목적지→후퇴→다음 작업→마지막 주차까지의 예상 이동거리를 사용합니다. 최대 6개 원기둥/720개 순열로 탐색량을 제한하며, 분명한 거리 개선이 있을 때만 바꿉니다.

드론의 새 물체 관측이 유효하면 위치 힌트를 갱신할 수 있고, 없으면 별도로 보존한 초기 연습 지도를 사용합니다. 초기 지도는 현재 물체 상태나 잘리는 이동 궤적 배열과 분리했습니다. 보이지 않는 물체가 바뀌었다고 초기 지도까지 자동으로 바뀌지 않습니다.

다른 비버의 물체를 빼앗거나 색별 목적지/투하 슬롯을 바꾸지 않습니다. 시작한 작업, 적재 중 물체, 큐브 매거진 순서, 햄스터 디스크 순서는 유지합니다. 다른 로봇의 미래 충돌까지 풀어 전역 최적을 증명하는 알고리즘은 아니며, 실행 중 기존 구역 잠금과 충돌 검사를 계속 적용합니다.

### 2. 격자 경로의 불필요한 꺾임 제거

A*가 만든 경로에서 멀리 있는 다음 지점으로 바로 갈 수 있으면 중간 지점을 줄입니다. 차체 중심선만 검사하지 않고, 현재 방향의 차체·집게·적재물 외곽이 지나가는 전체 영역을 기존 `segmentFree`로 검사합니다. 목표·기구 상태를 건너뛰거나 최소 간격 12mm를 줄이지 않습니다. 새로운 장애물로 기존 선분도 막혔으면 경로를 버리고 다시 계획합니다. 매 주행 단계의 충돌 검사도 유지합니다.

### 3. 긴 고정 회전 대기점 우회 감소

적재 후 멀리 떨어진 고정 대기점으로 항상 이동하는 대신, 80/120/160/200mm 후퇴 후보를 검사합니다. 후보까지의 이동, 적재 상태의 회전 샘플, 다음 목적지로 가는 선분이 모두 안전하고 예상 거리가 줄 때만 사용합니다. 회전 검사와 실제 회전은 여전히 이산 모형이며 실물 연속 충돌 안전을 증명하지 않습니다.

속도 0.22m/s, 서보/센서 확인 시간, 충돌 간격과 채점 조건을 그대로 두었습니다. 드론에만 속도 보너스를 주거나 드론 없음의 속도를 낮추지 않았습니다. **좋은 경로 알고리즘을 사용한 효과와 드론의 추가 관측 효과를 분리합니다.**

## 실제 드론의 이점을 해석하는 방법

정상이고 동일한 정보를 가진 시스템끼리 같은 시간에 끝나는 것은 정상입니다. 드론의 존재 자체가 모터나 집게를 더 빠르게 만들지는 않습니다. 이 버전은 다음 세 가지를 구분합니다.

- 경로와 작업 순서 개선: 양 모드 공통의 소프트웨어 이득.
- 기본 위치 관측 누락 보완: 추가 관측원의 이득. 중앙 관측도 가능할 수 있음.
- 중앙에서 가려진 대상을 다른 위치에서 찾기: 이동 관측의 이득.

현재 기본 위치 입력은 고정 카메라 2대를 의미하지 않는 합성 좌표 입력입니다. 실제 센서 방식·통신·정밀도는 아직 확정하지 않았습니다. 드론 영상, 동적 카메라 보정/PnP, 센서 간 시계 동기화, 펌웨어와 실제 기체 제어는 연결하지 않았습니다. 웹의 충돌/자유 공간 검사는 이상적인 장면 기하이고, 실제 픽셀에서 장애물 없는 영역을 추정한 것이 아닙니다. 센서·화각·태그·가림막·고장 패턴은 명시된 모의 가정입니다.

또한 물체의 ‘3회 연속 확인’은 이전 전달 프레임 시간 대신 **촬영 프레임 순번**으로 계산하도록 수정했습니다. 200ms 전달 지연에서도 연속 촬영 검출을 확인할 수 있고, 중간 촬영에서 놓치거나 보정이 실패하면 연속 횟수가 초기화됩니다. 오래된 전달 영상으로 최신 관측을 만들지는 않습니다.

결과 JSON은 완료/잔여 시간, 점수, 위치 대기, 지상 이동거리·회전량·교통 대기, 드론 복구 로봇·초, 계획 변경 횟수와 충돌/간격을 포함합니다. 공개 웹은 카메라나 서버에 이 결과를 전송하지 않습니다. 안전 시험실의 보고서는 schema v3이며 현재 경기 데이터를 저장합니다. 빠른 비교 결과는 별도로 계산한 경기입니다.

- `lib/mission.ts`: 공통 작업 순서/경로/회전 대기점 계획, 간헐 누락 일정, 실제 이동 계측.
- `lib/aerial.ts`: 별도 위치 관측 보완, 움직이는 시점 선택, 순번 기반 연속 검출.
- `lib/experiments.ts`: 정상/간헐/지속 가림 초기화와 같은 엔진의 비교 실행.
- `lib/comparison-worker.ts`: 화면을 막지 않는 브라우저 비교 계산.
- `components/aerial-panel.tsx`: 정상 실행, 공통 최적화 설정, 조건별 비교.
- `tests/coordination.test.ts`: 정상 드론 없음, 공통 최적화 공정성, 누락 복구, 경로 재검사, 작업 소유권, 초기 지도 불변, 전달 지연의 연속 검출.

웹 시험 52개 통과, TypeScript/lint 검사 통과를 확인했습니다. 기존 Python 영상·추적·모의 제어 코드는 이번에 수정하지 않았습니다. 실제 장치 출력은 계속 비활성입니다.
